## PSRAM・フレームバッファ・リング（第2段階）
- PSRAM 初期化は `psram/psram.c`（QMI M1、0xEB/0x38 の QPI、clk_sys÷3=100.8MHz）。**QMI のダイレクトモード中は XIP（フラッシュ含む）が止まる**ため、ダイレクトモード中に動くコードは SRAM 配置にし、フラッシュ上の関数を呼ばないこと（実際に停止した）。
- 実測: DMA 読み出し 41〜43MB/s（理論上限 50.4MB/s）。**640x480 RGB555 の表示コピーだけでフレーム時間の約85%（ライン周期の約93%）を使う**。CPU の PSRAM 描画に使えるのは残り約15%。空き帯域が少ないので、コピーが間に合わなければ `underrun` カウンタが増える。
- **フレームバッファ形式（2026-09-23 追加）**: `vga_set_mode()` で3形式から選ぶ。既定は `SGNANO_VIDEO_MODE`（main.c、既定 RGB555）。実行中は `v` キーで巡回切替できる（切替中は数ライン乱れる）。
  | モード | bpp | 1ライン | 全体 | PSRAM帯域 | CPU展開 |
  |---|---|---|---|---|---|
  | `VGA_MODE_RGB555` | 16 | 1280 B | 600 KB | 約23µs/ライン | なし |
  | `VGA_MODE_CLUT8` | 8（256色） | 640 B | 300 KB | 約12µs/ライン | 約11µs/ライン |
  | `VGA_MODE_CLUT4` | 4（16色） | 320 B | 150 KB | 約6µs/ライン | 約6µs/ライン |
  | `VGA_MODE_NONE`（第5段階 S3） | ― | ― | ― | **なし** | 背景色で埋める（約1µs/ライン） |
  - CLUT4 は **1バイトに2画素、上位ニブルが左の画素**。
  - パレットは `vga_set_palette()` / `vga_set_palette_all()` で設定する。色は `RGB()` マクロで作ったネイティブ形式で渡す。CLUT4 用に「パックド1バイト→2画素分の32bit」を引く表（`palette4x2`）も自動で作り直す。
  - **展開はリングスロット内で完結させる**（別バッファなし）。DMA でパックドデータをスロットの後ろ側（CLUT8はオフセット640、CLUT4は960）へ読み込み、CPU が前方へ展開する。書き込み位置は常に読み出し位置より手前になるので、前から順に「読んでから書く」限り安全。`scripts/test_expand.py` で同じ手順を再現して全640画素の一致を検証済み。
  - **モード切替は「表示経路をいったん完全に止めて作り直す」方式**（`display_stop()` → パラメータ変更 → `display_start()`）。部分的に差し替えるとレースが起きる。
  - **【重要・2026-09-23。2026-09-24 に PIO 側で対策済み】ライン同期の喪失**: RGB用SMは `wait 1 irq 4` でライン先頭を待つが、一度ずれると「フラグが既に立っている」ので素通りしてしまい、**ずれたまま安定する**。この状態では TX FIFO が毎ライン枯渇し（`fifo_stall` がライン周波数と同じ約31,480/秒で増える）、ブランキング期間にも映像が出るためモニタが同期できず「画面が出ない」になる。**モードを戻しても直らない**。
    → **2026-09-24、`vga.pio` の RGB用SMに `wait` の直前の `irq clear 4` を追加して自力で取り直せるようにした**（下の「ライン同期の自己復帰」を参照）。以下の記述は対策前の挙動。
    実機で CLUT4 へ切り替えたときに発生した。ログ上は `underrun` が増えず `min_ready=27`・`copy_max=12us` と**コピー側は正常**なのに映像が出ない、という形で現れる。切り分けには `fifo_stall` の増加率（ライン周波数と一致するか）を見るのが決定的。
  - 復帰は `vga_recover()`（= `display_stop()` + `display_start()`）。`V` キーで手動実行できる。
  - `display_stop()` での DMA 中止は、**RP2350 の errata E5 のとおり enable ビットを落としてから** `dma_hw->abort` を書く。落とさないと再トリガーされ、完了待ちから戻らなくなる恐れがある。待ちループには上限も設けている。
  - 診断: `[run]` 行にモード・`underrun`・`fifo_stall`・`min_ready`・`pair_max`・`timeout`・`recover` を出す。`[vga] state` / `[vga] disp` の詳細行はカウンタが増えたときだけ出る（`s` キーで常時表示に切替）。
  - 展開は `render.c` の `render_pair()` の中で両コアが行う（第5段階 S1 まで: `vga_copy_isr`、DMA_IRQ_1、優先度0x40）。SRAM 内で完結し、フラッシュ上の関数は呼ばない（`objdump` で確認済み）。`pair_max` の計測値には展開時間も含まれる。
- フレームバッファは PSRAM 非キャッシュ窓（`PSRAM_NOCACHE_BASE` 0x15000000）に置く。CPU の読み書きも同じ窓で行う（XIP キャッシュとの不整合回避、および表示用ストリームで XIP キャッシュのフラッシュ側コードを追い出さないため）。
- リング: ラインバッファ32本（`y % 32` 固定対応。480が32で割り切れるためフレーム間で対応不変）、表示ラインの**28ライン先**までコピー（上限は30）。コピー側・表示側の位置は「フレームをまたぐ絶対ライン番号」で比べ、コピーが遅れたら間に合わないラインを飛ばして次のラインから再開する（以前は遅れると「約500ライン先」と誤判定して次フレームまで停止し、1度の遅れで1フレームの大半が underrun になるバグがあった）。コピーch は第5段階 S1 でコアごとに1本へ分かれ、`render_pair()` 内のポーリング待ちになった（DMA_IRQ_1 による連続実行は廃止）。ライン割り込み（優先度0）が毎ライン NVIC ペンディング + `__sev()` で両コアの描画を促し、次ラインの完成チェック（`vga_underrun_count`）を行う。
- 割り込みハンドラと描画関数（`vga_line_isr` / `render_irq_handler` / `core1_main` / `render_pair`）は SRAM 配置で、フラッシュ上の関数を呼ばない（呼ぶと PSRAM ストリームと XIP が競合し遅延する）。`objdump` で `bl` の飛び先がすべて SRAM であることを確認済み。
- **プログラム全体を SRAM で実行する（`copy_to_ram`）**。実測で、フラッシュ上の USB 処理（printf 等）が QMI を PSRAM のコピーと奪い合い、表示用 DMA が遅れて `fifo_stall` が増え（USB 出力のたびに約 10/秒）、グリッチが出たため（2026-09-22、`min_ready=1`、`copy_max` 最大 79µs）。SRAM 使用量は約 95KB。フラッシュは起動時のコピーにのみ使う。
- **PSRAM クロック実測（2026-09-22、clk_sys=302.4MHz）**: 分周3（100.8MHz）は RXDELAY 3〜5 で OK だが 1ライン 31.0µs（ライン周期の98%）で余裕なし。分周2（151.2MHz、定格133MHz超）は RXDELAY 1〜2 が NG、**3〜5 が OK**（中央の4を推奨、1ライン 23.2µs・55MB/s）。**既定は分周2/RXDELAY4**（2026-09-22 決定。分周3は起動直後に underrun=512、定常でもコピー37〜45µs/ラインで余裕なし）。定格内に戻すには `-DSGNANO_PSRAM_CLKDIV=3 -DSGNANO_PSRAM_RXDELAY=4`。定格超過なので温度・個体差に注意。
- **CPU から PSRAM への書き込みは VBLANK 中のみ**（2026-09-22 実測で決定）。
  - 表示期間中に CPU が PSRAM へ書くと、`underrun` だけでなく `fifo_stall`（RGB用SMのFIFO枯渇=画面の横ずれ）が出る。PSRAM コピーが QMI で待たされている間、同じ DMA エンジン上の表示用チャネル（SRAM→PIO）も止まるためと推測。フレーム先頭で 16KB を書いただけで 42 fifo_stall/フレーム、書き込み時間は VBLANK 中の 4.5 倍。
  - VBLANK は 45 ライン（約1.43ms）だが、ライン 497 から次フレーム先頭 29 ライン分のコピー（約0.7ms）が始まる。**安全に書けるのはライン 480〜約496（約0.54ms）で、約30KB/フレーム**（実測 56MB/s）。
  - 実測: vblank 64x64（消去+描画 16KB、292µs）は underrun/fifo_stall とも 0、min_ready=27。128x128（64KB、約1.2ms が必要）は VBLANK に収まらず spill が全回発生し、underrun +16077 / fifo_stall +27757。
  - 大きな更新は複数フレームに分割する。将来はスプライト/タイルを PSRAM に書かず、リング上のライン生成時に重ねる方式（ラインバッファ方式）との併用で書き込み量自体を減らす。
  - 表示コピーが約11.1ms/フレーム（分周2）を使うため、全画面塗りなど同期なしの全力描画は表示と両立しない。
- 診断: `cmake -DSGNANO_DIAG_PSRAM=ON`（分周3/2 x RXDELAY を掃引して自己検証・帯域測定） で PSRAM 自己検証（8MB）と DMA 帯域測定のみ実行。

## 2コア描画パイプライン（第5段階 S1・2026-09-24）
表示ライン 2k と 2k+1 を**ペア k**（k = 0..239）とし、**core0 が偶数ペア、core1 が奇数ペア**を担当する。
各コアがペア単位で全ステージ（PSRAM 取得 → CLUT 展開 → テキスト合成）を行う。`src/video/render.c`。

- **ファイル分割**: `vga.c` は表示経路のみ（PIO・データ/制御ch・`line_table`・ライン割り込み）。生成側は `render.c`。
  両者で共有する内部データ（`vga_ring`、`vga_abs_line`）は `video/vga_internal.h`。
- **スロットの所有は自然に分かれる**: core0 は `y % 4` が 0,1 のライン、core1 は 2,3 のラインだけを書く。
  そのため2コアが同じスロットに触れることはない。
- **取得ch はコアごとに1本**（計 data / ctrl / copy0 / copy1 の4本）。**DMA_IRQ_1 による連続実行は廃止**し、
  `render_pair()` 内で上限つきポーリングで待つ。ペアの手順は `SPEC_lowres_2core.md` §4.3 のとおり
  （y0 の取得中に次の処理を進め、y1 の取得中に y0 を仕上げ、y1 の取得完了後に次の担当ペアの先頭を先行起動する）。
- **完了の公開は絶対ライン番号**（`render_slot_ready[32]`）。従来の `ring_id[]`（表示後に 0xFFFF で無効化）を廃止した。
  古い値は前フレームの絶対番号になるので一致せず、**ライン割り込みが毎ライン行っていた無効化処理が不要**になった。
- **`min_ready` は O(1)**: 各コアが `render_core_next[c]`（**次に生成する**ペアの先頭ラインの絶対番号）を公開し、
  その小さいほうと表示中ラインの差で求める。`underrun` は従来どおり `render_slot_ready[]` の厳密な照合で数える。
  - **「完成済みの番号」で測ってはいけない**（2026-09-24 に実機で `min_ready=0` が出て判明）。
    フレーム末尾では担当ペアが尽きたコアが止まる（core0 はライン477、core1 は479 で尽き、次フレームの生成は
    ライン497から）。完成済みの番号だと core0 が「ライン477で止まっている」＝遅れているように見え、
    表示がライン477に達した時点で余裕0と誤判定される。次の生成位置なら、フレームを跨ぐときに
    ブランキング45ライン分も進むので、この誤判定が起きない。単コア時代の `copy_pabs` と同じ意味になり、値も一致する（健全時27）。
- **ペア番号の進め方**: 絶対ライン番号は `frame * 525 + line`。ペアを+2進めるときは表示ライン+4、
  フレームを跨ぐときはブランキング45ラインぶんを足す（掛け算を使わないので、カウンタの折り返しも表示側と一致する）。
- **割り込み優先度**: ライン割り込み(0) > USB(0x80) > 描画(0xC0)。描画は `user_irq_claim_unused()` で確保した
  予備IRQ（46番）で動かし、ライン割り込みが毎ライン NVIC ペンディング + `__sev()` で両コアを起こす（`render_kick()`）。
  **従来のコピー処理(0x40)より USB の下になった**ので、`pair_max[0]`（core0側）の悪化に注意する。
- **core1 の停止・再開**: `display_stop()` が `render_stop()` を呼び、停止要求 + `__sev()` で core1 を待機状態へ入れ、
  上限つきで確認してから DMA を止める。`display_start()` は表示経路を作り直したあと `render_start()` で再開する。
  **ライン割り込みがまだ動いていないので、再開時は明示的に `__sev()` を出す**（出さないと core1 が WFE から戻らない）。
- **起動時のリング先詰め**: `render_start()` が core0 単独で先頭14ペア（28ライン = `VGA_RING_LEAD`）を同期生成し、
  そのあとペア14（core0）/ペア15（core1）から両コアの自走に入る。先詰めペア数は偶数にすること（担当の偶奇を保つため）。
- **待ちにはすべて上限**: 取得完了待ち 約0.4ms、core1 の停止確認 約2ms。超えたら `render_timeout[c]` を増やして打ち切る。
- **検証**: `scripts/test_pairs.py` が C と同じ式でスケジューラを再現し、30フレーム分について
  (1) 表示時点でラインが完成している (2) 表示中・DMA保持中のスロットへ書かない (3) 担当の偶奇が保たれる、を確認する。
  引数に「core1 が止まるライン数」を渡すと、遅れたときの飛ばしと復帰も確認できる（1〜5ラインの遅れは先行28ラインで吸収され underrun=0）。
- 診断ログ: `[run]` 行が `pair_max=NN/NNus`（コアごと）と `timeout=N/N`。`[rnd]` 行に各コアの進行位置を出す。
- **実測（2026-09-24、テキスト重畳あり、`underrun=0` `fifo_stall=0` `min_ready=25`、モード切替をまたいでも増加なし）**:

  | モード | pair_max（core0/core1） | 1ラインあたり | 単コア時代の copy_max |
  |---|---|---|---|
  | RGB555 | 56 / 57 µs | 約28.5 µs | 33 µs |
  | CLUT8  | 51 / 53 µs | 約26.5 µs | 32 µs |
  | CLUT4  | 34 / 36 µs | 約18 µs   | 20 µs |

  1ペア（＝表示4ライン分）に使える時間は約127µs なので、いずれも半分以下。
  `min_ready` が単コア時代の 27 でなく **25** なのは、**指標の粒度の違い**で実際の余裕が減ったわけではない。
  (1) 生成位置がライン単位からペア単位（2ライン）になった (2) 着手条件がペアの**後ろ**のライン
  （`pair_abs + 1`）で先行上限を見るため実効の先行が1ライン短い。負荷の軽い CLUT4 でも重い RGB555 でも
  25 で一定であることが、負荷による落ち込みではなく構造的な下限であることの裏付け。実際の危険は `underrun` で見る。
  **core0 と core1 の差は1〜2µs しかなく、「描画IRQ(0xC0)が USB(0x80)より下」による core0 の悪化は出ていない**
  （計画 `PLAN_lowres_2core.md` の R-1 は問題なしと判断）。
- **`v` キーのモード切替では、表示経路を止めてからテストパターンを描く**（`vga_stop()` → 描画 → `vga_set_mode()` → `vga_start()`）。
  表示したまま PSRAM へ 150〜600KB 書くと取得 DMA と QMI を奪い合い、1回の切替で underrun 約14,000・fifo_stall 約16,000 が出た
  （2026-09-24 実測。特に切替前が RGB555 のときが最悪で、CLUT4 のときはほぼ出ない＝空き帯域の差）。
  アプリからの PSRAM 書き込みの扱いは S2 の「フレームの進め方」で決める。

## フレームの進め方（第5段階 S2・2026-09-24）
`src/video/video.c`。描画中にアプリが表示資源を書き換えず、アプリが書き換えている間は描画しない、を時間で分ける。
```
[描画中]     両コアがフレーム N を先行生成 -> 最終ペアで「描画終了」（実測ライン453）
[アプリ時間] アプリが表示資源を書き換える -> video_start_frame() が「開始」（実測ライン464）
[描画中]     フレーム N+1 の生成（表示ライン497から。リングの先行28ラインぶん）
```
- API: `video_wait_render_done()` / `video_start_frame()` / `video_render_active()` / `video_frame_count()`
- 着手条件に「そのフレームの開始が出ていること」を追加（`render_step` の先頭で `pair_f < video_start_seq`）。
  各コアはフレームの範囲を越えた時点で `video_core_frame_done[]` を更新する。
  **遅れて飛ばしたペアがあっても越えれば終了扱いにする**（そうしないと描画終了が来ずデッドロックする）。
- 期限は **ライン500**（`video_start_deadline_line[mode]`）。描画終了済みなら強制開始（`late_start`）、
  終わっていなければ `late_render` を数えて `past_deadline` を立て、描画が終わったラインで自動開始する。
- 強制開始（ライン割り込み）とアプリの開始が二重に出ないよう、`video_start_frame()` は確認と発行を
  割り込み禁止で排他にする（数命令だけ）。
- `text_refresh()` は `video_start_frame()` の中（開始を出す直前）に移した。`text_refresh_until()` で
  **描画が始まったら（`video_render_active()`）途中で止める**。上限は `TEXT_REFRESH_MAX_CELLS`（64）。
- 検証: `scripts/test_frame.py`。アプリ時間2〜200ライン・アプリ無応答・コア停止の各条件で、
  underrun=0 / 使用中スロットへの上書き0 / `start_seq` が毎フレーム進む（デッドロックしない）ことを確認。
- **実測（2026-09-24、RGB555・テキスト重畳あり）**: 描画終了 **ライン453**、開始 **ライン453〜485**、
  `underrun=0` `fifo_stall=0` `min_ready=25` `pair_max=56/57µs`。
  **アプリ時間の窓は約1.1ms（ライン453〜488の35ライン）**。
  アプリ側の実測: 表示資源の書き換え（ステータス行1行）+ グリフ展開で **18〜21µs**。
  グリフ展開は **4〜7µs**（行ごとの未展開数で走査を飛ばす前は 192〜290µs だった）。

### 【重要・2026-09-24 実測】アプリ時間なら表示期間中でも PSRAM へ書ける（§3.5 の答え）
描画終了から開始までは **取得 DMA が1本も動いていない**ので、表示期間中（ライン453〜）でも全速で書ける。
| 条件 | 速度 | 1フレームに書ける量 |
|---|---|---|
| 従来（VBLANK のライン480〜496だけ、取得DMAあり） | 56 MB/s | 約30KB |
| **アプリ時間（ライン453〜500、取得DMAなし）** | **61.4 MB/s** | **約60KB** |
実測: 16KB/267µs、64KB/1066µs。いずれも `underrun=0` `fifo_stall=0` `min_ready=25`。
**アプリ時間の窓は約1.47ms（ライン453〜500の47ライン）**。この中に、表示資源の書き換え・
グリフ展開・PSRAM 書き込みをすべて収めること。超えると次項の問題が起きる。

### 【重要・2026-09-24】表示用 DMA は「1ライン分の先行」を失うと自力で戻らない
アプリ時間が期限を越えて強制開始されると画面が壊れ、`v`/`V` で作り直すまで戻らない。
**原因は、表示用 DMA（データch）が持っている「1ライン分の先行」を失うこと。**
- 正常時: 表示ライン L の割り込み時点で、データchは**そのラインのデータをほぼ転送し終えていて**
  TX FIFO は満杯。実測の目印は **`ctrl_idx = line+1`・`data_cnt≒311`・`txlevel=8`**
  （`[vga] snap ok` で確認できる）。SM はライン先頭（t=1740）から途切れずに出力できる。
- 壊れた状態: **`ctrl_idx = line+0`・`data_cnt=5`・`txlevel=5`**。そのラインのデータを
  そのラインの最中に取りに行っている（= 1ライン分の先行を失っている）。
  SM はライン先頭で FIFO が空なので待たされ（`fifo_stall` が毎ライン）、約430clk（36ドット）遅れて
  出力を始める。画面は右にずれ、映像は1ライン分ずれる。
- **一度先行を失うと戻らない**: データchは TX FIFO の空きでペーシングされるので「追い越す」ことができない。
  ライン524の割り込みで制御chの読み出し位置を表の先頭へ戻しても、**どのエントリを読むかが直るだけで
  タイミングの先行は戻らない**。`display_stop()`/`display_start()` は FIFO を先詰めしてから SM を
  起動するので、作り直せば直る。
- 切り分けに使った計測（`vga_print_state()`）: 枯渇した瞬間の `line` / `ctrl_idx` / `data_cnt` /
  `txlevel` / `rgb_pc` を**同じ割り込みの中で**読む（`vga_stall_snap_first` / `_last`、比較用に
  正常時の `vga_snap_ok`）。**別々の printf で読んだ値を比べてはいけない**（USB 出力の間に数ms 経つ。
  実際これで「制御chが先行している＝ライン同期の喪失」と誤読し、見当違いの対策をした）。
- 実測値: 壊れた瞬間 `line=501 ctrl_idx=501(line+0) data_cnt=5 txlevel=5 rgb_pc=5`。
  `rgb_pc=5` は出力ループの中で、SM は自走していない。
  **見るべきは `ctrl_idx` と `line` の差だけでなく `data_cnt` / `txlevel`**（正常 311/8、異常 5/5）。

**引き金は「強制開始の瞬間に両コアが同時に描画へ着手すること」**。
次フレームのペア0に着手できるのは表示ライン498から（先行28ラインの条件 `(pair_abs+1)-d <= 28` を
解くと L>=498）、core1 のペア1は500から。期限を500に置くと、強制開始の瞬間に**両方が同時に**
着手可能になり、PSRAM の取得が4ライン分一気に走って表示用 DMA が先行を失う。
- **対策: 期限を 488 にした**（498より前）。強制開始でも通常どおり 498(core0) -> 500(core1) と
  ずれて始まるので、burst にならない。`D` キーで期限を変えて確認できる。
- **実機で確認（2026-09-24）**: 期限 488 / 496 のどちらでも、アプリの開始を 500µs〜5000µs 遅らせて
  毎フレーム強制開始させても `underrun=0` `fifo_stall=0` `min_ready=25` `recover=0` で**まったく壊れない**。
  期限 500（= 498 以降）のときだけ壊れていたので、「498 より前かどうか」が境目であることが裏付けられた。
  期限を 496 にしても平気なことから、burst を避けること自体が要点で、余裕の大小の問題ではない。
- **backstop: 自動復帰**。ライン割り込みで枯渇が `VGA_STALL_RUN_LIMIT`（32ライン）連続したら
  `vga_recover_request` を立て、アプリのループが `vga_recover()` を呼ぶ。
  **このカウンタが増えたら、アプリ時間が期限を越えている**。

### 【重要・2026-09-24】ライン同期の自己復帰（`vga.pio`）
TX FIFO が**一度でも**1ライン分以上枯渇すると、RGB用SMは次のフラグ4が立ったあとに `wait` へ到達する。
そのまま待つと「既に立っている」ので素通りし、以後このSMは **7682clk/ライン**（表示640ドット分）で
自走する。ライン長 9612clk より短いのでデータが追いつかず、**毎ライン枯渇したまま安定して自力では戻らない**。
対策として `wait 1 irq 4` の直前に **`irq clear 4`** を入れた。
- 正常時、SMがこの命令に到達するのは t≈9422。次のフラグ4は t=11350 なので**1928clk（160ドット、6.4µs）の余裕**があり、
  この範囲の遅れは1ラインも落とさずに吸収する。
- それ以上遅れた場合は取り残しのフラグを捨て、**次のラインの先頭で必ず同期し直す**。代償はそのライン1本が黒くなることだけ。
- 1ライン落とすとデータchが1ライン遅れるが、ライン524の割り込みで制御chの読み出し位置を表の先頭へ戻しているので、
  次のフレーム先頭で自動的に揃う。
- 検証: `scripts/test_vga_sync.py` が2つのSMを1サイクル単位でシミュレートする。枯渇 500/3000/20000clk の各条件で、
  対策なしは「ずれた位相のまま出力」が 1〜5本出るのに対し、対策ありは **0本**（ずれた分は出さずに取り直す）。
- 併せて、**表示経路が死んだときの自動復帰**も入れた: ライン割り込みで枯渇が `VGA_STALL_RUN_LIMIT`（32ライン）
  連続したら `vga_recover_request` を立て、アプリのループが `vga_recover()` を呼ぶ（割り込み内では復帰できない）。
  PIO 側の対策が効けばここへは来ないはずなので、**このカウンタが増えたら別の原因を疑う**。
  枯渇が起きた表示ラインは `vga_stall_lines[]` に先頭8件まで記録され、`[vga] stall lines:` で出る。

### `VGA_MODE_NONE`（第5段階 S3・2026-09-24）
フレームバッファを表示せず、**背景色1色**で埋めるモード。**PSRAM からの取得を一切行わない**。
- 色は `vga_set_backdrop(RGB(r,g,b))`（ネイティブ形式）。`B` キーで巡回できる。既定は濃い青。
- `render_pair()` は取得の手順（1・3・5）を飛ばし、`finish_line()` で `fill_backdrop()`（320ワードを
  背景色で埋める）してからテキストを重ねる。取得ch は使わない。
- `v` キーの巡回に加えた（RGB555 → CLUT8 → CLUT4 → NONE → RGB555）。NONE へ切り替えるときは
  テストパターンを描かない（フレームバッファを使わないため）。
- **このモードでは表示用 DMA が PSRAM に触れないので、アプリは表示期間中でも PSRAM に書いてよい**。
  `p` キーの書き込み試験も NONE のときだけ `video_render_active()` のゲートを外す。
- 将来はローレゾ面の透過画素の位置にこの背景色が出る（S4 以降）。
- **実測（2026-09-24、実機で確認済み）**:
  | モード | `pair_max`（core0/core1） | `min_ready` |
  |---|---|---|
  | RGB555 | 56 / 57 µs | 25 |
  | CLUT8 | 51 / 54 µs | 25 |
  | CLUT4 | 34 / 37 µs | 25 |
  | **NONE** | **24 / 27 µs** | **26** |
  - NONE で **256KB を 4678µs（56.0 MB/s）で書き切れた。表示ライン 451 -> 74**（VBLANK と
    表示期間75ライン分をまたぐ）。`underrun=0` `fifo_stall=0`。**表示期間中でも PSRAM に書ける**ことを実証。
  - 同じ 256KB を RGB555 で試すと、ゲートが効いて **67KB（1121µs、61.2 MB/s、ライン453->488）で中断**する。
    こちらも `underrun=0` `fifo_stall=0`。ゲートが設計どおり働いている。
  - 4モードすべてと、その間の切替で `underrun=0` `fifo_stall=0`。自動復帰は1度も起きなかった。

## ローレゾグラフィック面（第5段階 S4・2026-09-24）
320x240 を縦横2倍で表示する面。`src/video/lowres.c`。仕様は `SPEC_lowres_2core.md` §5。
表示するモードは **CLUT8 / CLUT4 / NONE**（RGB555 では表示しない）。データはすべて SRAM。

- **画素形式 CLUT7**: 1画素1バイト。**bit7 = 透過**、bit0-6 = 色番号（0..127）。色番号0は透過ではない。
- **パターンRAM 128KB**（`lr_pattern`）。**64バイト単位**で番号を振る（0..2047）。タイルは 8x8、行優先、1行8バイト。
- **マップ 64x64 タイル固定**（512x512画素、端で折り返す）を2面（`lr_map[2]`、BG0=手前 / BG1=奥）。
  エントリは bit0-10 タイル番号 / bit11 横反転 / bit12 縦反転 / bit13-18 パレット番号。
- **パレット 64本 x 128色**（`lr_palette`、`RGB()` のネイティブ形式）。FB の CLUT ともテキストの16色とも別管理。
- **合成は手前から奥へ**。ラインバッファ（512エントリ、表示範囲 [64,384)）を 0x80（未確定）で埋め、
  各レイヤについて「確定済み(bit7=0)はそのまま、未確定には src を書く」を4画素ずつ行う。
  `sadd8`（dst+0 >= 0 で GE=1 = 確定済み）+ `sel` 2つを**1つの asm 文**にまとめる（GE フラグが文をまたいで保たれる保証がないため）。
- **BG の1ライン**は、41タイルぶんを `64 - fine` の位置から並べる（`fine = sx & 7`）。`fine != 0` で
  4バイト境界からずれるので、`packed` 構造体経由の単一 `LDR`/`STR` で書く（**LDRD/LDM/STM や memcpy は使わない**。
  `objdump` で確認済み。関数の入口/出口の `stmdb sp!`/`ldmia sp!` はスタックなので別）。
- **横反転は8バイトの逆順** = `__builtin_bswap32()` を2ワードに当てて入れ替える（`rev` 命令1つずつ）。
- **出力**（`lr_out[320]`）は倍幅。透過は `0x80008000`、それ以外は `c | (c<<16)`。
  bit15 はピクセル形式で常に0、RGB出力SMは OUT_COUNT=15 なので、透過の印が残っても画面には出ない。
- **重ね**: CLUT8/CLUT4 は透過でないワードだけ書く。NONE は透過なら背景色、そうでなければ出力を書く。
- 作業領域は**コアごと**（`lr_work[2]`）。ペアの手順2で1回描き、手順4と6（表示ライン 2L / 2L+1）で同じ出力を使う。

### 検証（実機に載せる前に2段構え）
1. `scripts/test_lowres.py` — 参照モデル（§5 の定義どおり、奥から順に塗る素朴な実装）と
   実装モデル（C と同じ手順）を Python で書き、全240ライン x 320画素の画素値とパレット番号が一致することを確認。
2. `scripts/test_lowres_c.py` — **`src/video/lowres.c` そのものをホストでコンパイルして走らせ**、
   1の参照モデルと突き合わせる（`scripts/host_lowres/` に pico ヘッダの差し替えを置いてある）。
   `sadd8`/`sel` は ARM 専用なので、ホストでは同じ意味の移植可能な実装に差し替わる（`SGNANO_HOST_TEST`）。
   タイルの索引・反転・折り返し・非整列の書き込み・出力への変換は実機とまったく同じコードを試験している。
   `sadd8`/`sel` 自体の確認は、実機での SIMD 版 vs 素朴版の自己検証で行う（S5）。
   **実機自己検証で使う素朴版（`src/video/lowres_ref.c`）も、ここで同じ参照モデルと突き合わせている。**
   こうしておけば、実機で不一致が出たときに「素朴版が間違っている」可能性を除ける。
   - 通した条件: スクロール 0〜511（折り返しの境目 504〜511 を全部）、反転の4通り、
     全画素不透明/全画素透過、パターンRAMの最後の単位、乱数の場面。**すべて一致**。

### フォント（`src/video/fonts/`）
以前の表示機構（`dvi_out_hstx_encoder`）で作った **8x8 ドット・1バイト/ピクセル・256文字 x 64バイト**の
フォントをそのまま使う。**1文字が64バイトで、パターンRAMの単位と一致する**。
- `font128_set_normal`（0x00/0xFF の2値）、`font128_set_bold2_alt`（0x00..0x80 のみ使用。
  **そのまま CLUT7 として読める**）、`font128_set_bold_italic`（0..255 の多値）。
  【訂正・2026-10-04】bold2_alt の**背景は 0x00**（不透明の色番号0）で、0x80 は文字 0 にしか無い。そのまま使うと背景が塗られて
  後ろの面が透けなかった（ユーザー指摘）。読み込むときに **0 だけを透過（0x80）に置き換える**（`lrdemo.c` の `FONT_STYLE_AS_IS`）。
  これで背景が透けるので、ラインが早く「全部確定」にならず、2面とも最後まで合成する。実測でモード5 の pair_max が
  54/57 -> **75/77us**（BG の合成 12 -> 24us）。予算 127us の約6割で、`underrun=0 fifo_stall=0`。
- **`__in_flash("font128")` でフラッシュに置く**。`copy_to_ram` ビルドでも `.rodata` のうち
  `.flashdata*` はフラッシュに残るので、SRAM を消費しない（48KB）。
  起動時に1回だけ読んでパターンRAMへ展開するので、表示中にフラッシュを触ることはない。
### 実機自己検証（`c` キー、SPEC §10.2）
`lr_selfcheck()` が、いまの場面を**最適化された実装**と**素朴な実装**（`lowres_ref.c`）の両方で
全240ライン描き、320画素ぶんの画素値とパレット番号を突き合わせる。
- 素朴版は1ラインに数百µs かかるので、**`vga_stop()` で表示を止めてから**行い、終わったら `vga_start()`。
- 作業領域は `lr_work[2]`（コア用の [0]/[1] とは別）。
- これが唯一、**`sadd8`/`sel` そのもの**を実機で検証する手段（ホスト試験では移植可能な実装に差し替わるため）。
- **実機で確認済み（2026-09-24）**: `0 mismatched pixels of 76800`、所要 **27ms**。
  デモマップ（反転混在）とフォント一覧の両方で一致。

### デモ（`src/video/lrdemo.c`）
- BG1（奥）= スクロールする文字タイル。**8タイルごとに横反転・縦反転を意図的に混ぜている**。
  【変更・2026-10-04】反転は**単語ごと**（そのまま -> 横反転 -> そのまま -> 縦反転を順に。横反転の単語は文字の並びも逆にして、
  単語全体が鏡に映ったように見せる）。スクロールは倍の速さ（横 1/1・縦 1/4。以前は 1/2・1/8）。
- BG0（手前）= 8タイルごとの格子（`+`/`-`/`|`、パレット4=赤）。ほとんどが空白タイル（全画素透過）なので
  BG1 が透けて見える。**右半分を横反転、下半分を縦反転**にしてあるので、反転が効いていることが目で分かる。
  BG0 は BG1 と違う速さでスクロールする（多重スクロール）。
- 字形をそのまま見たいときは **`F` でフォント一覧**にする（反転なし・スクロールなし、BG0 も消える）。
- デモ（`src/video/lrdemo.c`）のキー: `l`（面のオン/オフ）、`b`（BG0/BG1 の巡回）、`f`（フォント巡回）、
  **`F`（フォント一覧 16x16 の表 / スクロールするデモマップ の切り替え）**、`S`（スクロール停止）。
  書き換えは `lrdemo_tick()` がアプリ時間に行う。
- **デモマップは横反転・縦反転を意図的に混ぜている**（反転の実装を目で確認するため。2026-10-04 から単語ごと）。
  字形をそのまま見たいときは **`F` でフォント一覧**にする（反転なし・スクロールなし）。
- **フォントの読み込みは1フレーム64文字ずつに分ける**。16KB分のフラッシュ読み出しを
  アプリ時間（約1.1ms）で一度にやると期限を越え、実機で `fifo_stall` が数個出た（下記）。

### 実測（2026-09-24、実機で確認済み）
1ペアの予算は約127µs（表示4ライン分）。いずれも `underrun=0` `fifo_stall=0` `recover=0` `min_ready=24`。

| モード | ローレゾなし | BG1のみ | **BG0+BG1** |
|---|---|---|---|
| CLUT8 | 51/54 µs | 83/85 µs | **92〜94 µs（予算の73%）** |
| CLUT4 | 34/37 µs | 72/75 µs | **81〜83 µs** |
| NONE  | 24/27 µs | 63/66 µs | **73〜75 µs** |

`lr_max`（ローレゾ1ラインの描画＋変換）は BG1のみで 23〜30µs、BG0+BG1 で **35〜39µs**。
- **仕様の見積もり（付録A）より重い**。見積もりは CLUT8 で計 64µs・ローレゾ描画+変換 15µs だったが、
  実測は 93µs・36µs。**オブジェクト（S6）に使えるのは CLUT8 で約34µs、NONE で約52µs**。
  §13 の「タイル単位の全透過／全不透明の印による最適化」は、この数字を見ると必要になる可能性が高い。
- BG を1面足すと1ペアあたり約10µs 増える。
- **`fifo_stall` が合計9回だけ出た**。出た表示ラインは **501/502/505/506** で、いずれも
  `f`（フォント切替）を押した瞬間。アプリ時間に16KB分のフラッシュ読み出しを一度にやって
  期限を越えたため。**1フレーム64文字ずつの分割読み込みにして、再測定で `fifo_stall=0` を確認**（タグ `stage5-s4-lowres`）。
  なお分割前も**自力で復帰していた**（`fifo_stall` が9で止まり、`underrun=0`・`recover=0`）。
  PIO の `irq clear 4` が1ラインを落として同期を取り直すと、そのぶんデータchが先行を取り戻せる。
- フォント一覧（`F`）では空白タイル（全画素透過）が多いので、`lr_to_out` の「4画素まとめて透過」が
  効いて **pair_max が 70/73µs** まで下がる（デモマップは 82/86µs）。



### SRAM の使用量（S4 時点）
`.text` 40KB + `.data` 13KB + `.bss` 287KB = **約340KB / 512KB**。
ローレゾの内訳はパターン128KB + マップ32KB + パレット16KB + 作業領域 約5KB。

## オブジェクト（第5段階 S6・2026-09-24）
OAM 128個。仕様は `SPEC_lowres_2core.md` §5.6 / §5.7。
- 1件12バイト（`lr_obj_t`）。幅 8/16/32/64、高さ 1..256、優先度 0/1/2（3は予約で描画しない）、
  横反転・縦反転・表示ビット、パレット番号。
- **1ラインにつき OAM を1回だけ走査**し、優先度ごとの3リスト（OAM番号の昇順）に振り分ける。
- 合成の順は手前から **OBJ(2) → BG0 → OBJ(1) → BG1 → OBJ(0)**。
- パターンRAM からはみ出す（`pattern*64 + H*W > 128KB`）ものは描画せず `lr_obj_range_err` を数える。
- **確定済みの飛ばし3段階**: (1) 4画素単位（dst が全部確定済みなら src を読まない）
  (2) 8画素単位（`uint64_t cov` で64ブロック。オブジェクトは範囲全体が確定済みなら丸ごと飛ばす）
  (3) ライン単位（表示範囲のブロック8..47 が全部確定したら残りのレイヤを処理しない）。
- **表示範囲がすべて不透明になったら、FB の CLUT展開・背景色塗りを省く**（`lr_line_opaque()`）。
  `lr_overlay` が全ワードを上書きするので結果は変わらない。重ねも判定なしの単純コピーになる。

### 【重要・2026-09-24】実測: オブジェクトは予算に対して重い
1ペアの予算は約127µs。実機（CLUT8、BG2面 + テキスト）:

| 場面 | 1ラインのオブジェクト数 | `lr_max` | `pair_max` | 結果 |
|---|---|---|---|---|
| オブジェクトなし | 0 | 35〜39µs | 92〜94µs | 正常 |
| `o` デモ（大きさ混在128個） | **32** | **88〜96µs** | **115〜122µs** | 予算ぎりぎり。`fifo_stall` が時々出る |
| `O` 負荷試験（幅64x高さ64 を128個） | **128** | **162µs** | **205〜208µs** | 大幅超過。`underrun` も出る |

- **`underrun=0` でも `fifo_stall` が出る**。描画が遅れて表示用DMAが SRAM を奪われるため。
  画面にノイズとして見える。自動復帰（`recover`）が何度も走る。
- **正しさは問題ない**: 実機自己検証は `o` の状態で `0 mismatched pixels`（49ms）。

### 【重要】実測された能力の上限（2026-09-24、内訳つき）
ローレゾ1ラインの内訳（CLUT8、最大値µs）:

| 場面 | 1ラインのOBJ数 | `init` | `bg` | `obj` | `out` | `lr_max` | `pair_max` |
|---|---|---|---|---|---|---|---|
| OBJなし | 0 | 2 | 12 | 1 | 18〜21 | 29〜33 | 55〜58 |
| 散らばった OBJ | 32 | 14〜18 | 12〜25 | 16〜47 | 18〜19 | 56〜96 | 98〜152 |
| 全部重なる OBJ | 128 | 21 | 12 | **41** | 19 | 92 | 125〜134 |

- **重なったオブジェクトのほうが安い**。128個が全部重なると `cov` の飛ばしが効いて 41µs で済むのに、
  32個が散らばると 42µs かかる。**コストはオブジェクト数ではなく「実際に塗る画素数」に比例する。**
  飛ばしの3段階は設計どおり効いている。
- **1画素あたり約12サイクル**（BG 328x2 + OBJ 約960 = 1ライン約1600画素を `bg`+`obj` の 65µs で塗る）。
  4画素の合成が約38サイクル。非整列の LDR/STR が2アクセスになること、画素配列とパレット配列の
  2本を読み書きすること、2コアが同時に SRAM を叩くことが効いている。
  **この構造ではこれが下限に近く、個別の最適化で2倍は取れない。**
- `out`（19µs）と `init`（15µs）は**オブジェクトの数に関係なく常にかかる**。
- 仕様の付録Aの見積もり（オブジェクトに約60µs で「幅64換算100個以上」）には遠く届かない。

**実力は「320画素幅で約5重の重ね塗り」**。FB の CLUT展開があるぶん、モードで大きく変わる。

### 【重要】モード別の実用上限（2026-09-24 実測、`fifo_stall` が増えないこと）
| モード | 1ラインのOBJ数 | `lr_max` | `pair_max` | `fifo_stall` |
|---|---|---|---|---|
| **NONE** | 0 | 35/40 | 70/73 µs | 0 |
| **NONE** | 12 | 64/65 | 93/93 µs | 0 |
| **NONE** | 24 | 80/81 | 109/108 µs | 0 |
| **NONE** | **32** | **87/88** | **116/115 µs** | **0** |
| CLUT4 | 32 | 90〜95 | 126〜129 µs | 増える |
| CLUT8 | 7〜10 | 54〜61 | 106〜144 µs | 数百/秒 |
| CLUT8 | 24〜32 | 81〜89 | 150〜151 µs | 大量 |

- **`VGA_MODE_NONE` なら 128個（1ラインに32個）まで完全にクリーン**。ローレゾ面を使うなら
  これが本命の構成。640x480 の FB を下に敷く必要がないことが多いので、実用上の制約は小さい。
- **CLUT4 は 1ラインに32個でぎりぎり**（予算127µs に対し 126〜129µs）。
- **CLUT8 は1ラインに8個程度まで**。FB の CLUT展開（11µs x 2ライン）が効く。
- RGB555 ではローレゾ面は表示しない（仕様どおり）。
- デモは `o` キーで 24→48→96→128→off と巡回する。既定24個はどのモードでも安全。

### 今後の選択肢（2026-09-24 時点で保留）
**`VGA_MODE_NONE` なら現状でも 128個が動く**ので、当面の実用には足りている。
CLUT8 と併用したい場合のための改善の道は3つ:
- **(B) タイル単位の全透過/全不透明の印**（仕様 §13）。BG に効く（透過の多いフォントタイル）。見込み全体の1割程度。
- **(C) パレット番号を画素ごとに持たない**（面ごと・オブジェクトごとに固定し、変換時に解決）。
  合成の読み書きが半分になり **1画素6サイクル程度**まで下がる可能性がある。**仕様変更が要る**
  （「64本×128色を画素単位で選べる」を「レイヤ単位で選ぶ」に緩める）。効果は大きい。
- 表示解像度やレイヤ構成の見直し。


## テキストプレーン（第4段階・2026-09-23）
半角 **80x30 文字（8x16セル）= 640x480 ドット**で、グラフィック画面にちょうど重なる。`src/video/text.c`。
- **テキストVRAM**: 1セル2バイト（UCS-16）。**全角は隣接2セル・4バイトを UCS-32** として使う。左セルが下位16bit、右セルが上位16bit（並びとしてリトルエンディアンの u32 になる）。BMP の全角なら右セルは 0。
- **アトリビュートVRAM**: 1セル2バイト。bit0-3=文字色、bit4-7=背景色、bit8=全角の右側、bit9=文字色透過、bit10=背景色透過。
- **16色パレットは PC-98 準拠**（`pc98_rgb[]`）。下位8色が各成分7（暗）、上位8色が15（明）で、並びは黒/青/赤/紫/緑/水/黄/白。グラフィック側の CLUT パレットとは**別管理**。
- **グリフ面（SRAM 38.4KB）を経由する**。フォント ROM はフラッシュ上にあり、読むと QMI を PSRAM と奪い合うため、ライン合成では ROM を一切触らない。変更のあったセルだけ `text_refresh()` が ROM から SRAM のグリフ面（1セル16バイト）へ展開し、**VBLANK 中に少しずつ**行う（main ループ）。
- **実測（2026-09-23、テキスト重畳あり）**: RGB555 で `copy_max=33µs`・`fifo_stall=0`・`min_ready=27`、CLUT8 で 32µs、CLUT4 で 20µs。`copy_max` はライン周期(31.7µs)を超えるが、これは文字のある行だけの最悪値で、空行はほぼゼロのため平均では収まっている（`min_ready=27` が裏付け）。文字数を増やす場合はこの値に注意。
- 合成は `text_overlay_line()` が `vga_copy_isr` の中で行う（CLUT展開の後）。SRAM のみ参照・フラッシュ呼び出しなしを `objdump` で確認済み。空セル（文字なし＋背景透過）は8画素まとめて飛ばすので、文字が少ない画面では安い。

## フォント ROM（EmbUniFont）
- `src/video/font.c`。仕様は `font_binary_spec.pdf`（フォーマット版数1.0）。
- **配置: フラッシュ末尾4MB = XIP 0x10C00000**。`EmbUniFontUni.uf2` を BOOTSEL で書き込むと、この位置に入る（UF2 の対象アドレスで確認済み）。使用フォントは EmbUniFontUni（58,424文字）。
- 構造: ヘッダ(0x0)→ブロックテーブル(0x1000, 8B×1024)→グリフ領域(0x8000)。`B=cp>>8` でテーブルを引き、`rec = 0x8000 + glyph_offset + (cp&0xFF)*36`。レコードは exists/half/予約2B/データ32B。1行2バイト（1バイト目が左8ドット、MSBが左端）、`line_value` の下位4bitが開始行・上位4bitが行数-1。
- **検証済み**: `scripts/test_text.py` で、ROM からの読み出し・全角の左右分割・セル配置を実データで確認（A/あ/漢/半角カナ/SIP面の文字）。


### 【重要】`display_start()` の TX FIFO 待ちに上限がなかった（2026-09-24 修正）
`display_start()` は「表示ライン0 のデータを TX FIFO へ満たしてから SM を起動する」ため
`while (!pio_sm_is_tx_fifo_full(...))` で待っていたが、**上限が無かった**。
ここはライン割り込みを止めた状態で回るので、満ちないと**表示が止まったまま戻らない**
（`vga_frame_count` も `vga_line_index` も凍る。PIO の SM は有効のまま）。
上限（10万回）を付け、超えたら `vga_start_timeout` を増やして先へ進むようにした。
プロジェクトの決まり「待ちには必ず上限を設ける」の見落としだった。


## ピクセル形式（重要）
ピン順ネイティブ形式（16bit）: bit0=R0(MSB)…bit4=R4(LSB)、bit5=G0…bit9=G4、bit10=B0…bit14=B4、bit15=0。
一般的な RGB555（bit14-10=R, bit9-5=G, bit4-0=B）を15ビット反転したものと一致する。
【変更・2026-10-03】基板の更新で RGB DAC の各色の LSB/MSB が入れ替わり（GP1=R4(LSB) .. GP5=R0(MSB)）、ネイティブ形式は
**bit0-4=R・bit5-9=G・bit10-14=B（各色 bit0 側が LSB）**になった。`rgb555_to_native()` は R と B の入れ替えだけ、`RGB()` は定数式。
描画コードは必ず `RGB(r,g,b)`（各0–31）または `rgb555_to_native()` 経由で色を作る（`video/vga.h`）。PIO側ではビット反転しない。

## VGAタイミング・信号生成
- 640x480@60Hz。水平 640/16/96/**49**（計**801**）、垂直 480/10/2/33（計525）。HSYNC・VSYNC とも負論理。バックポーチを標準の48から49に増やし HTOTAL=801 としている（ドットクロック 25.2MHz のとき 水平 31.461kHz / 垂直 59.92Hz と、標準の 25.175MHz・800ドット・59.94Hz に近づくため）。
- 各パラメータは `video/vga.h` の `#define`。ただし `vga.pio` のループ回数は固定値なので、水平タイミングを変える場合は `vga.pio` も直す（`_Static_assert` で不整合を検出）。
- **PIO0 SM0（HSYNC）**: t=0（HSYNC↓）で CPU向けIRQフラグ0を発報、t=1152 で HSYNC↑、t=1738 でRGB用SMへIRQフラグ4を発報。1ライン 9612 sysclk。
- **PIO0 SM1（RGB）**: IRQフラグ4を待ち、`out pins,16`（OUT_COUNT=15）で 640ドット出力。1ドット12clk、2ドット/24clkのループ。表示開始 t=1740（同期96+BP49ドット）。終了後 RGB=0。ブランキング中は常に黒。
- **DMA**: データch（320ワード/ライン → SM1 TXF）+ 制御ch（アドレス表 `line_table[525]` を1件ずつ読みデータchの `READ_ADDR_TRIG` へ書く）。ライン単位のCPU介入なし。表示ラインはリングのスロット、ブランキングラインは黒ラインを指す。
- **ライン割り込み**（PIO0_IRQ_0、優先度0=最高、SRAM 配置）: ライン数カウント（基準はこのハンドラ）、line=490 で VSYNC Low、492 で High、524 で制御chの読み出し位置を表の先頭へ戻す。処理はこの3つのみ。
- ライン番号は表示開始ライン=0（0–479 表示、480–489 FP、490–491 同期、492–524 BP）。
- 割り込み禁止区間は短く保つこと（1ライン=31.7µs。ライン524の割り込みが行われる前にデータchが完了すると表が壊れる）。

## タイミング記述子（T3・2026-09-27）
`src/video/timing.h` / `timing.c`。従来は 640x480@60Hz の値が `#define` とライン番号の
直書きで散らばっていた（アプリ時間の窓 453〜500、期限 488、VTOTAL 525、VSYNC 490/492 …）。
**1つの表から引ける形**にした。

### 表し方
水平は「ドット」単位、垂直は「走査線」単位で、**引き伸ばしと余白を分けて持つ**:
```
h_visible = src_w * h_repeat     v_visible = src_h * v_repeat
h_active  = 左余白 + h_visible + 右余白    v_active = 上余白 + v_visible + 下余白
h_total   = h_active + FP + 同期 + BP      v_total  = v_active + FP + 同期 + BP
```
こうすると「320x200 を縦2倍で出して上下に40ラインの余白」も「256 を512幅で出して
左右に64画素の余白」も、同じ形で書ける。

### 表の中身（12行、すべて起動時とホスト試験で検査済み）
| 周波数 | 行 | ドットクロック | H | V | 実測の周波数 |
|---|---|---|---|---|---|
| 31kHz | 640x480 / 320x240x2 / 320x200x2 / 256x224x2 / 256x192x2 | clk/12 | 640/801 | 480/525 | 31.461 kHz / 59.93 Hz |
| 24kHz | 640x400 | clk/14 | 640/870 | 400/440 | **24.828 kHz / 56.43 Hz** |
| 24kHz | 320x200x2 | clk/28 | 320/435 | 400/440 | 24.828 kHz / 56.43 Hz |
| 24kHz | 256x192x2 | clk/36 | 256/338 | 400/440 | 24.852 kHz / 56.48 Hz |
| 15kHz | 320x240 / 320x200 | clk/48 | 320/400 | 240/262 | **15.750 kHz / 60.11 Hz** |
| 15kHz | 256x224 / 256x192 | clk/60 | 256/320 | 240/262 | 15.750 kHz / 60.11 Hz |
**24kHz は PC-98 の実測値（24.83kHz / 56.42Hz）にぴたりと合う。**

### 【重要な発見】リングの幾何は周波数ごとに違う
記述子に `ring_lines` / `ring_lead` を持たせたら、**15kHz が成り立たない**ことが検査で出た。
- リング本数は `v_active` を割り切る必要がある（スロットの対応をフレーム間で保つため）。
  **31kHz の 480 は 32 で割り切れるが、24kHz の 400 と 15kHz の 240 は割り切れない。**
- さらに **15kHz のブランキングは 22 ラインしかなく、先行 28 ラインでは
  「次フレームの先頭ペアに着手できるライン」が表示期間に食い込む**。
  → 期限を置く場所が無くなる（強制開始の瞬間に両コアが同時に着手し、
  表示用 DMA が「1ライン分の先行」を失う状態に必ず入る）。
- **決めた値**: 31kHz = 32/28、24kHz = **20/18**、15kHz = **16/14**。
  着手ラインは `v_total - ring_lead + 1`（31kHz で 498 = 525-28+1。実測と一致）。
- **T6 で `render.c` を記述子化するときに、この値を使うこと。**
  いまは `vga_timing_check_render()` が「記述子とコンパイル時定数が一致するか」を
  起動時に確かめるだけにしてある（食い違えば `[tm] ERROR` が出る）。

### 検査（実機とホストで同じ関数を呼ぶ）
`vga_timing_validate()` が見るもの: 導出値の辻褄、`v_total` がライン表に収まるか、
`h_active` が偶数（RGB用SMは2ドット1組）、**リングの幾何**、
**期限がブランキング期間かつ着手ラインより前**。
- 起動時に全行を検査して `[tm]` 行で出す（キーが A〜Z・0〜9・記号とも**全部埋まっている**ため）。
- `python3 scripts/test_timing.py` が `timing.c` をホストでコンパイルして同じ検査を走らせる。
  **論理を書き写していない**ので、片方だけ直して食い違うことがない。

### 記述子から作っているもの（T3 の範囲）

## フレーム tick の抽象化と周波数の状態（T4・2026-09-27）

### 監査: 映像の割り込みを時計代わりにしている箇所は無かった

|---|---|---|

| CD のストリーミング補充（`usbufi_task`） | `audio_stream_space()`（DMA の読み出し位置） | フレームとは無関係。**問題なし** |

### API（`src/video/video.h`）
```c
uint32_t video_frame_period_us(void);            // 1フレームの長さ（µs）
uint32_t video_frame_hz_q16(void);               // フレームレート（16.16）
uint32_t video_per_second_q16(uint32_t per_sec); // 「毎秒 per_sec」の1フレームぶん（16.16）
```
アプリは「1フレームに1つ」ではなく**「毎秒いくつ」**で書く。
フレームレートは 31kHz 59.93 / 24kHz 56.43 / 15kHz 60.11 Hz と違うため。
- **実測（2026-09-27）**: `frame 16687 us (59.926 Hz)`。診断の実測 59.925 Hz と一致。
  `60/sec advances 1.001 per frame` なので、従来の「1フレームに1」と見た目が変わらない。
- **値はタイミングが変わるときしか変化しないので `video_reset()` で1回だけ計算する。**
  `video_per_second_q16()` は掛け算1回で済む（除算を毎フレーム走らせない）。

### 周波数の状態（`src/video/timing.h`）
```c
vga_freq_t  vga_timing_freq(void);                 // いまの周波数（起動時は 31kHz）
const char *vga_timing_freq_name(vga_freq_t f);
const char *vga_timing_select(vga_freq_t, uint16_t w, uint16_t h);  // 成功なら NULL
```
`vga_timing_select()` は**検査を全部通ったときだけ**差し替える。
モード0（表示なし）は PIO にも同期にも触らないので、この値を読むだけで書き換えない。

### 【重要・2026-09-27 実測】`pair_max` は SRAM 上の配置に敏感（±3µs）
T4 でデモに数十バイト足しただけで `pair_max` が **55/58µs -> 58/61µs** と悪化した。
切り分けの経過（**条件を1つずつ動かした**）:
| 試したこと | 結果 |
|---|---|
| `lrdemo.c` の変更だけ戻す | **55/58 に復帰** → 原因はこのファイル |
| 毎フレームの 64bit 除算をやめてキャッシュ | 変わらず 58/61 → **除算ではない** |
| 変数の宣言位置を移す | 変わらず 58/61 → 宣言の場所でもない |
| スクロールの進み方をきっかり1/フレームに戻す | 変わらず 58/62 → **振る舞いでもない** |
| **シンボルの位置を新旧で比べる** | `render_pair` などが24バイト、**`vga_ring` が4バイト移動**していた |
**原因は SRAM 上の配置。** RP2350 の SRAM は語単位で銀行に振り分けられるので、
2コアが同時に流し込む `vga_ring` が1語ずれると取り合いの具合が変わる。
- **対処: `vga_ring` を 32 バイト整列に固定した**（従来は 4）。1ライン 1280B は 32 の倍数なので、
  すべてのスロットが同じ位相に載る。**他の変更に引きずられなくなる。**
- **整列後の基準値は `pair_max = 56/59µs`。**
- **【読み方】3µs 程度の差は「悪化」ではない。** 無関係な変更でも動く。
  本当に見るべきは `underrun` / `fifo_stall` / `recover` の3つ。

## HSYNC の PIO プログラムを記述子から組み立てる（T6 の第1段・2026-09-27）
`src/video/vga_pio_gen.h` / `.c`。`vga.pio` の HSYNC は 1ライン 9612 sysclk（31kHz）に
合わせたループ回数の直書きだった。24kHz は 12,180、15kHz は 19,200 サイクルなので、
**周波数ごとに別のプログラムが要る**。PIO0 の命令メモリは 32 語しかなく全部を常駐できないので、
**組み立てて載せる**方式にした。

### 作り
1ラインを3つの区間に分けて、それぞれ「ちょうど N サイクル進む命令列」を出す:
| 区間 | side | 長さ |
|---|---|---|
| 同期（先頭でライン割り込みを発報） | 0 | `h_sync * clks_per_dot` |
| 同期解除からフラグ4まで | 1 | `(h_sync+h_bp)*cpd - 2 - 同期` |
| フラグ4（RGB用SMへの合図） | 1 | 1 |
| 残り（表示 + フロントポーチ） | 1 | 残り |
N サイクルの出し方は3段階:
- 大きい塊 `set y,m-1` + [`set x,31` + `jmp x--[15]` + `jmp y--`] = 1 + 514m（最大 16,449）
- 中くらい `set x,k-1` + `jmp x--[15]` = 1 + 16k（17〜513）
- 端数 `nop [d]` = d+1（1〜16）

### 【重要】符号化は SDK の `pio_encode_*` を使わず自分で書いた
**ホストでも同じコードを走らせて検算するため**（スタブを検算しても意味がない）。
現行の `vga.pio` のアセンブル結果で検算済み:
`set x,31 side0` = `0xe03f` / `jmp x--,2 side0 [15]` = `0x0f42` /
`nop side0 [11]` = `0xab42` / `irq nowait 4 side1` = `0xd004`。
命令の上位3bitが種別、続く5bitが「遅延 / side-set」（side-set 1ビットなので bit4 が side、
bits3..0 が遅延で最大15）。`jmp` の飛び先は0起点で書けばよい（`pio_add_program` が
載せる位置を足してくれる）。

### 検証（`scripts/test_pio_gen.py`）
`vga_pio_gen.c` をホストでコンパイルし、出てきた命令列を**1サイクル単位で走らせて**
波形を確かめる。見るのは (1) 1ラインの長さ (2) 同期の長さ (3) フラグ4 の位置。
```
640x480@60 (31kHz)   23 語  1ライン 9612（記述子 9612） 同期 1152（1152） irq4 @1738（1738） OK
    現行 vga.pio との突き合わせ: 1ライン 9612 / 同期 1152 / irq4 @1738 -> 一致
640x400@56 (24kHz)   23 語  1ライン 12180  同期 924  irq4 @2182  OK
320x240 (15kHz)      23 語  1ライン 19200  同期 1440 irq4 @3118  OK
```
**12行すべてが 23 語に収まり、31kHz は手書きの `vga.pio` と完全に一致した。**
- 実機でも `[vga] hsync built : 23 words, line 9612 clk, sync 1152 clk, irq4 @1738 clk` と出て、

### RGB 用 SM も記述子から組み立てる（T6 の第2段・2026-09-27）
**横2倍は「1画素を2ドット分の時間だけ保持する」ことで作る。** ラインバッファは元の幅のままでよい。
- 1ラインに出す画素数 = `h_active / h_repeat`、1画素の保持 = `h_repeat * clks_per_dot`。
- 形は2通り。どちらも先頭が「x を作り直す → 取り残したフラグを捨てる → 合図を待つ」、
  最後が `mov pins, null`（1ライン出し終わったら黒）。**7語**に収まる。
  | 形 | 命令 | 条件 |
  |---|---|---|
  | (A) 2画素ループ | `out [a]` `out [b]` `jmp x--` | `2*cpp = a+b+3`、`cpp <= 32` かつ画素数が偶数 |
  | (B) 1画素ループ | `out [d1]` `nop [d2]` `jmp x--` | `cpp = 3+d1+d2` → 3〜65 |
- **31kHz 640x480 では (A) が現行の `vga.pio` と機械語が1語も違わない**
  （`a0 22 / c0 44 / 20 c4 / 6b 10 / 6a 10 / 00 43 / a0 03`）。

#### 【重要】遅延フィールドの桁数は side-set の有無で変わる
HSYNC は side-set 1ビットを使うので遅延は **4ビット（最大15）**、
RGB は side-set を使わないので **5ビット（最大31）**。
共通のマクロで 4ビットに丸めていたため、**cpp=24 のとき1周が 48clk のはずが 16clk になった**。
遅延が黙って切り詰められるだけでエラーにならないので、**サイクル数を数える試験が無ければ気づけない**。

### `render.c` の幾何を記述子から（T6 の第3段・2026-09-27）
`VGA_V_ACTIVE` / `VGA_V_TOTAL` / `VGA_RING_LINES` / `VGA_RING_LEAD` の直接参照をやめ、
**`render_start()` で記述子から写した変数**（`rg_*`）を使うようにした。
写す先は素の `uint16_t` にしてある（描画の熱い経路から構造体をたどらないため）。
ライン割り込み（`vga.c`）も同様に `tm_v_last` / `tm_v_active` / `tm_ring_mask` を見る。

#### 【重要】T3 で決めたリング本数が間違っていた
T3 では 24kHz を **20/18** と決めたが、**スロット索引はマスク（`y & (ring_lines-1)`）なので
`ring_lines` は2のべき乗でなければならない**。20 は使えない。
さらに**先詰めペア数（`ring_lead / 2`）は偶数**でなければならない（担当コアの偶奇を保つため）ので、
`ring_lead` は4の倍数である必要がある。
- `v_active` を割り切る2のべき乗: 31kHz(480) は 8/16/32、**24kHz(400) と 15kHz(240) は 8/16 だけ**。
- **決め直した値**: 31kHz = **32/28**、24kHz = **16/12**、15kHz = **16/12**。
  着手ラインは 24kHz が 429、15kHz が 251 で、期限（414 / 246）はどちらもその前。
- **検査規則に足した**（`vga_timing_validate()`）:
  「`ring_lines` は2のべき乗」「`ring_lead` は4の倍数」。
  **T3 の時点でこの2つを書いていれば、その場で弾けた。**
  記述子を作るときは、**使う側の制約（マスク・偶奇）を先に検査規則にする**こと。

#### 【重要】踏んだ不具合3つは**すべて同じ形**だった
「幅・倍率・語数を**1か所でしか設定しておらず、タイミング切替で更新していない**」。
タイミングを実行時に変える設計にしたら、**切り替えのたびに設定し直すものを洗い出す**こと。

| # | 症状 | 原因 |
|---|---|---|
| 1 | 1ラインごとに余計なラインが挟まる | ローレゾをペア単位（縦2倍前提）で描いていた。15kHz は縦等倍 |
| 2 | 31kHz で `pair_max` が 56/59 → **91/93µs** | ローレゾの縦倍率に**記述子の `v_repeat` を使った**。これは「元の解像度を走査線に何倍で出すか」で、640x480 は等倍なので 1。**ローレゾ面は常に 240 行**なので、正しくは `有効ライン数 ÷ 240`（640x480 なら 2） |
| 3 | **1ラインおきに「動かないライン」** | **表示用 DMA の転送語数が `vga_init()` で1回だけ**（320語のまま）。SM は 160 語しか取らないので余った 160 語が次のラインへ回り、**奇数ラインはスロットの「使っていない右半分」**（320幅では一度も書かれない）を表示していた |
- ライン表のスロット索引も `% VGA_RING_LINES`(32) 固定で、記述子の 16 本と食い違っていた（同時に修正）。
- **3 が決定打。** 1 と 2 を直しても症状が変わらず、「幅は合っているか」を疑って見つけた。
  **`underrun=0 fifo_stall=0` でも画は壊れる**（DMA は正しく流れていて、量が違うだけだった）。

| フレームの幾何（`v_active`/`v_total`/マスク/先行/ペア数/語数/ローレゾ縦倍率） | `render_start()` が `rg_*` へ写す |
| ローレゾの横倍率 | `lr_set_doubling()`（ラインバッファが 640 画素なら広げる、320 ならそのまま） |
| アプリ時間の期限 | `video_reset()` |

### T6 の仕上げ: タイミング表の全12行・モード6・CSYNC（2026-10-02）

#### 画面モードとタイミングの対応（`screen.c`）
| 操作 | タイミング |
|---|---|
| モード6 へ入る | 640幅の行なら**同じ周波数のローレゾ専用の行**へ（31kHz は 320x240 x2、24kHz は 320x200 x2。`D` で選んだ解像度を覚える） |
| モード1〜5 へ入る | ローレゾ専用の行なら**同じ周波数の 640幅の行**へ戻る。**15kHz には無いので断る**（`v` はモード0 と 6 だけを回る） |
| モード0 | いまのタイミングのまま（同期だけ出す） |
| `D` | 表の順に全行を巡回。ローレゾ専用の行ならモード6 に合わせる（モード0 ならそのまま） |
- **【T5 の記述の訂正】31kHz の 5 <-> 6 は表示経路を作り直すようになった**（PIO を載せ直すため）。
  【追記・2026-10-03】ユーザーの目視で、**31kHz の 5 <-> 6 の切り替えのたびにモニタが数秒ブラックアウトする**。作り直しの間 HSYNC が止まるため。直すなら、水平タイミングが同じときは HSYNC を止めずに RGB 側のプログラムだけ差し替える（積み残し）。
  【2026-11-04 対処】31kHz/24kHz では mode 6 も 640 幅のタイミングのままにし、ローレゾを 640 幅へ倍化して出す
  （`screen.c` の `timing_for`）。15kHz だけ従来どおりネイティブ。5 <-> 6 で表示経路を作り直さないので HSYNC は止まらない。
  【実機】`mode456.rb` の前後で `screen.c` の `restarts` を SWD で読み、1 回の実行で +4
  （Ruby の開始 2->1、モード 4、4->5、6->2 の 4 回。5->6 と 6->5 は +0）。`mode56.rb`（5->6->5->6->5）は
  boot の 2 -> 4 で、増えたのはモード 5 と元のモードへ戻るときの 2 回だけ（5<->6 の 4 回は +0）。underrun 0。
  水平タイミングは 640x480 と1クロックも違わないので、モニタから見た信号は同じ。
  4 <-> 5 など作り直す切り替えでは、作り直しの間（約1〜2ms）HSYNC が止まるので、モニタが一瞬乱れることがある。
  **5 <-> 6 はこの経路を通らない**（`display rebuilds` が増えない）。0 <-> 6、0 <-> 1 <-> 5 も従来どおり作り直さない。
- フレームバッファ（RGB555/CLUT8/CLUT4）とテキスト面は **640 幅のスロットでしか出さない**。
  ローレゾ専用の行では `vga_set_timing()` / `vga_set_mode()` が断り、テキスト面は重ねない。
  判定は `vga_timing_is_native_lowres()`（スロットが 640 画素未満）。
- `apply()` は**順番に注意**: ローレゾ専用へ行くときは FB を先に NONE にし、戻るときはタイミングを先に戻す。

#### 余白とローレゾの行（`render.c`）
- **上下の余白**はライン表が黒ラインを指すので、描画側は何も作らない（`lr_row_of()` が -1 を返す）。
  余白の上端・下端は**偶数**（ペアを割らないため）。`vga_timing_validate()` が検査する。
- **左右の余白**（31kHz の 256幅 = 320 画素のスロットの両端 32 画素）は**背景色**で塗る。
  ローレゾ面はその内側にしか書かないので、塗らないと前の中身が残る。
- ローレゾの行 = `(y - 上余白) / 縦倍率`。ネイティブなら縦倍率は表の `v_repeat`、行数は `src_h`。
  640幅なら**400ライン以上で縦2倍、行数は「ライン数 / 2」（上限 240）**。640x480 は 240行、640x400 は 200行。
  **ローレゾの下端より下は描かない**。
- **【2026-10-02 修正】640x400 で画面の上 60% にしかローレゾが出なかった**（ユーザー報告。下 40% は背景色）。
  縦倍率を「240 で割った商」で決めていたので 400/240 = 1（等倍・240行）になっていた。
  縦2倍・200行にして 400 ラインいっぱいに出す（24kHz の 320x200 x2 と同じ見え方）。
  ローレゾを描くのが2ラインに1回になったので `pair_max` も 67/72 → 39/41µs に下がった。
  確認は実機のリング16スロットを `mdw` で読み、背景色だけのラインが0本であること。
- ローレゾ面の横は `lr_set_geometry(表示幅, 倍幅か, 書き始めのワード)`。256幅なら x=0..255 を出す。

#### 【T6 で見つけた不具合】`display_stop()` が RGB 用 SM の y を 319 に固定していた
640幅の「2画素組数 - 1」を直書きしていた。生成した RGB プログラムは 1画素ループのこともあり、
回数はタイミングで変わる。**15kHz の 320幅はたまたま 319 で一致していた**ので気づかなかった。
256幅（y=255）では1ラインに 320 画素を取ろうとして表示が壊れるところだった。`rgb_gen.y_init` を入れる。
**作り直しのたびに設定し直すもの（T6 第4段の一覧）に、これも加わる。**

#### 複合同期（CSYNC）— **ライン割り込みで作る AND 型**
PIO の命令メモリは残り2語なので PIO には足さない。**HSYNC ピンを GPIO の出力上書きで Low に固定する**:
- VSYNC の先頭ライン（割り込みの時点で HSYNC は Low の最中）で Low に固定
- VSYNC の最終ライン+1（同じく Low の最中）で固定を外す。あとは PIO どおり同期解除で High
- **どちらも「Low の最中に Low へ固定 / 外す」なのでエッジが増えない**。エッジは PIO が作ったものだけ。
  割り込みの遅れが同期幅（15kHz で約4.7µs）を超えたときだけ崩れる。
- XOR 型（垂直同期中に反転）は、切り替えの瞬間に割り込みの遅れぶんの短いパルスが出るので採らなかった。
  AND 型は垂直同期中にセレーションが無い。**水平の同期を見失うモニタがあれば XOR 型を検討する。**
- `gpio_set_outover()` はフラッシュ上の関数なので、`io_bank0_hw->io[16].ctrl` を `hw_write_masked()` で直接書く。
- 対象は記述子の `csync` が立っている行（15kHz の4行）だけ。**既定は OFF**（`-DSGNANO_CSYNC=ON` で既定を変える）。
  **Ctrl-D**（0x04）で切り替える。印字できるキーはすべて埋まっているが、USB キーボードの Ctrl+英字は
  0x01〜0x1A を送るので、**制御文字はまだ空いている**。UART からは `scripts/console.sh -k $'\x04'`。
- 実機で有効にして `underrun=0 fifo_stall=0 recover=0`。**波形とモニタでの表示は未確認**。
  【追記・2026-10-03】**モニタでの表示はユーザーが目視で確認した**（15kHz で Ctrl-D）。波形は未確認。

#### 【不具合・2026-10-02 修正】ネイティブ幅でローレゾのドットが飛び、スクロールでちらついた
**ユーザーの観察**: 「横640 のモードではフォントがそのまま描かれるが、横320以下ではドットがスキップする」。
スクロールで字が1画素ずつ動くと、飛ぶドットが入れ替わって**フレームごとに点滅して見えた**。
- **原因**: `lr_overlay()` が透過の判定を**下位の画素の bit15 だけ**で行っていた。倍幅では1ワードの左右が
  同じ画素なのでそれで正しいが、**等倍（320幅・256幅ネイティブ）では1ワードに別々の2画素**が入る。
  「左が透過・右が不透明」のワードは丸ごと背景色にされて右の画素が消え、
  「左が不透明・右が透過」のワードは右の透過の印（`0x8000`）がそのまま出て**黒**になっていた。
- **対処**: 等倍のときは左右を別々に判定する（透過の半分だけ 0xFFFF にしたマスクで合成）。
- **決め手は実機のスロットを直接読んだこと**（`mdw`、実行したまま）。`800031bf` のように
  半分だけ透過の印が残ったワードが見えて、一目で分かった。
- **回り道**: 先に「表示へ送るデータがフレームごとに変わっていないか」を割り込みで計測した
  （フレーム全体とラインごとのハッシュ）。静止画で**12タイミングとも変わったラインは0本**で、
  「データはフレームごとには変わらない」までは分かったが、**毎フレーム同じように間違っている**ものは
  この計測では見えない。**「ちらつき」は時間方向の症状に見えて、原因は空間方向（1フレームの中の誤り）だった。**
- **試験の穴**: `test_lowres_c.py` は画素値とパレット番号までしか見ておらず、
  出力段（`lr_to_out()` → `lr_overlay()`）を通っていなかった。
  → **`scripts/test_lr_overlay.py` を足した**。倍幅/等倍・320/256幅・余白の有無・背景色/FB・不透明の割合を
  変えた800ケースで、スロットの全画素を定義と突き合わせる。修正前のコードでは 22,439 画素が食い違う
  （`got=8000` と出る）ことを確かめてある。

#### 画面の左上にタイミングと画面モードを出す（`lrdemo.c` の `label_update()`）
ユーザーは UART のログを見られないことがあるので、**ローレゾの BG0（格子のレイヤー）**に文字タイルで出す
（テキスト面はモード6 では出ないため。ユーザーの指定）。1行目がタイミング名、2行目が `MODE <画面モード>`
（CSYNC が有効なら ` CSYNC`）。BG0 は横にだけスクロールするので、見えている左端のタイル列から書き、
1タイル流れるごとに書き直す（8画素の範囲で左へ流れて戻る）。位置か内容が変わったときだけ書く。

#### 書き込み失敗の直後に、描画が止まった状態で起動したことがある
OpenOCD の書き込みが途中で失敗した直後の起動で、`pair_max=0/0`・`underrun` が増え続ける
（描画がまったく動かない）状態になった。`--rescue` から書き込み直したら再現しなかった。
**書き込みに失敗したら、測る前に必ず `--rescue` からやり直すこと。**

#### SRAM（2026-10-02）
T6 の追加で `.data`/`.rodata` が増え、**`.bss` の先頭の `stream_buf`（4KB 整列）の詰め物が境目を越えて
4KB 増え、1,300 バイト溢れた**（T6 第1段で記録した現象そのもの）。
→ ローレゾの作業領域を3つから2つにした。番号2（実機自己検証）は [0] を借りる
（自己検証は `vga_stop()` で両コアを止めてから行うので、その間 [0] は誰も使わない）。計測カウンタは別に持つ。
**残り 1,396 B**（変更前 2,808 B）。T7（コールドパスのフラッシュ実行）の優先度が上がった。



### テキスト面・ローレゾ面を開閉できる面にした（2026-10-03、SPEC_vram_alloc.md の P3・P4）
- **テキスト面**（`text_open` / `text_close`）: VRAM・アトリビュート・グリフ面・dirty（約50KB）を1つの構造体で取る。
  使う側はマクロ（`#define vram_ch (tm->ch)` など）で書き方を変えない。閉じているあいだの書き込み・展開は何もしない。
- **ローレゾ面**（`lr_open(cfg)` / `lr_close`）: パターン RAM（32/64/96/128KB）・BG の面数（1/2）・パレットの本数（1..64）を選べる。
  資源は「配列へのポインタ」（`uint32_t (*lr_map)[4096]` など）にしたので、`lr_map[plane][i]` の書き方のまま動く。
- **範囲外の番号**（SPEC §9.1）: 範囲外のタイルは透過、範囲外のオブジェクトは描かない、パレットは本数-1 で頭打ち、
  面数1なら BG1 は描かない。描画での確認はタイル単位・オブジェクト単位（画素単位ではない）。素朴版（自己検証）も同じ規則。
  ホスト試験 `smallcfg.c` で、範囲内の画素を 0..0x3F に限り、パターンの直後に番兵 0x7E を置いて、範囲外を読まないことを確かめた
  （最初は番兵を 0x55 にしていて、範囲内の乱数にも現れるので判定できなかった）。
- **安全の決まり**: 表示中の面は閉じない（断る）。閉じるのはアプリ時間（描画が止まっている間）なので、描画中に領域が消えない。
  画面モードが使う面は自動で開く（中身は空。デモの中身は `l` / Ctrl-L で開き直したときに入れ直す）。
- **デモ（lrdemo）**: 毎フレームの `lrdemo_tick()` はマップに書くので、閉じているあいだは何もしない（しないと空のポインタに書く）。
- 実機: 12タイミングで underrun/fifo_stall/recover 0。pair_max は同等か少し良い（31kHz 320x240 x2 で 34/36 -> 33/34µs）。
  自己検証は既定・小さい設定（32KB・1面・5本）とも 0 mismatched。


### 旧ボード用の切り替え `SGNANO_RGB_MSB_FIRST`（2026-10-03）
新しい基板の映像回路が不良（旧ボードでは絵が出る）なので、当面は旧ボードで映像を出す。旧ボードの DAC は
各色のビットの向きが逆（GP1=R0=MSB）なので、CMake の `-DSGNANO_RGB_MSB_FIRST=ON` で `RGB()` / `rgb555_to_native()` を
旧形式（一般的な RGB555 の15ビット反転）にする。色を作るのはこの1か所だけなので、ほかは何も変わらない。
- `RGB()` は5ビットの反転を定数式で書いた（`VGA_REV5`）。旧形式の15ビット反転と **32768色すべて一致**することをホストで確かめた。
- 起動ログの `[vga] RGB DAC : old board (...)` / `new board (...)` でどちらのビルドか分かる。
- 構成済みのディレクトリ: `build_oldboard/`（ON）。`scripts/flash_swd.sh build_oldboard/sgnano.elf` で書き込む。
- 【追記・2026-10-04】新しい基板で絵が出なかったのは、**L アングルのピンヘッダの向きの取り違え**だった（ユーザー）。
  回路の不良ではなかった。新しい基板（OFF）のビルドに戻し、起動ログが `new board (GP1 = R4 = LSB)` になることを確認。
  オプションは旧ボードを使うときのために残す。
- 【追記・2026-10-04】新しい基板で、表示（色を含む）が良好なことをユーザーが確認。

### ラインバッファを色1本にする試み（2026-10-04、積み残し）— **速くならなかったので戻した**
パレット番号を画素ごとに持たないよう、ローレゾの合成を書き換えた。ラインバッファは画素（CLUT7）+ パレット番号の2本から
**色（16ビット）1本**へ（bit15 = 未確定 / 透過）。描くときに、BG はタイルの、オブジェクトはオブジェクトのパレットで色を引く。
最後の変換はパレットを引かず、倍幅に広げて並べるだけ。自己検証・ホスト試験とも一致。
実測（モード5、`pair_max`）。3通り試した最終形（不透明で未確定の画素だけ色を引く）:

| オブジェクト | 変更前 | 4画素まとめて色を引く | 分岐なし | **最終形** |
|---|---|---|---|---|
| 0 | 75/76 | 83/85 | 80/83 | **74/76** |
| 24 | 87/88 | 105/105 | 99/100 | **97/95** |
| 128 | 119/116 | 137/137 | 140/139 | **130/128** |
- BG だけなら同じ、オブジェクトが多いと約1割遅い。以前は「確定済みは残す」を SIMD（sadd8/sel）で4画素まとめて処理していたが、
  色を引くには1画素ずつの判定が要り、重なりの多いオブジェクトで差が出る。
- 積み残しの表に書いた「1画素6サイクル程度まで下がる可能性」は外れた。メモリは同じ（作業領域 1KB）。
- **ユーザー判断で元に戻した**（2026-10-04）。いまのコードは画素 + パレット番号の2本のまま。

## 【2026-10-05】ファイラー（FB を表示したまま動かす）で直したこと
- **`video_wait_render_done()` の戻り方**: 描画が終わっていても、表示ラインがアプリ時間の窓（`表示ライン数 - ring_lead` から開始の期限まで）に
  入るまで待つようにした。PNG の解読（開始後に数十 ms 続く）のあとアプリ時間が次のフレームのライン 0 を越えると、その開始は次のフレームの
  ものと数えられ、期限の強制開始が起きない。すると「描画は終わった」ままになり、待ちが表示期間の途中（ライン 52 など）で戻って、アプリ時間の
  仕事（FB への書き込み）が表示と取り合った: 7 行の書き込みに 13.7ms、`underrun` 約 15,000・`fifo_stall` 約 17,000・表示経路の作り直し 47 回。
  待ちの上限も 2 -> 3 フレームに（開始がライン 0 より後に出ると次の窓まで約 1.85 フレームかかり、2 フレームではぎりぎりで諦めていた）
- **`video_app_us_left()`**: 開始の期限までの残り（µs）。アプリ時間に重い仕事をする所はこれを見て次のフレームへ回す
- **FB を隠す**（F2）: `render.c` に `fb_hidden`。ペアの先頭で1回読み、立っていれば PSRAM から取らずに背景色で塗る（表示経路は作り直さない）
- **テキスト面の展開**: 1フレームの上限 64 セル -> 全セル、アプリ時間の残りが 120µs を切ったら止める（1セル約 1.3µs。画面全体の書き換えが
  約 0.6 秒 -> 1〜2 フレーム）。あわせて `text_compose_begin/end`（下書きして変わったセルだけを展開の対象に）、`text_put_w`（幅を渡して置く。
  フォント ROM を引かない）、`text_puts_clip`（桁数で切る）を足した
- **fifo_stall の記録**を最初の8件 -> 最新の8件に（キーを押したときのラインを見るため）
- **アプリ時間の外でフラッシュのコードを走らせない**ことの確かめ方: 逆アセンブルで「RAM にある veneer（フラッシュへ飛ぶ中継）」と呼び出し元を

## 2026-10-18 CLUT8・CLUT4 の Ruby の fifo_stall（ユーザー指示で調べた）
- **出た時の様子**（ライン割り込みで fifo_stall を見つけたときに取得の状態を記録、`vga_stall_flags`）: モード 4 で 254 件中 232 件が**手伝いの描画中**。

  ペアを終える -> すぐ tick の割り込み（か眠ってアプリ）が PSRAM を触る -> 取得が 6µs -> 7〜17µs に延び、DMA の読み口が塞がって表示の DMA が止まる」

  終わるまで戻らない -> 4 秒に 4〜16 へ。(3) 残りは取り合い: 取得の処理が「手伝いが描いている」と読んだ直後に手伝いが描き終え「取得は無い」と読んで戻っていた ->
  どちらも自分の印を書いて DMB してから相手を読む -> 4 秒に 1。(4) 最後の 1 件は、ライン割り込みが「止まっている」と読んで取得の割り込みを起こす間に次の取得が始まり、
  起こされた分が走っている取得を終わったことにしていた（まだ届いていないラインを仕上げるおそれもあった）-> INTS0 が立っているときだけ終わりとし、立っているときだけ消す -> **0**
  （モード 3・4 とも 4 秒 x 3 回、mandel640.rb も 0。起動・ファイラー・モード 5・コピーの窓・ZMODEM も underrun 0）
- BASEPRI を 1 ペアの間だけにした最初の版は効かなかった（tick はペアの終わりの直後に入っていた）。推測で直すより、時刻つきの記録で重なりを見るのが早かった

## 2026-10-23 ときどき R の bit3（GP4）が効かなくなる件（積み残し、保留）

## ラスタバッファ（vga_ring）を SRAM0〜3 と SRAM4〜7 に分ける（2026-10-31、ユーザー提案）
- RP2350 の SRAM は 0x20000000〜0x2003FFFF（SRAM0〜3）と 0x20040000〜0x2007FFFF（SRAM4〜7）がそれぞれ 4 バンクの縞。リング 32 本（40KB）はもとは `.bss` の中で SRAM0〜3 にまとまっていた
- **前半 16 本を `.bss` の頭（4KB 整列、SRAM0〜3）、後半 16 本をアリーナの上の端（`vmem_alloc` の固定、SRAM4〜7）に置き、ペアごとに交互に使う**（ライン 0,1 -> 前半、2,3 -> 後半…）。
  スロットの番地は `vga_ring_slot[]`（`VGA_RING(slot)`）。取得の DMA が書くスロットとワーカー・表示の DMA が読むスロットが、隣のペアなら別のまとまりになる。`-DSGNANO_RING_SPLIT=OFF` で元の形
- 測り方: 分けない版・分ける版を交互に書き込み、場面ごとに `busperf.sh -w 100 -n 3 sram sram2 xip` を 3 回ずつ（`sram0-7_contested` の合計、100ms あたり）

  | 場面 | 分けない | 分ける | 差 | pair_max |
  |---|---:|---:|---:|---|
  | ファイラー（RGB555、core0 だけ） | 130 万 | 137 万 | +5%（ばらつきの中） | 45 -> 45µs |
  | mode5.py（テキスト + ローレゾ、FB なし） | 67.3 万 | 67.3 万 | ±0% | 82 -> 83µs |
  | mode3.py（CLUT8 + ローレゾ、両コア） | 293 万 | 260 万 | **-11%** | 287 -> 290µs |
  | mode2.py（RGB555 の FB） | 366 万 | 338 万 | **-8%**（窓ごとのばらつきも 336〜416 万 -> 332〜345 万） | 277 -> 277µs |

- FB の取得があるモードで効く。FB を使わないモードの取り合いは、SRAM で走るコード・データとの取り合いが大半で、リングを分けても減らない。SRAM4〜7 の取り合いは少し増える（半分が移るので）が合計では減る。underrun は前後とも 0
- SRAM の空きは約 2KB 減る（前半を 4KB の境目にそろえる分）。起動ログ `[vga] ring split: lo ... hi ...` で置き場を確かめる（分けられていなければ警告）

### 【追記 2026-10-31】PSRAM へ写す所を「関所が開くまで眠る」に（memcpy の待ち方）
