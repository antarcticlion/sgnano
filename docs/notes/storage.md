### USB メモリ（マスストレージ、2026-09-26）
`src/input/usbmsc.c`、`CFG_TUH_MSC=2`（同時2台）。**認識・容量・セクタ読み出し・
MBR のパーティション表まで実機で動作**。ファイルシステムの解釈はまだ。
```
[msc] 0: mounted addr=2 VID=13FE PID=3600
[msc] 0:  silicon-power  3919872 blocks x 512 B = 1914 MB
[msc] 0: read LBA 0 OK (MBR signature 55 AA found)
[msc]  fa b8 00 10 8e d0 bc 00 b0 b8 00 00 8e d8 8e c0 fb be 00 7c bf 00 06 b9 00 02 f3 a4 ea 21 06 00
[msc]  partition 0: type 0c (FAT32) start LBA 62, 3916974 blocks (1912 MB)
```
先頭32バイトは本物の MBR の冒頭（`cli` → スタック設定 → `rep movsb` で 0x0600 へ退避 → ジャンプ）。
- キー: **`#`** = セクタ0を読む、**`$`** = 状態を出す。画面は25行目。
- 転送用のバッファは**静的に置き、4バイト境界に載せる**（転送中も生きている必要がある）。
- 映像への影響なし（`underrun=0` `fifo_stall=0` `recover=0`）。

#### FAT の読み出し（`%` キー、2026-09-26）
MBR -> パーティション -> ブートセクタ -> BPB -> ルートディレクトリ、と辿って一覧する。
`%` は**押すたびに次のドライブへ回る**。実測（USB メモリ、FAT32）:
```
[fat] 1: partition 0, type 0c
[fat] 1: the boot sector is at LBA 8064
[fat] 1: FAT32  OEM "MSDOS5.0"  label "NO NAME"
[fat]  512 B/sector, 8 sectors/cluster (4096 B), 487952 clusters, 3911808 sectors total
[fat]  root directory: cluster 2 -> LBA 16256 (8 sectors)
[fat]   16029429  SDCC-3~1.BZ2  sdcc-3.9.0-amd64-unknown-linux2.5.tar.bz2
[fat]   <dir>  ?V????~1      新しいフォルダー
```
- **種別はクラスタ数で決まる**（4085未満=FAT12、65525未満=FAT16、以上=FAT32）。容量では決まらない。
  2GB はちょうど FAT16 の天井（65524 x 32KB）なので、どちらの可能性もある。
- **MBR を持たない「スーパーフロッピー」形式**もある（セクタ0がいきなりブートセクタ）。
  末尾の `55 AA` は**どちらにもある**ので署名では区別できない。
  **先頭がジャンプ命令（`EB xx 90` か `E9`）か**で見分ける。
- **【落とし穴】パーティション表は「いま読んだセクタ」から直接取ること。**
  別経路（`#` キー）で埋まる変数に頼ったら「パーティションが無い」と誤判定した。
- 長いファイル名(LFN)は属性 `0x0F` の項目に **13個の UTF-16 符号単位**を
  オフセット 1(5個)/14(6個)/28(2個) に分けて置き、**後ろの項目から順に**並ぶ。
  先頭バイトの下位6bitが順番（1始まり）、`0x40` が最後の項目の印。
  **フォント ROM は Unicode 索引、テキストプレーンは UCS-16/32 なので、LFN はそのまま渡せる。**

#### FAT16 も実機で確認（2026-09-26）
FAT32 とは**ルートディレクトリの配置が根本的に違う**（固定領域 vs クラスタチェーン）ので、
別途の検証に意味がある。480MB の USB メモリで確認:
```
[fat] 1: partition 0, type 06
[fat] 1: the boot sector is at LBA 64
[fat] 1: FAT16  OEM "mkfs.fat"  label "NO NAME"
[fat]  512 B/sector, 16 sectors/cluster (8192 B), 61403 clusters, 982976 sectors total
[fat]  root directory: LBA 560, 512 entries (32 sectors)   <- 固定領域（FAT32 はクラスタ2から）
[fat]   <dir>  CH32V3~1      CH32V303VCT6_BASE
```
- クラスタ数 61403 < 65525 で FAT16 と判定。FAT32 側は 487952。
- ボリュームラベルの位置も FAT16 用（オフセット43。FAT32 は71）で正しい。
- OEM 名が `mkfs.fat`（Linux 製）で、FAT32 側の `MSDOS5.0` と作成元が違う。
  **BPB の解釈が特定のツールに依存していない**ことの裏付けになる。
- **残るは FAT12**。USB-FDD の UFI/CBI ドライバが要る（下記）。

#### 【重要】バスパワーのハブに USB メモリを複数ぶら下げない（2026-09-26 実測）
KORG のハブ（`05E3:0606`、バスパワー）にキーボード + USBメモリ2本を繋ぐと、
**3台目が列挙のいちばん最初の要求から応答しない**:
```
[0:0] Open EP0 with Size = 8
Get 8 byte of Device Descriptor
[0:0] Get Descriptor: 80 06 00 01 00 00 08 00
on EP 00 with 8 bytes: OK        <- SETUP は出たが、データが返らないまま停止
```
最初の2台は毎回きれいに載り、3台目だけが毎回同じところで落ちる。
**セルフパワーの PD ドック（`2109:2817`）に替えたら完全に消えた。**
USB メモリは1本で 200〜500mA 引くので、バスパワーでは賄えない。
- ハブの使い分け: **電流を食う機器・多数接続はセルフパワーのドック**、
  KORG のハブはパッド1台など軽い構成向き。

#### 取り外し可能メディアのクラスドライバ（UFI/CBI と ATAPI/BOT、2026-09-26）
`src/input/usbufi.c`。**TinyUSB の MSC は `06=SCSI` + `50=BOT` しか受け付けない**ので、
それ以外を名乗る機器（フロッピー・光学ドライブ）は弾かれる。
`usbh_app_driver_get_cb()` で**独自のクラスドライバを足した**（SDK は無改変）。

| サブクラス | 機器 | 転送方式 | 実機で確認 |
|---|---|---|---|
| `04` UFI | USB フロッピー | **CBI** | TEAC FD-05PUB、**FAT12 まで読めた** |
| **`02` MMC-5 (ATAPI)** | **CD/DVD ドライブ** | **BOT** | **HL-DT-ST DVDRAM GT50N、ISO9660 を確認** |
| `05` SFF-8070i | 光学・MO 等 | どちらも | 未確認（受け付けるようにはしてある） |

##### 転送方式は2つ。プロトコル番号で切り替える
| 段階 | **CBI**（フロッピー） | **BOT**（光学・USBメモリ） |
|---|---|---|
| コマンド | **制御転送 ADSC**（`bmRequestType=0x21, bRequest=0x00, wLength=12`） | **31バイトの CBW** を bulk OUT（署名 `USBC`） |
| データ | bulk IN/OUT | bulk IN/OUT（同じ） |
| 完了 | **割り込み IN の2バイト**（UFI では **ASC/ASCQ**） | **13バイトの CSW** を bulk IN（署名 `USBS`、`[12]` が状態） |
エンドポイント3本（bulk 2 + 割り込み）なら CBI、2本なら BOT。
**命令語は SCSI とほぼ同じ**なので、コマンド組み立ては共通で使える。

##### ATAPI（光学ドライブ）で実機確認した内容
```
[ufi] MMC-5 (ATAPI) over BOT: VID=1132 PID=4511 itf=0, bulk IN 81 OUT 02
[ufi] device type 05, vendor "HL-DT-ST", product "DVDRAM GT50N    "
[ufi] sense: key 06 asc 28 -- media changed
[ufi] media: 281412 blocks x 2048 B = 562824 KB
[ufi] read LBA 16 OK: 01 43 44 30 30 31 01 00 41 50 50 4c 45 20 43 4f  ".CD001..APPLE CO"
                      └ 型01=基本ボリューム記述子、"CD001"=ISO9660 の識別子
```
- **光学メディアは 2048 バイト/セクタ**（USB メモリの 512 とは違う）。バッファもそれに合わせる。
- **ATAPI は `READ CAPACITY`(25h) でよい**（容量が固定）。フロッピーのように
  `READ FORMAT CAPACITIES` を使う必要はない。機器種別で切り替えている。
- **BOT で失敗したら `REQUEST SENSE` で理由を聞く。** CSW の状態バイトは
  「失敗した」としか言わない。これを入れるまで、メディアのスピンアップ待ちの
  一時的な失敗で読み出しが止まっていた。
- ISO9660 は **LBA 16** が入口（`:` キー）。

##### オーディオ CD の TOC（`\` キー、2026-09-26）
`READ TOC`(43h) でトラック一覧を取る。実機のオーディオ CD で確認:
```
[cd] TOC: tracks 1..6
[cd]  track  1  audio  LBA      0   32380 sectors  7:11
[cd]  track  6  audio  LBA 182952   18080 sectors  4:01
[cd]  lead-out at LBA 201032 (44:40 total)
```
- 応答は `[0..1]`=以降の長さ / `[2]`=最初のトラック / `[3]`=最後のトラック、
  続いて8バイトずつ: `[1]`=ADR/Control（下位4bit の **bit2 が1ならデータ、0なら音声**）/
  `[2]`=トラック番号（**0xAA = リードアウト**）/ `[4..7]`=開始 LBA（ビッグエンディアン）。
- **トラックの長さは「次のトラックの開始 - 自分の開始」**で求める。1件ずつ遅らせて出す。
- 1秒 = **75セクタ**。

##### オーディオ CD の音声セクタを読む（`!` キー、2026-09-26）
**音声トラックは `READ(10)` では読めない**（2048バイトのユーザーデータが無いので
ドライブが拒否する）。**`READ CD`(BEh)** を使う:
```
[1]    bit2-4 = 期待するセクタ種別（001 = CD-DA）-> 0x04
[2..5] 開始 LBA（ビッグエンディアン）
[6..8] 読むセクタ数
[9]    返してほしい内容（bit4 = ユーザーデータ 2352バイト）-> 0x10
```
実機のオーディオ CD で確認（1秒 = 75セクタ刻み）:
```
LBA   0  peak     7   無音（ディザ程度）
LBA  75  peak   194   フェードイン
LBA 150  peak  4969   音楽が始まる
LBA 225  peak  6688
```
音声は **16bit 符号付きリトルエンディアンの L/R 交互**。1セクタ = 2352 バイト =
**588サンプル(ステレオ) = 1/75 秒**。

###### 【重要】セクタ長は媒体で違う。バッファは最大に合わせる
USB メモリ **512** / CD-ROM・DVD **2048** / **オーディオCD の生セクタ 2352**。
2048 で確保したまま 2352 を読んで**他の変数を壊した**（LBA の表示が化けて気づいた）。

##### 【重要】BOT の Case 5: 要求より実データが短いとき
要求した長さより実データが短いと、機器は**データ段のあとエンドポイントを STALL したまま
CSW を待たせる**（BOT 仕様 Case 5: Hi > Di）。**短いパケットで転送が終わるので
ホストは STALL に気づけず、CSW が永久に来ない。**
```
[ufi] CBW sent (31 bytes), cmd 43, data 512
[ufi] data stage ok: 60 of 512 bytes      <- TOC は届いている
[ufi] the status stage did not return     <- CSW だけ来ない
```
→ **`len < 要求長` なら先回りして HALT を解除してから CSW を読む。**
解除は標準要求 `CLEAR_FEATURE(ENDPOINT_HALT)`（`bmRequestType=0x02, bRequest=0x01,
wValue=0, wIndex=エンドポイント`）。halt していなくても無害。

##### 【重要】`hcd_edpt_clear_stall()` は呼んではいけない
RP2040/RP2350 の HCD では**中身が `panic("hcd_clear_stall")` だけの未実装**。
呼ぶとその場で停止する（実機でウォッチドッグ再起動になった）。
機器側の HALT は上の標準要求で解除でき、ホスト側のデータトグルは次の転送で
DATA0 から始まるので、実用上はそれで足りる。

##### ISO9660 の解析（`]` キー、2026-09-26）
`src/input/usbiso.c`。FAT と同じく**セクタを1つ読む手段だけ**を差し替える形
（`usbiso_open()` に読み出し関数を渡し、`usbiso_sector_ready()` で戻す）。
```
[iso] primary volume "SOR_MIDI", 1024 blocks x 2048 B
[iso] root directory: LBA 38, 4096 bytes
[iso]      34070  SC0101.MID
[iso]      68965  SC0101S8.MID
[iso] 37 entries in the root directory
```
**実機の CD-ROM で37件すべてを一覧できた**（2セクタにまたがるディレクトリも正しく読む）。

###### 構造
- **LBA 16 からボリューム記述子が並ぶ**。1つ 2048 バイトで
  `[0]`=型（1=基本 / 2=補助(Joliet) / 255=終端）、`[1..5]`="CD001"。
- 基本記述子の **`[156..189]` がルートディレクトリのレコード**（34バイト）。
  `[40..71]` がボリューム名、`[80..]` が総ブロック数、`[128..]` が論理ブロック長。
- **ディレクトリレコード**: `[0]`=レコード長 / `[2..9]`=位置 LBA / `[10..17]`=大きさ /
  `[25]`=属性（bit1=ディレクトリ）/ `[32]`=名前の長さ / `[33..]`=名前。
  **数値は両エンディアンで二重に記録**されているので、前半（LSB 側）を読む。
- 名前 `0x00` は "."、`0x01` は ".."。ファイル名の末尾には版数 `;1` が付く。
- レコード長 0 に当たったらそのセクタは終わり（次のセクタへ）。

###### Joliet 拡張（未検証）
補助記述子（型2）の `[88..90]` が `25 2F 40|43|45` なら Joliet で、
**名前は UTF-16BE**。基本記述子より優先して使うようにしてある。
**フォント ROM が Unicode 索引・テキストプレーンが UCS-16/32 なので、変換表なしで
そのまま渡せる**（FAT の長いファイル名とまったく同じ利点）。
手持ちの CD に Joliet が無く、**日本語名の CD があれば確認したい**。

##### この複合ドライブは1本のプラグで3台以上現れる
`1132:4511`（光学）のほかに **ハブ・LAN(`0BDA:8153`)・カードリーダー(`2109:8817`)** が
同時に現れる。そのため:
- **ハブ枠（`CFG_TUH_HUB=3`）とアドレス（`CFG_TUH_DEVICE_MAX=8`）を食う。**
  他の機器と一緒だと**アドレスが枯渇**し、`enum_request_set_addr 1612: ASSERT FAILED`
  （`TU_ASSERT(new_addr != 0)` = 空きアドレスが無い）で列挙が止まる。
  列挙に失敗した機器のアドレスが回収されないまま再接続を繰り返すのが直接の原因。
- 切り分けのときは**そのドライブだけを繋ぐ**のが早い。
- `&` キーは**押すたびに次の「引き受け手のいない機器」へ回る**ようにした。
  複合機は1台目だけ見ても足りないため。

##### CBI の転送の作法（BOT との違い）
| 段階 | BOT（USBメモリ） | **CBI（フロッピー）** |
|---|---|---|
| コマンド | bulk OUT に CBW(31B) | **制御転送 ADSC**（`bmRequestType=0x21, bRequest=0x00, wIndex=インタフェース, wLength=12`） |
| データ | bulk IN/OUT | bulk IN/OUT（同じ） |
| 完了 | bulk IN の CSW(13B) | **割り込み IN の2バイト** |
エンドポイント3本（bulk IN/OUT + 割り込み IN）が CBI の見分け方。

##### 実機で動作した範囲（TEAC FD-05PUB、IBM 銘、`0644:0000`）
```
[ufi] device type 00, vendor "TEAC    ", product "FD-05PUB        "
[ufi] sense: key 06 asc 29 -- unit attention      <- 電源投入リセットの通知
[ufi] sense: key 06 asc 28 -- media changed       <- ディスクを認識
[ufi] format: 2880 blocks x 512 B = 1440 KB
[ufi]  also supports 1232 x 1024 B = 1232 KB      <- 日本の 1.2MB(2HD)
[ufi]  also supports 2400 x 512 B = 1200 KB
```
`INQUIRY` / `REQUEST SENSE` / `TEST UNIT READY` / `START STOP UNIT` /
`READ FORMAT CAPACITIES` が通り、センスコードも解読できている。

##### 【重要】踏んだ落とし穴
1. **`set_config` の中から制御転送を出してはいけない。** 列挙の制御転送がまだ走っており
   断られる。`usbh_driver_set_config_complete()` で先へ進ませ、**500ms 後に**出す。
2. **コマンドの STALL は「失敗」ではない。** CBI 仕様では、受けられない状態の機器が
   ADSC を STALL してよい。**`REQUEST SENSE` で理由を聞く**のが正しい手順。
   同じコマンドを出し直しても状態は変わらない。
3. **フロッピーに `READ CAPACITY`(25h) は使えない**ことがある（`asc 31` で失敗）。
   容量が固定でないため、**`READ FORMAT CAPACITIES`(23h)** で書式を聞くのが正しい。
4. **最初の容量記述子の種別コードの意味**（ここを誤読した）:
   `01`=**未フォーマット**（この容量は「フォーマットできる最大値」）/ `10`=フォーマット済み /
   `11`=メディア無し。**`01` は「ドライブが書式を読めていない」**という意味で、
   そのまま読みに行っても `asc 31` になる。
5. 電源投入直後は `asc 3A`（メディア無し）を返すことがある。フロッピーは
   **コマンドを受けて初めてモーターを回してディスクを見に行く**ので、数回粘る必要がある。

##### 【重要】UFI の割り込み2バイトは ASC/ASCQ（状態バイトではない）
CBI 仕様では、**UFI 機器の完了データは `ASC` と `ASCQ`** で、一般の CBI 機器の
「状態バイト（bStatus）」とは意味が違う。**成功は ASC=0 かつ ASCQ=0。**
ここを一般 CBI として読んでいたため、**失敗を成功と誤認していた**
（`MODE SELECT accepted` と出たのに実際は通っていなかった）。

##### 【重要】データの方向を取り違えない
`MODE SELECT` のようにデータを**渡す**コマンドは bulk **OUT**。
IN へ出すと当然いつまでも完了せず、状態機械が固まる（実機で発生）。
`usbh_edpt_xfer()` の戻り値も必ず見ること。開始できないまま放置すると同じく固まる。
データ段・完了段の待ちには**上限**（3秒）を設けてある。

##### 実装したコマンド
`INQUIRY` / `REQUEST SENSE` / `TEST UNIT READY` / `START STOP UNIT` /
`READ FORMAT CAPACITIES`(23h) / `MODE SENSE(10)`(5Ah) / `MODE SELECT(10)`(55h) / `READ(10)`(28h)。
`MODE SENSE` で実機が返した形状は正しい: `medium type 94, 2 heads, 18 sectors/track,
512 B/sector, 80 cylinders`（= 1.44MB）。**ドライブの電子回路は正常**と分かる。

##### 【完成】別のドライブで FAT12 まで読めた（2026-09-26）
最初のドライブは**スピンドルモーターの故障**だった（下記）。**別の TEAC FD-05PUB** に
替えたところ、一度で通った:
```
[ufi] format: 2880 blocks x 512 B = 1440 KB (formatted)   <- 種別が 10（フォーマット済み）
[ufi] read LBA 0 OK: eb 3c 90 4d 53 44 4f 53 35 2e 30 00 02 01 01 00
                     └ EB 3C 90 = ジャンプ命令、"MSDOS5.0"、512B/セクタ、1セクタ/クラスタ
[fat] 0: no MBR -- sector 0 is the boot sector itself     <- スーパーフロッピー形式
[fat] 0: FAT12  OEM "MSDOS5.0"  512 B/sector, 1 sectors/cluster, 2847 clusters
[fat]  root directory: LBA 19, 224 entries (14 sectors)   <- 1.44MB の標準どおり
```
**これで FAT12 / FAT16 / FAT32 の3種類すべてを実機で確認できた。**
| | クラスタ数 | ルートディレクトリ |
|---|---|---|
| FAT12（フロッピー 1.44MB） | 2847 | LBA 19 の固定領域、224項目 |
| FAT16（USBメモリ 480MB） | 61403 | LBA 560 の固定領域、512項目 |
| FAT32（USBメモリ 1914MB） | 487952 | クラスタ2から辿る |

###### 読み出し元を差し替えられるようにした
FAT の解析は BOT（USBメモリ）でも CBI（フロッピー）でも同じなので、
**セクタを1つ読む手段だけ**を差し替える形にした（`usbmsc_fat_open_with()` に
読み出し関数を渡し、読めたら `usbmsc_fat_sector_ready()` を呼ぶ）。
**転送方式の違いが解析側に漏れていない。** キーは `"`（フロッピー）と `%`（USBメモリ）。

##### ドライバの到達点
転送の全経路（制御転送 ADSC / bulk IN / bulk OUT / 割り込み完了）が動作し、
コマンド12種を実装（`INQUIRY` `REQUEST SENSE` `TEST UNIT READY` `START STOP UNIT`
`REZERO` `SEEK(10)` `VERIFY(10)` `READ(10)` `READ FORMAT CAPACITIES`
`MODE SENSE(10)` `MODE SELECT(10)` `PREVENT ALLOW MEDIUM REMOVAL`）。
**回るドライブがあれば即座に動き**、`READ(10)` が通れば既存の FAT 解析へそのまま繋がる。
**FAT12 の検証だけが機材待ちで保留。**
【追記・2026-09-26】別の TEAC FD-05PUB で FAT12 まで読めた（「【完成】別のドライブで FAT12 まで読めた」の節）。
- 切り分けキー: `<` REZERO / `>` SEEK / `?` VERIFY / `@` 強制 READ / `+` モーター回す /
  `_` 止める / `*` 畳みかけて読む / `^` READ を連打（音の確認用）/ `{` `}` メディアのロック /
  `~` MODE SENSE / `|` 書式を指定（1.44MB → 1.2MB(1024B) → 1.2MB(512B) → 720KB を巡回）。
- **USB の FDD は省電力でモーターをすぐ止める。** 待ちを挟むと次のコマンドのときには
  止まっている。`*`（畳みかけ）は完了コールバックから間を置かずに次を出す経路。

#### 機器の素性を読む道具（`&` キー）
`usbkbd_dump_interfaces(daddr)`。設定記述子を取り、インタフェースの
クラス/サブクラス/プロトコルとエンドポイント構成を並べる。引数 0 で
**「列挙は通ったのにどのドライバも引き受けていない機器」**を自動で選ぶ。
Mass Storage なら `UFI (floppy) + CBI with interrupt` のように名前で出る。
**「動かない」機器に当たったら、まずこれで何を名乗っているか見ること。**

#### SRAM が足りなくなった -> 音源のキャプチャ領域を削った
MSC を足したら **984 バイト溢れた**。`docs/DEVELOPMENT.md` の方針どおり、まず
**`cap_buf`（`C` キーの自己診断専用）** を 32KB -> 8KB に縮めた（`SGNANO_AUDIO_CAP_WORDS`、
既定 2048 ワード）。普段の再生には一切使わない領域で、形式の確認には数周期あれば足りる。

### `ufi_finish` をコマンドごとの完了処理に分けた（2026-10-03 のリファクタリング）
1つの switch（複雑度 96、294行）を、コマンドごとの `done_*()` と表 `done_tbl` に分けた。中身は変えていない。
長いもの（センスの解釈、書式の読み取り、CD の読み出し）はさらに分けた（`sense_text` / `sense_no_media` / `format_unreadable` など）。
- **大きさに注意**: `-O3` が小さくなった `ufi_finish` を呼び出し元（`ufi_xfer_cb` / `usbufi_task`）へ展開し、オブジェクトが +1.4KB 増えた。
  冷たい経路なので `noinline` を付けて +0.9KB まで戻した。それでも SRAM の 4KB の崖を越えたので、
  タイミング表とキーボードの文字の表を `__in_flash` でフラッシュに置いて戻した（devenv.md の SRAM の節）。
- 実機で確認（光学ドライブ `1132:4511`、オーディオ CD 6トラック）: マウント直後の INQUIRY -> TEST UNIT READY -> READ CAPACITY、
  TOC の一覧、LBA 16 の読み出し（データが返らず3秒で打ち切り -> read failed）、**ストリーミング再生 30秒（75 sectors/s、underruns 0）**。
  **FDD の経路（書式の読み取り・センス・連打）は機器が無いので未確認。**
- **残り**: `ufi_xfer_cb` 33、`usbufi_task` 33、`ufi_start` 25、`ufi_open` 22、`usbufi_force` 17。SRAM の余裕と FDD の実機確認の都合で保留。
- **気づいた点（元からの振る舞い）**: 転送中に次のコマンドを出すと黙って捨てられる。`\`（TOC）の 0.2秒後に `:` を送ると何も出なかった。

### 【2026-10-03、積み残し】音声トラックへの READ(10) で光学ドライブが固まる → 拒否と立て直し
**以前「転送中に次のコマンドを出すと TinyUSB が panic する」と書いたのは見立て違いだった。**
入口はどれも「処理中なら断る」を確かめており、2つ目のコマンドは出ていない。本当の引き金は
**音楽 CD に `READ(10)` を出すこと**（`:` や `]` は LBA 16 = ISO9660 の入口を読む）。

#### 観測
- HL-DT-ST GT50N は音声トラックへの `READ(10)` に **STALL もデータも返さず、IN を NAK し続ける**。
  数分たっても戻らず、次の CBW も受け取らない。**BOT の Mass Storage Reset（制御転送）にも答えない**。
- そのあと起きることはタイミングで2通り:
  1. 通常のビルド: データ段を出した直後に `Can't continue xfer on inactive ep 81` で panic -> 再起動。
     printf なしの記録（`-DSGNANO_USB_EVTRACE=ON`、下記）で、データ段（0x81、2048バイト）を出した
     直後・次のイベントの前に止まることを確かめた。HCD の割り込み処理の中なので、こちらからは防げない
     （panic の `ep 81` はキーボードやハブの割り込み IN の可能性もある）。
  2. TinyUSB の全経過を出すビルド: panic せず固まる（printf でタイミングが変わる）。
- STALL は1回も来ていない（`hcd_event_handler` を横取りして数えた。HCD は STALL をどのエンドポイントで
  受けても epx の完了として報告する作りなので、それを疑って確かめた）。
- **RP2040/RP2350 の HCD は `hcd_edpt_abort_xfer()` が未実装（何もせず false）だった**。2026-11-04 に `--wrap` でハードウェアの転送停止を足した（`docs/notes/usb.md`）。`tuh_edpt_abort_xfer()` は
  TinyUSB の使用中の印を外すだけで、ハードウェアには転送が残る。

#### 対処（`usbufi.c`）
1. **拒否**: メディアを認識したら（READ CAPACITY が通ったら）黙って TOC を読んで覚える
   （`[cd] TOC read: 6 tracks (6 audio, 0 data)`）。**音声トラックへの `READ(10)` は出さずに失敗として返す**
   （`[ufi] LBA 16 is in an audio track -- not sending READ(10)`）。`-DSGNANO_UFI_AUDIO_GUARD=0` で切れる（立て直しの試験用）。
2. **立て直し**: 段（コマンド・データ・完了）が3秒返らなければ、
   (a) 出している転送を取り下げる（`usbkbd_cancel_xfer()`: バッファ制御の AVAILABLE を落とし、`tuh_edpt_abort_xfer()`）
   (b) BOT の Reset Recovery（Mass Storage Reset -> IN / OUT の HALT 解除）
   (c) それも返らなければ**ホストを作り直す**（`usbkbd_request_restart()`。ポートのリセットからやり直すので戻る）。
   元のコマンドは失敗として返す。立て直しの間は `busy`。CBI（フロッピー）は (a) だけ。
- 以前は BOT のコマンド段（CBW）に時間切れが無かった。前のコマンドで固まったドライブは CBW も受け取らないので、そこでも止まっていた。

#### 実測（2026-10-03）
| 条件 | 結果 |
|---|---|
| 通常のビルドで `:` / `]`（音楽 CD） | 出さずに失敗。以後の TOC・音声セクタ・CD 再生の先読みも正常 |
| 拒否なしの通常ビルド | 2/2 で panic（直す前と同じ。拒否が要る理由） |
| 拒否なし + 全経過のビルド | 5/5 で固まる -> リセットも返らない -> 約13秒でホストの作り直し -> ドライブが戻り TOC も読める |
| `(` | `state idle, resets N, TOC known (6 tracks)` で状態が見える |

#### 切り分けの道具: `-DSGNANO_USB_EVTRACE=ON`
`hcd_event_handler` と `usbh_edpt_xfer_with_callback` を `--wrap` で横取りし、printf なしで64件の環
（`usbfix_evtrace` / `usbfix_evtrace_n`）に記録する。ウォッチドッグを切ったビルドで止め、
SWD の `dump_image` で読み出す。**printf のログを出すと再現しない現象**に使う。

### 【2026-10-03】FDD と光学ドライブの同時接続、データ CD で見つかった不具合（実機で確認済み）
FDD（TEAC FD-05PUB）を足して試験した。FDD 単体は FAT12 の一覧・形状の問い合わせとも正常。そのあと光学ドライブで
**データ CD**（TURBOC40J）を試して、以下が見つかった。ほとんどが「ドライブを固まらせ、抜き挿しするまで戻らない」形で現れた。

| # | 症状 | 原因 | 対処 |
|---|---|---|---|
| 1 | FDD と光学を同時につなぐと FDD が固まる | `ufi_open` が「1台だけ扱う」の確認より前に `ufi_bot` を書き換えていた。後から光学（BOT）が列挙されると FDD（CBI）へ CBW を送った | 確認を先にする。断った機器はログに出す |
| 2 | データ CD の TOC のあと CSW が来ない | 短い応答のあと**先回りで HALT 解除**していた。止まっていなくても機器のトグルが DATA0 に戻り、CSW を受け取れない | GET_STATUS で止まっているときだけ解除（のちに 4 で短い応答自体を無くした） |
| 3 | 抜き挿し直後の最初の読み出しが3秒で時間切れ | ディスクの回転待ち（実測 3194ms / 4404ms、2回目以降は 34ms） | 光学ドライブだけ待ちを20秒 |
| 4 | ISO を読んだあとの TOC で CSW が来ない | 要求 512 に対して応答 20（BOT の Case 5）。機器は bulk IN を STALL してよく、HCD はそれを届けない | **TOC を2回に分けて読む**（先頭4バイトで長さを知り、ちょうどの長さで読む）。Case 5 が起きない |
| 5 | データトラックへの CD-DA の READ CD でドライブが固まる | 音楽 CD への READ(10) の裏返し | TOC を見てデータトラックへは出さない |
| 6 | ISO のあとの `:` が何も表示しない | ISO 解析の印が残り、結果が解析のほうへ渡っていた（前からの不具合） | 手動の読み出しで印を戻す |
| 7 | HALT 解除が塞がっていると TOC が失敗 | 「塞がっていた」を失敗にしていた | 200ms 後に出し直す |

#### 【重要】このドライブ（GT50N）は、コマンドを終わらせられないまま打ち切ると固まる
CSW を受け取れないまま打ち切ると、以後は INQUIRY も返らず、**ボードの再起動（ポートのリセット・再列挙）でも戻らない**。
ドックが給電し続けるので、抜き挿しするまで戻らない。BOT のリセットは原因ではなかった（リセットを送らない版でも固まった）。
→ **固まる引き金を出さないこと**（上の 3〜5）が肝心。時間切れからの立て直しは最後の手段。

#### 試して外れたもの（どちらも悪化したので外した）
- 「次の IN で止まる」を疑い、300ms ごとに GET_STATUS で止まっているかを聞く見張り -> 一度も止まっているのを見つけなかった
- HALT 解除のあと、ホスト側のトグルも DATA0 に戻す（`hw_endpoint_xfer_start` を横取りして `next_pid` を 0 に）
  -> リセット後の通信が全滅した。**このドライブは止まっていないときの HALT 解除でトグルを戻さない**らしく、ホストだけ戻すとずれる

#### 確認（2026-10-03、実機）
- データ CD: ISO と TOC を交互に繰り返して失敗0、`:` で LBA 16（`.CD001`）、`!` は出さずに断る
- 音楽 CD: 自動の TOC で 6 トラック（すべて音声）、`]` / `:` は出さずに断る、`!` で音声セクタ、TOC、CD 再生の先読み
- 映像は `underrun=0 fifo_stall=0 recover=0`

### 【2026-10-04、積み残し】FDD と光学ドライブを2台同時に扱う
`usbufi.c` の1台分の状態（約45個の static 変数）を、機器ごとの構造体 `ufi_dev_t`（`UFI_MAX` = 2）にまとめた。
関数の中の書き方は、マクロで「いま扱っている機器（U）」を指すようにして変えていない（text.c の開閉と同じやり方）。
- U を選ぶのは入口だけ: TinyUSB からの呼び出し（接続・完了・切断、制御転送の完了）は**アドレス**で、
  キー操作は**種類**で（FDD のキー・FAT はフロッピー、CD のキー・ISO・再生は光学ドライブ。`)` `=` はフロッピーを優先）、
  `usbufi_task()` は全機器を順に回す。CD の再生（PSRAM の先読み）は光学ドライブでだけ回す。
- バッファは機器ごと（`.bss` が約3KB 増）。状態表示は `(` で2台とも、画面のステータスは7行目と12行目。
- 実機（2026-10-04）: FDD（FAT12、22件）と光学ドライブ（音楽 CD、6トラック）が同時に認識され、
  FAT の一覧と TOC を交互に・同時に出しても両方とも成功。音声セクタ（CD）とセクタ0（FDD）もそれぞれのドライブに届く。

### 【実験・2026-10-04、積み残し】CD のデータ段を epx で読む — **未完成**
バルクは割り込み枠で1フレーム1パケット（64 KB/s）なので、データ段だけを epx（1フレームに何パケットでも投げられる）で
読む実験をした（`usbhw_epx_bulk_in()`、`usbufi.c` の Ctrl-B で切り替え。**既定はオフ**）。
- 作り: CBW と CSW は TinyUSB に任せ、データ段だけ USB の割り込みを止めて epx を直接操作する。epx の設定は退避して戻す。
  トグルは割り込み枠の最後の PID の逆から始め、パケット数が偶数の読み出し（CD 再生のまとめ読み 16セクタ = 588パケット）に限る。
- 結果: 最初のパケットが **34バイトの短いパケット**で返り、`sie_status` に **ENDPOINT_ERROR（0x00800000、RP2350 で追加）**
  が立った（`buf_ctrl=0000e022`）。シーケンスエラーではない。残りのデータは CSW として読まれ（`bad CSW signature 01 00 00 00` =
  音声データ）、立て直しのあとドライブが固まった（抜き挿しが要る）。
- 最初の試行ではウォッチドッグの時間切れで再起動した（ウォッチドッグを切ったビルドでは止まらず、先読みが 0 のまま）。
- 次に調べること: ENDPOINT_ERROR の詳細（`ep_rx_error` / `ep_tx_error`）を最初のパケットの直後に読む、epx のバッファの種類
  （割り込み型だと以前の実験 `g` では 8バイトを正しく受け取れていた）、割り込み枠のポーリングとの同時動作。
  **失敗するたびにドライブが固まり抜き挿しが要る**ので、試すときはまとめて。

### 【2026-10-04、積み残し】CD のデータ段を epx で読む — **完成、既定オン**（上の「未完成」の節の続き）
**結果**: 先読みが **64 KB/s -> 平均 830〜895 KB/s**（CD の等速 176 KB/s の約5倍）。4分間の連続再生で `underruns 0`、
壊れたパケット 0、制御転送の詰まり 0。2,918回・約40MB を読み、2% ほどは epx を借りずに従来の経路で読んだ。
参考: [TinyUSB issue #3533](https://github.com/hathach/tinyusb/issues/3533)、
[embassy PR #7128](https://github.com/embassy-rs/embassy/pull/7128)（RP2350B で epx のバルク 62 -> 744 KiB/s）。

直したこと（`usbhw_epx_bulk_in()`）:
1. **割り込みエンドポイントのポーリングを止めて読む**（`int_ep_ctrl` を 0 にし、200µs 待ってから。終わったら戻す）。
   SIE は epx と割り込みエンドポイントでハンドシェイクの記録を共有しており（issue #3533）、ポーリングとぶつかって
   最初のパケットが 34 バイトで切れていた。止めてからは切れていない
2. **`ENDPOINT_ERROR` は壊れの印ではない**。機器が NAK を返したあと（シーク中）の正しい 64 バイトのパケットにも立つ
   （`NAK_REC` と一緒、`ep_rx_error` は 0）。壊れとみなして読み直したら、ACK 済みのパケットを1つ失いずれた。
   壊れの判定は CRC・ビットスタッフ・溢れだけ（その場合は同じ PID で読み直す。実測では一度も起きていない）
3. SIE_CTRL・バッファ制御の書き込みのあとの待ちを、CPU のサイクル数ではなく 1µs に（48MHz 側へ届くのを待つ）
4. **最初のパケットが 20ms 来なければやめて従来の経路へ**（ドライブの回転待ちで 2.1 秒待ち、その間アプリが止まった）
5. **制御転送が epx を使っていたら借りない**。SETUP の送信中は AVAILABLE が立たないので、`hcd_setup_send` の包み
   （`usbfix.c`）で時刻を覚え、5ms 以内なら借りない。完了の印（`TRANS_COMPLETE`・`buf_status` の bit0）が残っていても借りない。
   これが無いと、2分ほどで制御転送が詰まり、見張りがホストを作り直してドライブが外れた
6. **読んでいる間（約45ms）も音のリングへ書き足す**（約1ms ごとに呼び出し側の `idle` を呼ぶ）。書き足さないと
   音のリング（約23ms）が底をつき、DMA が古い中身を鳴らし直して**音が約9%遅れ、継ぎ目でプチプチいった**（ユーザーが聞いて指摘）。
   記録では「鳴らした 44,100 フレーム/秒」なのに「再生したセクタ 68/秒」（正しくは 75）だった

使い方: `'` は epx がオンなら**ディスクの終わりまで**（最初のデータトラックの手前か、リードアウト）再生し、10秒分を貯めたら
鳴らし始めて、あとは鳴らしながら読む。オフ（Ctrl-B）なら従来どおり30秒分。Ctrl-B で速さの記録を出す。

### 【2026-10-04】FAT32 への書き込み
- `usbfat_write.inc` を FAT16 / FAT32 の両方を扱える形に書き直した。FAT16 との違いと対応:

  - ルートがクラスタの鎖。鎖をたどって同じ名前と空き項目を探し、**空きが無ければクラスタを1つ足してルートを伸ばす**

  - **FSInfo**: 空きを探すのは「次に探し始める位置」から（終わりまで来たら先頭へ）。書いたあと、空きクラスタの数（解放した分を足し、

## 【2026-10-09】exFAT・NTFS・ext4 の実装の手間の見積もり（積み残しの⑧。近日着手の予定）
基準は FAT の実装: 読み出し `usbfat.c` 735 行（約 1 日）、書き込み `usbfat_write.inc` 1,051 行（約 1.5〜2 日。新規作成・置き換え・
フォルダ・削除・名前の変更・長い名前・FSInfo）、ホスト試験 約 570 行。FAT32 = 1.0 として、ファイラーで一覧・読み出し（のちに新規作成・
削除・名前の変更）をする前提の推定。

| | 読み出し | 書き込み | 主に手間のかかる所 |
|---|---|---|---|
| exFAT | 0.6〜0.8（約 1 日） | 0.8〜1.0（約 2 日） | ファイル = 項目の組（File 85h・Stream C0h・名前 C1h x n）、空き領域はビットマップ、連続したファイルは FAT をたどらない（NoFatChain）、項目の組のチェックサムと名前のハッシュ（大文字表）、64 ビットの大きさ |
| ext4 | 1.0〜1.3（約 2 日） | 3〜4（1〜2 週間） | 読み: エクステント木・inode・ディレクトリ（htree も先頭から順に読める）・inline data。書き: ブロック / inode のビットマップ、グループ記述子の数、エクステント木の分割、metadata_csum（CRC32C）、jbd2 との整合 |
| NTFS | 1.5〜2.5（3〜5 日） | 5〜10 以上（数週間） | 読みでも MFT レコードと修正配列、常駐 / 非常駐の属性、データラン、ディレクトリの B+木（INDX）、属性リスト、圧縮（LZNT1）・疎ファイル。書きは $LogFile・MFT / ビットマップの割り当て・B+木の挿入と分割・セキュリティ記述子 |

共通してかかるもの:
1. **SRAM**（最大の制約）: USB の完了コールバックは FB を表示したままアプリ時間の外で走るので、解析のコードは SRAM に置く決まり。
   テスト用アプリの空きは約 1.8KB で、読み出しの実装（exFAT 6〜8KB・ext4 10〜15KB・NTFS 15〜25KB の見込み）が入らない。
   (a) アクセスの間だけ FB を隠してコードはフラッシュ（ファイルの新規作成と同じ。手間は小さいが FB がちらつく）か、
   (b) USB では生のセクタを SRAM に読むだけにし、解析はアプリ時間（フラッシュ）で行う形に作り直す（FAT にも効く。1〜2 日）。**先にどちらかを決める**
2. **2TB の壁**: READ(10)（32 ビット）で読んでいる。大きなディスクには READ(16) が要る（TinyUSB に口が無いので自前の CBW。約 0.5 日）。4K セクタのディスクは +0.5 日
3. **ホスト試験の道具**: mkfs.ext4・e2fsck・mkntfs はある。exFAT は exfatprogs（mkfs.exfat・fsck.exfat）を入れる
4. **大文字小文字を区別しない比べ方**: exFAT・NTFS はディスク上の大文字表（最大 128KB）を使う。SRAM に載らないので ASCII とラテン文字だけ自前の表で比べる割り切り（日本語は大文字小文字が無いので実害は小さい）

おすすめの順: (1) exFAT を読み書きとも（64GB を超える SD / USB メモリの既定で出会う機会が多く、FAT に近く安い）、(2) ext4 は読み出しだけ、
(3) NTFS は読み出しだけ・必要になったら（書き込みは手間も壊したときの影響も大きい）。
実機の試験には、いまの HDD（JMS578）の区画（MBR 版: FAT32・exFAT・NTFS・FAT16・ext4・FAT32、GPT 版も 6 区画）が使える。

  - ファイルの中身は、エクステント（PSRAM、8192 個まで）を求めてから 16KB ずつ SRAM の受け場へ読み、受け手へ渡す（アプリ時間、1 フレームに 16KB）
  - SRAM に置くのは完了の受け口だけ。ボリュームの塊・受け場（約 25KB）は開いている間だけ借り、テスト用アプリへ行くときに返す
  - PSRAM は約 2.2MB。**CD の先読みの「4MiB 残す」から、exFAT・NTFS が使っている分を引く**（両方を一緒に使えるよう。4MiB はこのために空けたもの）
- exFAT: ブートセクタ・ファイルの組（85h / C0h / C1h、名前は 255 文字まで）・NoFatChain（連続）と FAT の鎖・ボリュームラベル
- NTFS: ブートセクタ・$MFT の並び（レコード 0 の $DATA）・修正配列・INDEX_ROOT と INDX ブロック（BITMAP で使用中のもの）・
  DOS の 8.3 の名前は出さない・ルートのシステムのファイル（MFT 番号 16 未満）は出さない・常駐のデータ・データラン（疎もある）・ボリューム名
- 名前は一覧から取った正確な名前で引くので、大文字表は読まない（ASCII だけ大文字小文字を同一視）。exFAT の書き込み（名前のハッシュ）のときに要る
- **まだ扱わないもの**: 書き込み、NTFS の圧縮・暗号化・属性リストで $DATA が分かれたファイル、1 セクタ 512 バイト以外、2TB を超える位置
- ホスト試験 `scripts/test_fs.py`: exFAT は mkfs.exfat（exfatprogs を `apt-get download` で取り出す）+ `scripts/host_fs/exfatmk.py`（自前で中身を書く。
  fsck.exfat で確かめる）、NTFS は mkntfs + `scripts/host_fs/ntfsmk.c`（libntfs-3g を直接使う。マウントは権限が無い。ヘッダは ntfs-3g-dev を取り出す）。
  連続・FAT の鎖（22 エクステント）・長い名前・日本語の名前・2 段のフォルダ・空のファイル・200 項目のフォルダ（INDX）・断片化した NTFS のファイル
  （6 エクステント・約 60MB）を、区画の先頭が 0 と LBA 2048 の両方で、一覧と CRC32 で突き合わせる
- 実機: HDD（JMS578）の exFAT（B:）・NTFS（C:）の一覧と、`System Volume Information` のファイル（76 / 12 バイト。NTFS は常駐）を開けた。
  テスト用アプリの空き 680 B。**大きなファイル（非常駐・PNG）は、ユーザーが PC でファイルを入れてから確かめる**
- **【実機で見つけて直したこと】**
  - **スタックのあふれ**: exFAT の列挙がスタックに 1.2KB（組 608 B・名前 510 B）を取り、core0 のスタック（4KB）があふれて、すぐ下の
    **core1 のスタックを壊した**。core1 が `__wfe` から戻らず、毎ライン underrun（14 秒で 40 万回）。組と名前をボリュームの作業領域（`v->rec`）へ
    移して 96 B に。core0 のスタックを起動時に塗り（`stack_paint`、0xA5A5A5A5）、最高水位を読めるようにした（`stack_high_water`。止めずに
    `mdw 0x20081000 1024` でも読める）。ふだん 1.6〜1.7KB、PNG の解読の最中で 2.2KB
  - **PNG を開くとボリュームが閉じられていた**: `filer_leave`（一覧の置き場を返す。PNG を開く前にも呼ぶ）でボリュームを閉じていた。
    テスト用アプリへ行くとき（`filer_leave_app`）だけにした
  - **アプリ時間の窓を越えていた**: `fs_poll` の 1 段（受け手へ 16KB を渡す・PSRAM のキャッシュへ 4KB 写す、フラッシュのコード）を残り 200µs で
    始めていて、PNG を読む間に underrun 251・fifo_stall 87。500µs に（届いた分の片付けも含めて）
- 実機（直したあと）: exFAT の PNG（1344x896・1.6MB）3.97 秒、NTFS の PNG（2688x1792・7.9MB）19.2 秒、どちらも underrun 0・fifo_stall +1〜2。
  テスト用アプリへ行って戻っても読める。テスト用アプリの空き 648 B
- 【遅さ】読み出しは 0.4〜0.5MB/s（FAT の USB メモリは 0.65MB/s 以上）。アプリ時間に 1 回ずつ頼むので、16KB を読む間（1 フレームより長い）に
  次を頼めない。【追記 2026-10-09】下の「受け場 2 つ」で解決
- 【観察中】起動直後に一度だけ `underrun` 約 380 回（HDD のマウントの頃）が出ることがある。今の版で 6 回中 2 回（どちらも書き込んだ直後の起動）、
  変更前の版で 5 回中 0 回。裏読み・exFAT / NTFS のボリュームはその時点で使われていない（数を見た）。原因は未確定

## 2026-10-09 exFAT・NTFS の読み出しを受け場 2 つに

- ストリームの受け場を 16KB x 2（`app_alloc`、ストリームの間だけ）にし、**完了の受け口（`fs_io_cb`、SRAM）で次の READ(10) を出す**。
  次に読む位置（`nx_lba` / `nx_cnt` / `nx_bytes`）はアプリ時間に `step()` が用意しておき、受け口はもう片方の受け場が空いていれば使う。
  塞がっていた（`tuh_msc_read10` が false）・受け場が空いていないときは、アプリ時間に頼み直す。受け手へは頼んだ順に渡す（`st_issued` / `st_deliv`）。
  疎の範囲は読み出しの後ろに並べて 0 で埋める。打ち切りは `nx_valid` を下ろして連鎖を止め、読んでいる分が届いてから受け場を返す
- 受け口で割り算をしない: 頼んだ時刻を ms（`to_ms_since_boot` = 64bit の割り算、フラッシュの定数）から `time_us_32()` に（`check_sram_funcs.py` が見つけた）
- 実機: exFAT の PNG（1.6MB）3.97 -> **2.65 秒**、NTFS の PNG（7.9MB）19.2 -> **12.5 秒**。3 回ずつ underrun 0
- **これで表示の不具合が 1 つ表に出た（映像側、`docs/notes/video.md` の同じ日付の節）**: 読み出しが途切れなくなって core0 の描画が遅れ、
  期限に描画が終わらずライン 0 を越えると、1 フレーム遅れのまま固定され毎ライン underrun が続いた

## 2026-10-09 exFAT の書き込み・FAT の流し書き・ファイラーの作る・消す・コピー

ユーザーの依頼: 「ファイルの新規作成、削除、書き込み」。exFAT を先に（NTFS はあと）、2 ドライブ間のコピーまで。試験で B:（exFAT）・C:（NTFS）に書いてよい。

### exFAT の書き込み（`src/fs/exfat_w.inc`、`fs_write` / `fs_delete` / `fs_cancel`）
- 書く順番（途中で止まっても既存のファイルを壊さない）: 大文字表を引いて名前のハッシュ -> 親のディレクトリを調べる（同じ名前・空き項目の並び。
  足りなければ 1 クラスタ伸ばす）-> 空きクラスタを集める（まず 1 続き、無ければ飛び飛び）-> データ -> （飛び飛びなら）FAT の鎖 -> ビットマップ ->
  項目の組（後ろのセクタから、85h のセクタを最後に。置き換えは同じ場所を書き換える）-> （置き換えなら）古いクラスタを返す
- 消す: InUse を下ろす（85h のセクタから）-> ビットマップで返す。フォルダは中が空のときだけ
- ディレクトリを伸ばす: NoFatChain のフォルダで隣のクラスタが空いていなければ、鎖を書いて NoFatChain を下ろし、親の項目の大きさを書き直す
- 名前のハッシュに要る大文字は、書くたびに大文字表（圧縮）を 1 回なめて名前の文字の分だけ引く（128KB の表を PSRAM に広げない）
- 書き込みは `fsc_write`（キャッシュも書き換える = 書き通し）。1 つの読み書きが終わるまで次の段へ進まない（`xw->sec`・`xw->buf` を USB が読んでいる間に変えない）
- 決めごと: 日付は固定（2026-10-04 12:00）。PercentInUse・VolumeDirty は触らない。ビットマップと大文字表は 1 続きのクラスタにあるものとする
- ホスト試験（`test_fs.py` の exFAT write）: 書く・置き換え（大きく・小さく）・空・日本語の名前・消す・空でないフォルダ / 無い名前 / 使えない名前 / 同じ名前のフォルダ /
  途中のフォルダが無い / 入らない を断る・ルート（FAT の鎖）と NoFatChain のフォルダを伸ばす・飛び飛びの割り当て（8 エクステント）。

### FAT（`usbfat`）

### ファイラー（`filer.c`・`src/filer/fcopy.c`）
- **N** は exFAT でも作る。**Del** で消す（y で確かめる）。**C** でコピー: 行き先のドライブ（FAT・exFAT・フロッピー）を選び、パス（ファイルの名前が入っている）を直して Enter。ESC で止める

## 2026-10-09 書き込みのデータ段も epx で送る（積み残し）

- `usbhw_epx_bg_start()`（裏読み）に**送る向き**を足した（`ep_addr` の向きで決まる）。1 パケットずつ epx の窓へ写して SEND_DATA で出し、
  届いた（ACK）割り込みで次を出す。`usbfix.c` の `hcd_edpt_xfer` の包みで、MSC としてマウントされた機器の bulk OUT（512 バイト以上・128 の倍数）を渡す
- **PID**: TinyUSB はトグルをソフトで 1 パケットごとに反転させ、バルクは割り込み枠（OUT は向きのビットが立った枠）で送る。MSC のデータ段の直前には
  必ず同じエンドポイントで CBW（1 パケット）が出るので、その枠のバッファ制御に残った PID の逆から始める。パケット数を偶数に限れば TinyUSB の覚えている
  次の PID ともずれない。**OUT にはシーケンスエラーの知らせが無く、PID を間違えると機器は受け取ったふりをして捨てる**ので、中身の CRC32 で確かめた
- 速さ（HDD、JMS578）: コピー C:（NTFS）-> B:（exFAT）7.9MB **80 -> 344 KB/s**、C: -> A:（FAT32）**294〜302 KB/s**（読みと書きが同じ機器で交互）。
  B: の中のコピー（全部読んでから書く）1.6MB **54 -> 306 KB/s**（書き込みだけなら約 500 KB/s）。epx で送った回数 476（7.7MB のほぼ全部）
- **中身の確かめ**: コピーが流した中身の CRC32 をログに出すようにした（`[filer] copied ... CRC32 xxxxxxxx`）。C: -> B: -> A: -> B: と写し、
  3 回とも `5c8a85cb`（exFAT と FAT の書き込みの両方が正しい）。別の画像で B: -> A: -> B: も `a0a0e31b` で一致。PNG の解読は CRC・adler32 を確かめないので、これで見た
- 試験で作ったファイルは消した（A: は 1 項目、B: は 22 項目に戻った）
- **途中で見つかった、裏読みの割り込みの嵐**（`docs/notes/usb.md` の同じ日付の節）: 映像が数フレーム止まり、1 フレーム遅れに固定される不具合の引き金だった

## 2026-10-09 NTFS の書き込み（作る・置き換える・消す）

ユーザーが候補の中から選んだ。`src/fs/ntfs_w.inc`（ntfs.c に取り込む）。口は exFAT と同じ `fs_write` / `fs_delete` / `fs_cancel`。

### 安全のための約束（ボリュームごとに最初に 1 回確かめ、だめなら書かない）
- `$Volume`（3）の VOLUME_INFORMATION が NTFS 3.x で、dirty の印が無い
- `$LogFile`（2）のリスタート領域が「きれいに閉じた」（使用中のクライアントが無いか、RESTART_VOLUME_IS_CLEAN）。全部 0xFF（空の記録）もきれい。
  Windows の高速スタートアップ・休止状態のあとは断る（ログに書きかけの記録があり、Windows がやり直すと書いた中身を壊す）
- ログは書かない（きれいに閉じたボリュームでは Windows はやり直さない。ntfs-3g はログを全部 0xFF に戻すが、ここは確かめて触らない）
- **2026-11-09 の限定修復**: リスタート領域が unclean でも、クライアントの `oldest_lsn` と `client_restart_lsn` が
  `current_lsn` と同じなら「やり直す記録が無い」とみなし、**両方**のリスタートページの clean 印を立て、`$Volume` の dirty を消してから書く
  （`N_LOG2` / `N_LOG_FIX1` / `N_LOG_FIX2` / `N_VOL_FIX`）。未処理の記録があるとき・2 枚目が読めない/連続していないときは断る。
  強制書き込みモードは作らない（壊す危険があるため）。断る理由は画面に出す（`rbfs_last_why`）。

### 手順
- 作る: データ -> `$Bitmap` -> MFT のレコード（$STANDARD_INFORMATION・$FILE_NAME・$DATA。512 バイト以下は常駐）-> `$MFT` の `$BITMAP` -> 親の索引
- 置き換え: 新しいクラスタにデータ -> `$Bitmap` -> レコードの名前なし `$DATA` を差し替え（ほかの属性はそのまま。$FILE_NAME の大きさも）-> 索引の項目の大きさ -> 古いクラスタを返す
- 消す: このフォルダの中の名前（Win32 と DOS の 2 つまで）を索引から外す -> クラスタを返す -> レコードを未使用にして順番号を進める -> `$MFT` の `$BITMAP`。フォルダは中が空のときだけ
- 索引（$I30、B 木。照合は大文字表 $UpCase で比べ、同じなら大文字小文字で）:
  - 挿入は葉へ。入らなければ分ける（項目をバイト数で半分に、中央の項目を親へ上げる。左を新しいブロックへ）。親も入らなければ繰り返す
  - INDEX_ROOT（MFT のレコードの中）があふれたら、中身を新しい INDX ブロックへ移し、ルートは「おしまいの項目 + 子」だけに。
    **先にルートを縮めてから** INDEX_ALLOCATION と $BITMAP を足す（足してから縮めると、親のレコードに空きが無かった）。INDEX_ALLOCATION が足りなければ 1 ブロック伸ばす
  - 内側の項目を消すときは、左の部分木のいちばん右の項目で置き換える
  - **空になった葉は外す**（親の中でそれを指す項目を兄弟の葉へ下ろし、葉を $BITMAP で未使用に）。外さないと、あとで内側の項目を消すときに置き換えの項目が見つからなかった
- 新しいファイルの名前空間は **POSIX（0）**（ntfs-3g と同じ）。Win32（1）は「別に DOS の名前がある長い名前」の意味で、8.3 の名前を作らないので使えない
  （最初 Win32 にしたら、libntfs-3g が対の DOS の名前を探して見つからず、消せなかった）。セキュリティ ID は親のもの、日付は固定（2026-10-04 12:00）
- `$UpCase` は最初に書くときに PSRAM へ 128KB 読む（`upcase_ok` まで使わない。【誤り】読み出し待ちから戻ったとき「もう表がある」として途中の表で比べ、項目を先頭に入れて索引を壊した）

### 断るもの（未対応）

## 2026-11-05 FAT の SRAM 不足

## 2026-11-08 USB-HDD 間のコピーが 30 秒で止まる（msc512 の同時転送）

- **症状**: ファイラーで G:（305GB HDD の NTFS）の `YM2151`（303 ファイル、5.7MB）を
  A:（JMS578 38GB HDD の FAT32）へコピーすると、1〜3 ファイルで止まり、30 秒後に
  `[fatrd] the drive did not answer` / `could not read the volume`。キーボードまで反応しなくなることがあった。
- **切り分け**:
  - `MSCINFO`: msc0 = `152D:0578`（38GB、A〜F）、msc1 = `0411:00A8`（305GB、G）。A: と G: は**別の機器**。
  - 止まった LBA（A: 239223 など）は `USBREAD` の生読みで全部読める。**不良セクタではない**。
  - 時間切れのログで、`msc512` の転送が addr 1（A:）と addr 3（G:）の両方で残っていた。
- **原因**: `msc512` の「512 バイト機器 + SRAM バッファ」の近道が `m5.busy` を立てず、
  G: の読み出しと A: の書き込みが同時に走っていた。RP2350 の HCD はバルクを 1 本ずつしか扱えないため、
  完了が返らず 30 秒で時間切れになる。さらに「空き確認 → busy を立てる」の間に USB タスクが割り込む競合もあった。
- **直したこと**:
  - すべての MSC 転送を `m5` で直列化（近道を削除）。
  - busy の確認と設定を `save_and_disable_interrupts` で排他。
  - 時間切れで `msc512_abort` を呼び、塞がりを下ろす。`fjob` は同じファイルを最大 4 回やり直す。
  - `usbfat` はボリュームの形（daddr/lun/区画）を覚え、ファイルごとの MBR/VBR 読み直しをやめる。
  - 保険として、書き込み確定 `SYNCHRONIZE CACHE`、FAT の 4KB 区切り読みを入れた。
  - 遠隔コマンド: `MSCINFO` / `USBSYNC` / `USBRESET` / `USBREAD` / `COPYGAP` / `USBRESTART`。
- **実機**:
  - 22 ファイルのフォルダ（`G:/YM2151/Fantasy_Zone...`）→ A:/: **13 秒で完了**。
  - 303 ファイル全体 G:→A:: 150 前後で USB ホストが詰まる（修正前は 1〜3 ファイル）。

## 2026-11-16 ドライブ文字の固定

- **ユーザー指示**: 決めた大容量記憶の機器がつながったら決めた文字を振り、つながっていなければその文字は空けておく（ほかの機器に回さない）。見分けは VID:PID と USB のシリアル番号（区画ごと）。設定は S:。
- **表**（ユーザーと決めた形）: `S:/SystemSettings/DriveLetters.cfg`。見かけた機器を**区画ごとに 1 行**、そのとき振った文字で**無効（0）**として書き足す（同じ VID:PID・シリアル・区画の行があれば何もしない。シリアルの無い機器は容量で見分ける。区画を調べている間とシリアルを読む前は待つ）。行は 64 まで。**頭を 1 にした行（有効は 8 行まで）だけ**が文字を固定する。1 行の形: `1 K msc 0411:00A8 0 625142448 000013101FAA`（有効・文字・種類・VID:PID・区画（- = 区画なし）・容量・シリアル）。
- **有効にする**のは手で: ファイラーのドライブの窓（F9 / L）の F2（有効・無効）・F3（文字を決めて有効）か、ファイルを書き替えて Ctrl+R。9 つ目の有効・文字がぶつかる行は無効として読む。
- **文字の振り方**（`filer.c` の `assign_letters`）: 有効の行に当たる区画は決めた文字、残りは A から順に S と有効の行の文字を飛ばす。ドライブは文字の順に並べる。窓では固定の文字に `*`、つながっていない有効の行も薄い色で出す。
- **シリアル番号**（`src/input/usbserial.c`）: 機器がつながってから 3 秒たったら、機器記述子と iSerialNumber の文字列記述子を 1 度だけ読む（GET_DESCRIPTOR を自分で組む。1 度に 1 つの制御転送、塞がっていれば次のフレーム）。外れたら忘れる。
- **直したこと**: Ctrl+R で読み直す途中（ファイルを読む待ちの間もファイラーの画面の仕事が回る）に、まだ読んでいない区画を無効の行として書き足し、あとから読んだ行が「同じ行がもうある」で捨てられていた。読み書きの最中は書き足さない。`sscanf` が newlib の一式（約 8KB）を SRAM に引き込んだので、16 進・10 進は自前で読む。
- **実機**: 7 区画が無効で書き足された。F3 で G: -> K:、F2 で B: をいまの文字で有効、リセットのあとも保たれた。ファイルを手で書き替えて Ctrl+R で C: -> Q:。
