## USB HID キーボード（第6段階・2026-09-24）
RP2350 のネイティブ USB ポートを**ホスト**にして、OTG ケーブルでキーボードを直結する。
`src/input/usbkbd.c`、設定は `src/tusb_config.h`。ハブは使わない（`CFG_TUH_HUB=0`、`CFG_TUH_DEVICE_MAX=1`）。

- **ブートプロトコル**で受ける（レポート記述子を解釈しない）。レポートは 8バイト固定
  `{修飾キー, 予約, キーコード x6}` なので扱いが簡単で、キーボードなら必ず対応している。
- 前回のレポートと比べて「新しく押されたキー」だけを文字にしてリングへ積む。
  押しっぱなしのリピートは自前（400ms 待って 40ms 間隔。USB 側はリピートしない）。
- **複数のキーボード配列**（2026-11-03）。US は TinyUSB の `HID_KEYCODE_TO_ASCII` をそのまま、JIS / PC98 / 親指シフト /
  AZERTY / QWERTZ / スペイン語 / ポルトガル語 / イタリア語は差分表を持つ。ファイラーの F10 の「キーボードロケール」で選び、
  `SystemSettings.cfg` の `kbd=` に残す。英語の AT104 / Macintosh / SUN Type6/7 / HP-UX / SGI、日本語の OADG109 / PC98 /
  PC-8801mk2SR / X68000Z / 親指シフト / μTRON / AX / Sun日本語USB などを並べる（機種固有のキーや非 ASCII は一部未対応）。
  `K` キー（テスト用アプリ）でも US/JIS を切り替えられる。**英字・数字はほとんど同じ**なのでコマンド操作には影響しない。
- **USB キーボードと UART コンソールのどちらからでも同じ `handle_key()` へ流す**。
  打たれた文字はテキスト面の20/21行目と UART（`[kbd] key 0x..`）に出る。`U` で USB の状態。
- `tuh_task()` は**アプリのループと `video_wait_render_done()` の中の両方から**呼ぶ
  （`video_set_idle_hook()`）。待っている間も USB を止めないため。

### 【重要・2026-09-24 の反省】「自力で接続イベントを起こす」対策は**不要で、むしろ害だった**
当初「デバイスが既に刺さった状態で `tuh_init()` すると、`hcd_rp2040.c` は接続の“変化”割り込みでしか
検出しないので気づかない」と考え、`hcd_event_device_attach()` を自分から呼ぶ対策を入れた。
**これが間違いで、列挙を壊していた。**
- TinyUSB のログ（`-DSGNANO_USB_DEBUG=2`）を出して見たところ、接続の割り込みは**ちゃんと来ていて**
  列挙も始まっていた。`USBH Device Attach → Full Speed → Open EP0 → Get 8 byte of Device Descriptor`
  まで進んだところへ、こちらの接続イベントが割り込んで止めていた。
- **対策を外したら、そのまま列挙が通った**（`HID mounted: protocol=keyboard` → `keyboard ready`）。
- さらに、繰り返し呼ぶと usbh の状態が壊れ、**約1秒後にシステムごと止まる**
  （毎回きっかり572フレーム = 9.5秒で停止）。ハブの列挙が失敗していたのもこれが原因。
- 対策のコードは `SGNANO_USB_ATTACH_FIX` で無効化して残してある（既定 0）。

**なぜ誤診したか**: 起動バナーで `usbkbd_print_info()` を呼んでいたが、
**USB の列挙は起動から1秒ほどかかる**ので、バナーの時点では必ず `no keyboard` と出る。
これを「認識に失敗している」と読み違え、ありもしない問題の対策を作り込んでしまった。
→ バナーからキーボードの状態表示を外した。着脱は `tuh_mount_cb`/`tuh_umount_cb` が出すし、
  いつでも `U` キーで見られる。
**教訓**: 「出ていない」を「失敗している」と決めつける前に、**まず観測の仕方を疑うこと**。
PT8211 のときと同じ轍だった。TinyUSB のログを最初に出していれば1手で済んだ。

### 【重要】デバッグプローブを繋いでいると TinyUSB の assert で CPU が止まる
TinyUSB の `TU_ASSERT` が失敗すると `TU_BREAKPOINT()` が走る。これは
```c
if ((*ARM_CM_DHCSR) & 1UL) __asm("BKPT ");   /* デバッガが繋がっているときだけ止める */
```
という作りで、**プローブを繋ぎっぱなしにしていると（OpenOCD が C_DEBUGEN を立てたまま離れるため）
assert ひとつで CPU ごと止まる**。プローブが無ければ assert は false を返すだけで、
その機器の列挙に失敗するだけで動き続ける。
- **見分け方**: 停止位置を調べて `bkpt 0x0000` の上にいたら TinyUSB の assert。
  `arm-none-eabi-objdump -d --start-address=<pc> --stop-address=<pc+4>` で確認できる。
- **対処**: `scripts/flash_swd.sh` は書き込み／リセットの最後に
  `mww 0xE000EDF0 0xA05F0000`（DHCSR の C_DEBUGEN を落とす）を実行してから離れる。
  これで実機本来の挙動になる。**これを入れる前は「ハブを挿すとフリーズする」と誤解していた。**


### USB の列挙がうまくいかないときの診断
`cmake -DSGNANO_USB_DEBUG=2` でビルドすると TinyUSB が列挙の経過を UART に出す。
**SDK は CMake 変数 `LOG` から `CFG_TUSB_DEBUG` を決め、`-DCFG_TUSB_DEBUG=0` をコマンドラインで
付けてしまう**ので、`tusb_config.h` の `#ifndef` では上書きできない。`pico_sdk_init()` より**前**に
`set(LOG <level>)` する必要がある（CMakeLists.txt でそうしてある）。
切り分けには `U` キーも使える（`VBUS` / `SPEED`（1=Low, 2=Full）/ `LINE`（0=SE0, 1=J, 2=K））。


### ハブ対応（2026-09-24）
`CFG_TUH_HUB=2`、`CFG_TUH_DEVICE_MAX=4`（`usbh.c` の `TOTAL_DEVICES = DEVICE_MAX + HUB` なので
ハブはアドレス5,6を使う）。**ハブを2段つないだ構成で列挙・キー入力とも動作する**。
- **TinyUSB はハブに対して `tuh_mount_cb` を呼ばない**（`usbh.c`: `is_hub_addr()` ならログに出すだけ）。
  着脱のログだけ見ていると「ハブが見えない」ことになる。`U` キーで全アドレスを走査した一覧を出す:
  ```
  [usb]  addr=1 VID=258A PID=0016 speed=Full
  [usb]  addr=5 VID=214B PID=7250 speed=Full  [HUB]
  [usb]  addr=6 VID=1A40 PID=0101 speed=Full  [HUB]
  ```
- **【安定性・2026-09-25 解決】バスパワーのハブ2段では、起動時の列挙が 6/11（約55%）でしか
  一発で成功しない**。失敗しても**自動で作り直して必ず復帰する**ようにした（下記）。実測 **11/11 が最終的に成功**。

#### 原因（2026-09-25 特定）
RAM に貯めた TinyUSB のログ（`-DSGNANO_USB_LOG_RAM=ON`、`u` キーで吐き出し）で捕まえた。
失敗したときに出るのはこの2つで、**どちらもハブ経由の制御転送が1回こけただけ**:
| ログ | 場所 | 意味 |
|---|---|---|
| `process_enumeration 1496: ASSERT FAILED` | `usbh.c` | 設定記述子の `wTotalLength` が `CFG_TUH_ENUMERATION_BUFSIZE`(256) を超えた＝読めた値が壊れている |
| `process_set_config 566: ASSERT FAILED` | `hid_host.c` | HID の設定中の制御転送が成功以外で返った |
**TinyUSB は assert で打ち切り、そのまま再試行しない**。機器は `connected=1` のまま残るので、
抜き差しするまで直らない。**アプリのループは止まらないので、ウォッチドッグでは救えない**。
（以前「`_parse_configuration_descriptor` の `itf2drv` の assert でアプリが止まる」と書いていたのは誤り。
あれはプローブを繋いだままで `TU_BREAKPOINT` が CPU を止めていたのを見ていた。）
- 記述子そのものは小さい（キーボードで約60バイト）ので、`CFG_TUH_ENUMERATION_BUFSIZE` を増やしても
  直らない。**読めた値が壊れている**のが問題で、そのまま進んでも転送は失敗する。

#### 対処: 列挙が黙って失敗したら、ホストスタックごと作り直す
`usbkbd.c` の `reinit_check()`。**3秒（`SGNANO_USB_REINIT_MS`）たっても何もマウントされなければ
`tuh_deinit()` + `tuh_init()`**。上限5回（`SGNANO_USB_REINIT_MAX`。機器が無いときに延々やらないため）で、
マウントに成功したら回数は戻る。
- **実測（2026-09-25、ハブ2段、リセット12回）**: 一発成功6、作り直しで復帰5、失敗のまま0。
  復帰にかかるのは起動から約5秒（作り直しが2.5秒、そのあと列挙に2.7秒）。
  この間も映像は `underrun=0` `fifo_stall=0` `recover=0` `min_ready=25` のまま乱れない。
- `U` キーの `reinit=N` で作り直した回数が分かる。
- **一発成功率（約55%）そのものはソフトでは直せない**。ハブ経由の転送品質の問題なので、
  セルフパワーのハブなら改善する可能性がある。**手持ちが無いため保留**（2026-09-25）。

#### 列挙の失敗を追う道具（`-DSGNANO_USB_LOG_RAM=ON`）
**UART へ直接出すと待ち時間で列挙のタイミングが変わり、失敗が再現しなくなる**
（レベル2 をそのまま出したら 11/11 成功してしまった）。そこで TinyUSB のログの出力先を
`CFG_TUSB_DEBUG_PRINTF` で RAM の環状バッファ（16KB、`src/input/usblog.c`）に差し替える。
- `u` キーで吐き出す。**起動から6秒たっても何もマウントされていなければ自動で吐き出す**。
- 既定 OFF（SRAM を 16KB 使うため）。`-DSGNANO_USB_DEBUG=1` と組み合わせると、
  出力量が少ないまま assert の場所だけ確実に捕まえられる（この組み合わせで原因を特定した）。

### 【重要・2026-09-25】DualShock 3 の振動を追っていて見つかった、土台の不具合4つ
振動そのものより手前に、**入力が止まる・機器が列挙し直され続ける**不具合が隠れていた。
「振動が来ない」の相当部分はこれが原因（設定を送っても再列挙で毎回消えていた）。

1. **出力レポートを無言で捨てていた**。`ds3_send_out()` は `tuh_hid_set_report()` が
   `false`（制御転送が塞がっている）を返すとそのまま諦めていた。**掃引14段階のうち9段階が
   機器に届いていなかった**。印を立てて `usbpad_task()` から出し直すようにした。
2. **パッド用の張り直し（kick）を、マウント時に無条件で有効化していた**。
   張り直しは「データトグルがずれて1件も来ない機器」専用の劇薬で、正常な機器に当てると
   逆にレポートが止まる（この注意自体は前から書いてあったのに、パッドだけ例外にしていた）。
   DS3 で `reports=0` になっていた。**猶予のあいだ1件も来なかったときだけ入れる**に変更。
   - 猶予は **3000ms**。**DS3 は有効化コマンド（feature 0xF4）が通るまで1件も出さない**ので、
     500ms では「無反応」と誤判定して張り直しを入れてしまい、かえって黙り込んだ。
3. **ホスト作り直しの堂々巡り**。2の結果 `stuck_check`/`drop_check` が連発し、数秒おきに
   全機器が再列挙されていた。**間隔の下限 8秒**（`HOST_RESTART_MIN_MS`）を入れ、
   さらに `host_restart()` でも `mounted_peak` / `drop_due_ms` を戻すようにした
   （手で頼んだときだけ戻していたのが漏れ。戻さないと「作り直した直後＝まだ1台も戻っていない」を
   『機器が減った』と判定して、また作り直す）。

4. **`stuck_check` が「存在しない詰まり」を報告していた**。`tuh_descriptor_get_device()` が
   `false`（= 制御転送が塞がっている）を返すのを詰まりに数えていたが、これは正常な一時状態。
   パッドの有効化や LED の指示と重なるだけで5回に達し、**ホストを作り直していた**
   （振動の掃引のたびに作り直しが走り、パッドの入力まで巻き込まれた）。
   **DS3 の有効化で一度踏んだのとまったく同じ誤り。**
   → 「塞がっていた」は数えず 200ms 後に出し直す。**出せたのに返ってこない**ものだけを数える。
   ずっと塞がったままは本物なので、別枠（`STUCK_BUSY_MAX` = 約10秒）で見張る。

**結果**: DS3 が毎秒100件で安定して流れるようになった（再マウント0・張り直し0・作り直し0）。
確認は `[run] pad: ok reports=N` の行（`main.c` で追加）。
振動の掃引（`.`）も14段階すべてが届き、映像も無傷のまま完走する。

### 【重要・2026-09-25 確定】DualShock 3 へ出力レポートを送ると、入力も出力も同時に止まる
毎秒100件で安定して流れているところへ出力レポート（振動・LED）を**1回**送ると、
**その瞬間から入力が永久に止まる**。送った転送自体も完了が返らない。
```
[run] pad: ok reports=2072      <- 毎秒100件で正常
[pad] output report ... (rumble right=0 left=160)
[run] pad: ok reports=2167      <- 以後14秒まったく増えない
```
- **割り込み OUT（EP 0x02）でも制御転送（SET_REPORT）でもまったく同じ**。
  それぞれ単独で切り分けた（`;` キーで経路を切り替えられる）。**経路の問題ではない。**
- 映像は無傷（`underrun=0` `fifo_stall=0` `recover=0`）。アプリのループも止まらない。
- 復帰にはホストの作り直し（`R`）が要る。

#### 試して外れた対策（3つとも、入れたことで悪化した）
| 対策 | 結果 |
|---|---|
| 制御転送の間だけ `usb_hw->int_ep_ctrl` のビットを落としてポーリングを止める | **止めても詰まる**（＝競合ではない）。しかも**ビットを戻してもポーリングが再開しない** |
| パッドの入力が黙ったら PID を反転して張り直す（F310 と同じ手） | **入力も出力も完全に死んだ**。張り直しが8回連続で走り二度と流れない |
| 送信前に `tuh_edpt_abort_xfer(daddr, 0x81)` で入力転送を正式に取り下げる | **さらに悪化**。入力が最初から0件。列挙直後はまだ転送が張られていないため状態が合わない |

**【教訓】この3つはいずれも「自分が足した対処が原因で壊れた」。本日3度目。**
`docs/DEVELOPMENT.md` の「張り直しは止まる機器専用の劇薬」という自分の警告を、同じ日に3回踏んだ。
**次に疑うのは自分のコードではなく、機器そのものと別ホストでの挙動。**

#### 【決定的】止めるのは「振動バイト」だけ。同一ビルドでの A/B
`/` キー（LED だけを変える）と `,` キー（振動を入れる）を、**同じビルド・同じ48バイトの
出力レポート・同じ経路**で比べた。**違うのはバイト `[4]`（大モーターの強さ）だけ**。

| 送ったもの | 入力レポート |
|---|---|
| LED のみ（`[4]`=0） | 118568 -> 120068 **毎秒100件、途切れなし** |
| 振動（`[4]`=160） | 123367 -> **123389 で完全停止** |

**出力レポートの転送そのものは問題ない。モーターを回せと言われた瞬間に機器が応答しなくなる。**

#### 有力な仮説: 電流不足（ブラウンアウト）
ユーザーが早い段階で「**160だけは振動が来ました**」と報告している。**一度でも回ったなら
モーターは存在する**。すると「振動を実装していない偽物」より、**モーターの起動電流で
バスパワーのハブが電圧降下し、機器が応答しなくなる**ほうが筋が通る。
- 振動モーターの起動電流は数百 mA。バスパワーのハブにキーボードと同居している。
- LED だけなら電流はごく小さく、実際まったく問題が起きない。
- **セルフパワーのハブが手元に無いため、確認は保留**（2026-09-25、ユーザーの判断で振動は中断）。

#### 振動を再開するときの手順
1. **セルフパワーのハブ**か、パッドを**直結**にして試す。
2. 強さを小さい順（1 → 8 → 32 → 64 → 128 → 255）に上げ、**どこで入力が止まるか**を見る。
   `.` キーの掃引がこの順になっている。**振動を感じなくても、入力が止まるかどうかで判定できる**
   （小さい強さでも止まる = 電流ではない / 大きい強さだけ止まる = 電流不足）。
3. 可能なら DS3 を PC か PS3 につないで、振動が動く個体かを確かめる。
   Windows は DS3 を素では扱えないので、DsHidMini 等のドライバが要る。PS3 があればそれが最速。

### 振動の掃引（`.` キー）

DS3 の出力レポートの流儀は2つある。**LED が `[9]` で効くことは実機で確認済み**なので
並びは Host Shield 流で合っているはずだが、継続時間の値や強さの与え方が未確定。
| | `[0]` | 振動 | LED |
|---|---|---|---|
| USB Host Shield 2.0 | 0x00 | `[1]`=右時間 `[2]`=右強さ `[3]`=左時間 `[4]`=左強さ | `[9]` |
| Linux hid-sony | 0x01（レポートIDの再掲）+ `[1]`=0x01 | `[2]`〜`[5]` | `[10]` |
`.` キーで7通り（継続時間 0xFF/0xFE/0x20、強さ 160/255、小モーター、Linux 流の並び）を
順に鳴らし、どれで振動したか申告してもらう。

### 実測（2026-09-24、実機で確認）
- キーボード: `VID=258A PID=0016`、Full Speed。`zxcvbnm,./ asd` が正しくデコードされた。
- 同時動作: CLUT8 + ローレゾ + 発音2ボイス + キーボードで
  `underrun=0` `fifo_stall=0` `recover=0` `min_ready=24` `pair_max=65/68µs`。
- SRAM は約425KB / 512KB（TinyUSB ホストスタックで約17KB 増）。

## USB HID マウス（2026-09-25）
`src/input/usbmouse.c`。キーボードと同じネイティブ USB ポートにぶら下げる。
TinyUSB の HID コールバックは1組しかないので、`usbkbd.c` が受けて `tuh_hid_interface_protocol()` で振り分ける。
画面（テキスト面の23/24行目）には**移動量とボタンだけ**出す。`N` キーで累計を0に戻す。

### ホイールにはレポートプロトコルが要る
**ブートプロトコルのマウスレポートは仕様で3バイト `{ボタン, X, Y}` なので、ホイールが入らない。**
実機（093A:2510）も、ブートでは3バイトしか返さなかった（TinyUSB のログの `on EP 81 with 3 bytes`）。
→ マウント時に渡されるレポート記述子を解釈し、ホイールがあれば
`tuh_hid_set_protocol(..., HID_PROTOCOL_REPORT)` で切り替えて、その並びで読む。
- 解析対象は「よくあるマウス」に絞る: Generic Desktop の X(0x30)/Y(0x31)/Wheel(0x38) と Button ページ。
  レポートIDあり・8/16bit フィールドにも耐える。解釈できなければブートの並びに戻る。
- **切り替えが済むまではブートのレポートが来る**ので、レポート長が記述子どおりのときだけ
  解析結果を使い、それ以外はブートの並びで読む（長さで見分ける）。
- 実機の解析結果: `4 bytes id=0 btn@0(8) x@8/8 y@16/8 wheel@24/8`。`U` キーの
  `len=4 map=1 wheel_in_descriptor=1` で、実際にその並びで読めていることを確認できる。

### 【重要・2026-09-25】ハブ越しのロースピード機器は、割り込み EP を張り直せば動く
**ロースピードのマウスをハブの先につなぐと、割り込み転送が1〜4レポートで止まる。**
エンドポイントは `avail=1` のまま polling しているのにデータが返らない。映像やアプリのループは
正常なのでウォッチドッグでは救えない。**バッファ制御レジスタを書き直すと再び流れる。**

#### 切り分け（条件を1つずつ動かした）
| 試したこと | 結果 |
|---|---|
| マウス直結（単独） | 正常。毎秒60〜100レポート、数千件途切れず |
| マウス（Low）+ キーボード（Full）をハブ越し | マウスが1〜4レポートで停止。キーボードは正常 |
| **マウス以外の HID を一切 polling しない**（`-DSGNANO_HID_MOUSE_ONLY=ON`） | やはり停止。他のインタラプト転送は無関係 |
| 停止後に制御転送（GET_DESCRIPTOR） | **成功**。機器は生きていて PRE 付きの制御転送も通る |
| 制御転送で読む（GET_REPORT(Input)） | 手持ちの機器は未実装で失敗（`-DSGNANO_MOUSE_CTRL_POLL=ON` で残したが既定 OFF） |
| **バッファ制御レジスタを PID 反転して書き直す** | **復帰する。これが対処** |

#### 対処: 黙ったら割り込み EP を張り直す（`usbkbd.c` の `hid_kick_check()`）— **既定は無効**
**【重要】これは「止まる機器」専用の劇薬で、止まらない機器に使うと逆に1レポートも来なくなる。**

| 機器・構成 | 張り直しなし | 張り直しあり |
|---|---|---|
| `093A:2510`（ハブ1段） | 1〜4レポートで停止 | **正常**（効率0.98） |
| `045E:0083`（ハブ2段カスケード） | **正常**（数千レポート連続） | **`reports=0`。何も来ない** |

→ **既定 `SGNANO_HID_KICK_MS=0`（無効）**。止まる機器に当たったときだけ
`-DSGNANO_HID_KICK_MS=20` でビルドするか、実行中に **`Z` キー**で入れる（`z` は1回だけ張り直し）。
- **PID を反転させる**のが正しい。こちらが勝手に張った転送をドライバは知らないので
  `next_pid` が1つずれたまま進み、レジスタの現在値を反転するとちょうど本来の次の PID になる。
- **間隔は 20ms**。実測（レポート数 / 張り直し回数）: 20ms=0.98 / 10ms=0.20 / 4ms=0.077 /
  レポート受信の直後=完全に固着。詰めるほど悪化するのは、まだ届いていない転送を取り下げるため。
- **書き方はデータシート §4.1.2.5.1 "Concurrent access" の手順に従うこと**:
  ① AVAILABLE **以外**を先に書く ② 3 clk_usb ぶん待つ ③ AVAILABLE を立てる。
  待ちは clk_sys 302.4MHz なので 3 clk_usb ≒ 19 clk_sys。余裕を見て 32 サイクル。
  **TinyUSB 本体の `busy_wait_at_least_cycles(12)` は 125MHz 前提で、ここでは足りない。**
  ドライバの割り込みが同じレジスタを触るので、この3手順は割り込み禁止で囲む。
  手順を守らない版では、カスケードで**マウス・キーボード・ハブのステータス EP が全部同時に**止まった。

#### 【重要】ハブ2段カスケード + ロースピードのマウスは不安定（2026-09-25 実測）

### 【重要】ハブ越しロースピードの張り直しで踏んだ3つの罠（2026-09-25、すべて修正済み）
1. **`Data Seq Error` で panic して再起動していた**。`hcd_rp2040.c` はシーケンスエラーを受けると
   `panic("Data Seq Error")` で止まる。PID 反転をすると時々これが起きる。PID が合わないパケットは
   ハードウェアが捨てるだけなので、**`USB_INTE_ERROR_DATA_SEQ` を止めて回数だけ数える**
   （`usbkbd_seq_err`、`U` で見える）。本物のホストも再送で回復する事象であって、止まる理由ではない。
2. **レポート長が縮んだまま戻らなくなる**。転送後の `buf_ctrl` の LEN には**受信した長さ**が入る。
   張り直すときにそれを引き継ぐと、一度短いレポートを受けた時点で以後ずっと短いまま。
   実機で 4バイトのマウスが 3バイトに縮み、**ホイールが読めなくなった**。必ず要求長へ戻すこと。
3. **同じマウスが二重登録される**。ハブのポートが起動時に揺れると `addr=1` と `addr=3` の両方が残る。
   最初にマウントされたほうを覚えていると、実際に喋っているのは別のアドレスで、
   張り直しも生死確認も空振りする。**レポートが届いたアドレスへ乗り換える**（`usbmouse_rebind()`）。

### 【重要】機器が減ったまま戻らないときの作り直し（2026-09-25）
ハブ経由だと**キーボードが勝手に外れる**ことがある（ハブがポートの切断を報告する）。
マウスが残っていて `mounted_n != 0` なので、従来の「全滅したら作り直す」は働かない。
物理的に挿さっていてもハブが再接続を報告しないことがあり、**抜き差しするまで戻らない**。
→ **同時マウント数が最大より減ったまま5秒たったら、一度だけ作り直す**（`SGNANO_USB_DROP_MS`）。
本当に抜かれた場合に繰り返さないよう、実行前に基準を今の数へ下げる。手動は `R` キー。

### 【重要・2026-09-25 原因特定】カスケードでバス全体が死ぬのは「制御転送の詰まり」
ハブ2段カスケードで一定時間後にすべての HID が黙る件の正体は、
**制御転送（EP0）が1本返ってこなくなり、TinyUSB のホストスタックが詰まること**。
`tuh_control_xfer()` は1本ずつしか出せず、**非同期の制御転送にはタイムアウトが無い**。
返ってこないと以後どの制御転送も出せず、列挙もハブのポート監視も進まなくなる。

#### 決定的だった観測（`U` キー / `Q` キー）
| 観測 | 意味 |
|---|---|
| `[probe] addr=7: could not start (control busy)` が全アドレスで出る | **EP0 が永久に busy** |
| パッドとキーボードが `tuh_mounted()` で false | 列挙が完了していない |
| `[hw] sof 448 -> 451 (running)` | **バスのフレーミングは生きている** |
| `[hw] ... irqs=147` が凍結、`ints=0` `buf_status=0` | USB 割り込みが1本も来ない |
| エンドポイントは `avail=1` で armed | ハードは待っているだけ |
- `R`（`tuh_deinit`+`tuh_init`）で確実に戻るのは、この状態が全部作り直されるから。
- ロースピード機器の有無とは無関係（マウスを抜いても起きた）。**カスケード特有の症状。**

#### 対処: 制御転送が出せるか毎秒試して、詰まったら作り直す（`stuck_check()`）
**1秒ごとに機器記述子の読み出しを1本出す**。連続5回出せない（または返ってこない）なら
詰まったと判断して `host_restart()`。副作用が無く、毎秒1本ぶんの帯域しか使わない。
- **操作の有無に依存しないのが利点**。HID のレポートは触らないと来ないので、
  「レポートが来ない」では停止と無操作を区別できない（`SGNANO_USB_IDLE_RESTART_MS` の限界）。
- `-DSGNANO_USB_STUCK_CHECK_MS`（既定1000）/ `-DSGNANO_USB_STUCK_MAX`（既定5）。
- `U` の `wedged=N` で作り直した回数が分かる。
- **実測（2026-09-25、ハブ2段 + パッド + キーボード）**: 起動時に1回 `wedged=1` が出て復帰し、
  以後45秒以上安定。以前は数十秒で必ず死んでいた。

### 【重要】キーの自動リピートには上限が要る（2026-09-25）
USB キーボードは**状態が変わったときだけ**レポートを送る。押しっぱなしの間レポートは来ない。
つまり「離した」を取りこぼすと、こちらのリピートは**永久に打ち続ける**。
実測（ハブ2段）: 90秒たっても毎秒26回 `1` を出し続けた（`kbd_reports` は増えないまま）。
→ 新しいレポートが 5秒（`SGNANO_KEY_REPEAT_MAX_MS`）来なければリピートを打ち切る。
本当に押しっぱなしでも止まるが、押し直せばよいので取りこぼしより害が小さい。

### N キーロールオーバー（2026-09-26）
ブートプロトコルのレポートは仕様で「修飾キー + 予約 + キーコード6個」と決まっており、
**同時に6キーまで**しか取れない。多くのキーボードは**2本目の HID インタフェース**に
全キーのビットマップを持っていて、そちらなら同時押しの数に制限がない。

#### 実機 `258A:0016` の2本目（227バイトの記述子。レポートIDで7種類を多重化）
| ID | 用途 | 中身 |
|---|---|---|
| 1 | System Control | 電源・スリープ・ウェイク（Usage 0x81〜0x83 の3ビット） |
| 2 | Consumer Control | 音量・再生など。16ビットのコード1個（Usage 0〜0x2FF） |
| 3 | ベンダ独自 | 入力3バイト |
| **4** | **NKRO キーボード** | Usage 0x04〜0x70 を **120ビットのビットマップ**で送る |
| 5 / 6 | ベンダ Feature | 5バイト / **1031バイト**（ファーム更新やマクロ設定用か） |
| 7 | マウス | ボタン5個、X/Y 16ビット、ホイール、水平ホイール(AC Pan) |
EP が16バイトなのは ID 4 のため（レポートID 1 + ビットマップ15バイト）。
**「使っていない」だけで「無用」ではない**ので、この EP を節約対象にしてはいけない。

#### 実装（`usbkbd.c` の `handle_nkro()`）
```
85 04 / 05 07 / 19 04 29 70 / 75 01 95 78 / 81 02
-> [0]=0x04、[1..15] が 120 ビット。ビット i が Usage 0x04 + i（1バイト目の bit0 が 'a'）
```
- 立ち上がったビットだけを新規押下として拾う（前回のビットマップと比較）。
- **修飾キーはビットマップに含まれない**（0xE0〜0xE7 は 0x70 より外）。
  Shift/Ctrl は**ブート側のレポートから借りる**（`nkro_mod`）。
- **両方のインタフェースが同時に報告する。** NKRO を一度でも見たら
  ブート側のキーは使わない（`nkro_active`）。使うと二重入力になる。
- **【重要】リピートの打ち切り判定は、2本目のインタフェースの到着時刻も見ること。**
  ブート側だけ見ていると「レポートが来ていない」と誤判定してリピートを切ってしまう。
- ホストを作り直したら `nkro_active` を戻す（機器が変わるかもしれないので判定し直す）。
- `U` に `NKRO: active/not seen`、インタフェース番号、同時押しの最大数を出す。

#### 実機で確認（2026-09-26）— **11キー同時押しまで正しく取れる**
最大を更新したときだけビットマップと Usage 一覧を出すようにして計測した
（押した瞬間にこちらが記録している必要がなくなる。これが決め手だった）。
```
 3 keys: 00 00 00 20 02 00 02 ...  usages 21 25 35
 6 keys: 10 00 00 21 0a 00 02 ...  usages 08 1c 21 25 27 35
 7 keys: 10 20 00 21 0a 00 02 ...  usages 08 11 1c 21 25 27 35   <- ブートの限界(6)を突破
11 keys: 96 20 80 21 0a 00 02 ...  usages 05 06 08 0b 11 1b 1c 21 25 27 35
```
ビットマップと Usage が整合し、段階的に増やすと前のキーを保ったまま加わる。
`U` の `NKRO: active (inst=N, reports=N, max keys held at once=N)` で確認できる。

**【測り方の工夫】「最大を更新したときだけ出す」**。
実機の操作とこちらの記録の窓が合わず、何度も取り逃していた。
**累積の最大値を持たせて、更新時にだけ出力する**ようにしたら一度で取れた。
人の操作を待つ計測では、窓を広げるより**状態を残す**ほうが確実。

### キーボードの LED（2026-09-25）
LED は HID の **OUTPUT レポート1バイト**で指示する（bit0=Num, bit1=Caps, bit2=Scroll,
bit3=Compose, bit4=Kana）。`tuh_hid_set_report()` = 制御転送なので、他の転送と競合したら
50ms 後に送り直す。`usbkbd.c` の `leds_task()`。
- **ロックキーの押下で該当ビットを反転する**。LED の状態を持つのはホスト側で、
  キーボードは自分では変えない（USB の決まり）。`lock_key()` でロックキーは文字にせず LED だけ変える。
- **Caps Lock は Shift と一緒に押されたときだけ反転する**（日本語配列の作法。単独では何も起きない）。
  Num Lock と Scroll Lock は単独で反転する。
- **【重要】マウント直後に勝手に SET_REPORT を出してはいけない。** 最初は `leds_sent` を
  `leds_want` と一致させておき、**ロックキーが押されるまで何も送らない**。
  列挙の直後に制御転送を1本投げる実装にしていたら、ハブ2段カスケードで
  **その後バスが黙る**現象が出た（`reports=2` のまま23分）。やめたら直った
  （キーボードのレポートが毎秒流れ、LED も正常に切り替わる）。
  つながり直したときも送り直さない（`leds_sent = leds_want`）。
- API: `usbkbd_set_leds(mask)` / `usbkbd_leds()`。`E` キーで巡回（N → C → S → 全部 → 消灯）。
- `U` の `leds=NCS(送れた回数/失敗回数)` と、画面のキーボード行の `led NCS` で状態が見える。

### 目標構成に向けた設定（2026-09-25）
キーボード + マウス + パッド2 + USBメモリ2 = **6台**（+ ハブ2台）を想定して広げた。
- `CFG_TUH_DEVICE_MAX` 4 → **6**（`usbh.c` の `TOTAL_DEVICES = DEVICE_MAX + HUB` なので
  **ハブはアドレス7,8**に移る。`U` の表示もそれに追随する）
- `CFG_TUH_HID` 6 → **10**（キーボード2 + マウス2 + パッド2台ぶん）
- **USBメモリを読むには `CFG_TUH_MSC` が要る**（今は 0 なので列挙されるだけで使えない）。

### 【解決・2026-09-25】パッドが動かないのは「データトグルのずれ」だった
**ゲームパッドはデータトグルがずれた状態で始まることがある。** 機器は正しく報告しているのに、
ホストが逆の PID を待っていて受け付けないため、1レポートも届かない。
→ **20ms ごとに PID を反転して割り込み EP を張り直す**と噛み合い、正常に流れ出す。
パッドとして認識した機器には**自動で適用**する（`usbkbd_kick_enable_forced()`）。

#### 決め手になった実験
epx（制御用 EP）から IN トークンを**1ms 間隔で連続**に投げ、**PID を毎回反転**した
（`usbkbd_epx_in_burst()`、`g` キー）。**88回目でデータを捕まえた**:
```
[epx] burst: GOT DATA after 88 tries (8 bytes): 80 7f 80 7f 38 00 00 ff
```
解読すると X/Y/Z/Rz=中央、ハット=中立、**ボタン1と2が押されている**。
記述子から求めた並びと完全に一致し、**機器も解析も正常**と確定した。
1回ずつ問い合わせる実験では NAK しか返らず取りこぼしていた
（HID は状態が変わった瞬間にしかレポートを作らないため、粗いサンプリングでは捕まらない）。

- 実証: F310 で **0件 → 306件**。起動しただけで流れ、ボタンもハットも正しく取れる。
- マウス（ハブ越しロースピード）で作った張り直しと**同じ仕組み**。症状も同じだった。
- **張り直しは「止まる機器」専用**という位置づけは変わらない。既定は無効で、
  パッドと「ハブ越しロースピード」のときだけ自動で入る。`Z` キーで手動でも入る
  （対象が未設定なら、いちばん長く黙っている HID を自動で選ぶ）。

### DualShock 3 対応（2026-09-25）
DS3 は**有効化コマンドを受け取るまで入力レポートを一切出さない**。`usbpad.c` の `ds3_*`。
1. `SET_REPORT(Feature, レポートID 0xF4, {0x42, 0x0C, 0x00, 0x00})` で動作モードに入れる
2. 続けて出力レポート（ID 0x01、48バイト）で**振動を停止し LED1 を点灯**する
   （初期化しないと振動モーターが回りっぱなしになることがある。実機で発生した）
- マウント時に自動で送る（`-DSGNANO_PAD_DS3_AUTO=OFF` で切れる）。`J` キーで手動やり直し。
- レポートの解読は**汎用の記述子解析がそのまま使える**（`49 bytes id=1 buttons=19@8`、
  軸は X@40 Y@48 Z@56 Rz@64）。生レポートの `01 00 00 00 00 00 82 81 84 80 ...` と一致する。
- **実測: 起動しただけで 1416 件のレポートが流れる。**

#### 【重要】暴走しない仕掛け
応答しない機器（DS3 の ID を名乗る PS2 変換アダプタ等）に当たると制御転送が返ってこない。
上限3回・時間切れ2秒・再試行間隔3秒を設けている。これが無いと
「詰まり検出 → ホスト作り直し → 再マウント → また送る」の堂々巡りになる（実測で発生）。
- **【重要】「制御転送が塞がっていて出せなかった」は試行回数に数えないこと。**
  列挙の直後は塞がっているのが普通で、数えると相手が応答する前に上限を使い切る（実測で発生）。
  塞がっていたときは 200ms 後に出し直し、**実際に出せたものだけ**を数える。
- マウント直後は 500ms 待ってから最初の送信を試みる（列挙が落ち着くのを待つ）。
- レポートが流れ始めたら送るのをやめる。

#### 振動
出力レポート（ID 0x01、48バイト）の `[1][2]` が小さいモーター（継続時間・オンオフ）、
`[3][4]` が大きいモーター（継続時間・強さ 0..255）。`0xFF` = 連続。
- `,` キーで 弱 → 最大 → 小モーター → 両方 → 停止 と巡回。`.` キーでデモ（間に停止を挟む）。
  `J` は振動も止める。画面28行目に指示内容を出す（感触と見比べられるように）。
- **【重要】デモで段階を進めるときは、前の送信が完了するまで待つこと。**
  待たずに進めると送信を飛ばし、その段階の設定が届かない（実測で10段階中3回しか送れなかった）。

### パッド2台（2026-09-25）
`USBPAD_MAX` は元から2だが、**台数が増えて初めて出る不具合が3つ**あった。いずれも修正済み。
画面は **26/27行目 = パッド0、28/29行目 = パッド1**、ログは `[run] pad0:` / `[run] pad1:`。

1. **DS3 の有効化がもう1台に邪魔される**。`usbpad_task()` の「もうレポートが流れているなら
   有効化は不要」という判定が **`pads_have_reports()`（どれか1台でも）** を見ていた。
   F310 を同時につなぐと、そちらの数件で止まってしまい **DS3 の有効化が一度も送られず**、
   DS3 は永久に 0 件のままだった。**その機器自身のレポートだけを見る**（`usbpad_has_reports(daddr)`）。
2. **張り直しの対象を1つしか持てなかった**（`kick_daddr` / `kick_inst` が単一）。
   2台目を登録すると1台目を上書きして、片方が張り直されない。
   **インスタンスごとの配列**（`kick_on[]` / `kick_daddr_of[]` / `kick_len_of[]`）にした。
3. **DS3 に張り直しが入ってしまう**。有効化前は 0 件が正常なのに「止まっている」と誤判定し、
   毎秒100回の空振りに加えて機器を黙らせる。

#### 【重要】張り直しを入れるかは「機器で分ける」。猶予では間に合わない
一度は「猶予のあいだレポートが来なければ入れる」という汎用の判定にしたが、**これは失敗だった**:
- **F310 はマウント直後に入れないと間に合わない**。3.5秒待つ版では **2件で固着したまま、
  以後いくら張り直しても復帰しない**（`kick` が毎秒50回走っているのに 0 件のまま）。
- 「1件でも来たか」で見るのも駄目。F310 は**数件だけ出して止まる**ので自力で流れていると誤判定する。
→ **DualShock 3 なら入れない、それ以外のパッドならマウント直後に入れる**、と機器で分ける
（`usbpad_is_ds3()`）。DS3 は有効化さえ通れば自力で毎秒100件流れるので張り直しは不要。

#### 実測（2026-09-25、良品ハブ `05E3:0606` に F310 + DS3 + キーボード）
```
[usb]  addr=1 VID=046D PID=C216 speed=Full     <- F310
[usb]  addr=2 VID=054C PID=0268 speed=Full     <- DualShock 3
[usb]  addr=3 VID=258A PID=0016 speed=Full     <- キーボード
[usb]  addr=7 VID=05E3 PID=0606 speed=Full  [HUB]
[run] pad1: 054C:0268 addr=2 reports=2520      <- 毎秒100件で安定
```
- **4台とも素早く列挙され、DS3 とキーボードは正常に動く。** 映像は `underrun=0` `fifo_stall=0` `recover=0`。
- **F310 だけが 2 件で止まったまま**。今朝は同じハブ・同じ張り直しで 665 件流れていたので、
  ソフトではなく **F310 自身の状態か電源**を疑う段階。**挿し直しから試すこと。**

### 【重要・2026-09-26 訂正】ホストのエンドポイントの枠は **15本**（8本ではない）
RP2350 のホストは **EP0 以外に15本**のエンドポイントを扱える。
```c
io_rw_32 int_ep_addr_ctrl[15];                              // ハードウェア
#define USB_HOST_INTERRUPT_ENDPOINTS (USB_NUM_ENDPOINTS - 1) // = 15
static struct hw_endpoint ep_pool[1 + PICO_USB_HOST_INTERRUPT_ENDPOINTS];  // TinyUSB
```
**「8本まで」と一日書いていたのは誤りで、原因は自分の診断コードだった。**
`usbkbd.c` の走査が `for (i = 0; i < 8; i++)` になっており（8か所）、そのせいで
1. `U` の `[hw] intep` 一覧が **8本までしか出ず**、満杯に見えた
2. **9本目以降にいる機器は、張り直しも停止も空振りしていた**（`rearm_ep()` が見つけられない）
→ `USBKBD_INT_EPS`（= `USB_HOST_INTERRUPT_ENDPOINTS`）に直した。

**【教訓】「観測された上限」は、観測の側の上限かもしれない。** 今日の別件
（バナーの `no keyboard` を「認識失敗」と誤読）とまったく同じ轍。
**まず観測の仕方を疑うこと。**

#### 種別に関わらず1本ずつ取る
EP0 以外のすべてのエンドポイントがこの枠を使うので、**バルクも1本**。
USB メモリは IN + OUT で **2本**。`U` の `ep_ctrl` の bit27-26 が種別
（0=制御、1=アイソクロナス、**2=バルク**、**3=割り込み**）。USB メモリは `a8...` = バルクだった。

#### 【実測・2026-09-26】7台 + ハブ3段 = **14/15 本**で同時動作
```
addr=1  ABCD:1234  USBメモリ 480MB      intep1/2   (OUT+IN)
addr=2  258A:0016  キーボード            intep5/6   (IN x2、2本目は未使用)
addr=3  13FE:3600  USBメモリ 1914MB     intep7/8
addr=4  046D:C216  F310                 intep9     (OUT は開かない)
addr=5  045E:0083  マウス(Low,ハブ越し)  intep10    (pre=1)
addr=6  13FE:3600  USBメモリ 1914MB     intep11/12
addr=7  054C:0268  DualShock 3          intep13    (OUT は開かない)
addr=9/10/11       ハブ3段              intep0/3/4
```
映像は `underrun=0` `fifo_stall=0` `recover=0` で無傷。
**8台目（Switch Pro、IN+OUT で2本）を足すと 16 本で1本足りない。** 空ける手:
1. **ハブを2段にする**（1本）。配線だけで済む。
2. **キーボードの2本目のインタフェース**（`protocol=none`、16バイト、未使用）を開かない（1本）。
3. USB メモリを「使うときだけ開く」（最大で台数x2 - 2 本）。

### Nintendo Switch Pro コントローラ（`057E:2009`、2026-09-26 完了）
`usbpad.c` の `sw_*`。**ハンドシェイク・入力の解読とも実機で動作**。
毎秒125件、40秒間で再列挙・詰まりとも0、映像は `underrun=0` `fifo_stall=0` `recover=0`。

#### ハンドシェイク（割り込み OUT = EP 0x01 へ、**レポートID つきの64バイト**）
**出力レポートは番号つきで、いずれも63バイト固定**（記述子の末尾に出ている）:
```
85 01 ... 95 3f 91 83   レポートID 0x01（副命令つき）
85 10 / 85 80 / 85 82   それぞれ Output
```
したがって送るのは「先頭がレポートID、全体で64バイト」。
**2バイトの短いパケットで送っていたときは、割り込み OUT が永久に完了しなかった。**

順に `80 01`（状態）→ `80 02`（ハンドシェイク）→ `80 03`（ボーレート）→ `80 02` →
**`80 04`（USB を強制。これが無いと HID の時間切れで接続し直す）**、
最後に レポートID 0x01 の副命令 `[1]=連番 [10]=0x03 [11]=0x30` で入力形式をフルにする。
間隔は 60ms。上限つきの再送と、制御転送への切り替えも入れてある。

#### 入力レポート 0x30 の解読（記述子の解析では読めない）
記述子の解析結果（`64 bytes id=48 buttons=10@0`）は**当てにならない**。実際の並び:
```
30 a8 91 00 80 00 00 f8 7f 00 f8 7f
│  │  │  └─┬──┘  └───┬──┘ └───┬──┘
│  │  │  ボタン3B   左スティック 右スティック（12bit x2 の詰め込み）
│  │  └ 電池と接続（0x91 = USB給電・満充電）
│  └ タイマ
└ レポートID 0x30
```
- `[3]` 右: bit0=Y 1=X 2=B 3=A 4=SR 5=SL 6=R 7=ZR
- `[4]` 共通: bit0=- 1=+ 2=右スティック押込 3=左スティック押込 4=HOME 5=キャプチャ
- `[5]` 左: bit0=下 1=上 2=右 3=左 4=SR 5=SL 6=L 7=ZL
- 12bit の展開: `x = r[6] | ((r[7]&0x0F)<<8)`、`y = (r[7]>>4) | (r[8]<<4)`。中央は 2048。
- **十字キーはボタンとして来る**ので、ハット（0=上、時計回り、8=中立）に変換する。
- **Y は上が大きい**ので反転して他機種に揃える。
- こちらのボタンの並び: bit0=B 1=A 2=Y 3=X 4=L 5=R 6=ZL 7=ZR 8=- 9=+ 10=左押込 11=右押込
  12=HOME 13=キャプチャ
- 実測: `btn=0000000a hat=2`（A+X、十字右）、`X=-107 Y=+67 Z=+32 Rz=-122`。すべて追従。

#### 【重要】手順待ちの機器に張り直しを入れてはいけない（本日4度目の同じ誤り）
**これが動かなかった真の原因。** 張り直し（kick）が Switch Pro に入っていたため、
毎秒100回 PID を反転することになり、**割り込み OUT も制御転送も止まっていた**。
ログの順番が決定的だった:
```
[hid] will re-arm addr=1 ... while it is silent for 20 ms
[usb] control probe did not return (1/5)        <- 直後に制御転送が返らなくなる
```
**有効化やハンドシェイクを待っている機器は「黙っているのが正常」。**
外したとたん、割り込み OUT の完了もハンドシェイクの完走も、入力の受信も一度に通った。
→ `usbpad_needs_setup()`（DS3 と Switch）を張り直しの対象から外す。
張り直しが要るのは F310 のような「データトグルがずれて始まる」機器だけ。

#### 幽霊の枠を掃除する
Switch Pro は時々自分で接続し直すが、**取り下げの通知は来ない**ので、前のアドレスの枠が
「つながったまま固まった」状態で残る。実測で同じパッドが3枠を占めた（addr=1/5/6）。
→ マウント時に「同じ VID/PID で 2秒以上レポートが来ていない枠」を外す（`PAD_STALE_MS`）。
ハンドシェイクが通れば接続し直し自体がほぼ起きなくなる。

#### 外れた対策（記録）
- `tuh_edpt_abort_xfer()` で詰まった割り込み OUT を取り下げる → **システムごと停止**し、
  ウォッチドッグが毎回再起動した。RP2350 の HCD の中止処理は割り込み駆動の EP には使えない。
- 制御転送で送るとき `wValue = 0x0200`（レポートID 0）にしていた → 機器が受け付けない。
  正しくは `0x0200 | レポートID`。

### パッド3台の同時接続（2026-09-26）
セルフパワーの複合ドック `2109:2817` に **Switch Pro + DualShock 3 + F310** を接続。
**Switch と DS3 の2台は完全に動作**する。列挙・ハンドシェイク・有効化とも一度で成功し、
幽霊の枠・詰まり・作り直しはいずれも0。映像は `underrun=0` `fifo_stall=0` `recover=0`。
```
[run] pad0: 057E:2009 addr=1 reports=2275  <- Switch Pro、毎秒125件
[run] pad2: 054C:0268 addr=3 reports=1762  <- DualShock 3、毎秒100件
[run] pad1: 046D:C216 addr=2 reports=0     <- F310 だけ動かない
```

#### F310 が動かないのは機器側（ポートの入れ替えで確定）
**F310 と DS3 のポートを物理的に入れ替えた**ところ、結果がそっくり入れ替わらなかった:
| | 入れ替え前 | 入れ替え後 |
|---|---|---|
| F310 が居たポート | F310 = 0件 | **DS3 = 1762件、正常** |
| DS3 が居たポート | DS3 = 正常 | **F310 = 0件** |
**どちらのポートでも DS3 は動き、F310 は動かない。** ハブ・ポート・段数ではなく F310 側の問題。
- 張り直し（kick）の有無は無関係（切っても入れても2件のまま）。
- バスの混雑も無関係（`X` キーで他の機器の割り込み IN EP を全部止めて F310 だけにしても2件）。
- 挿し直しでも復帰しない。
- **直結でも動かない**（2026-09-26）。ハブを介さず基板に直結しても 2 件で固着。
  つまり「ドックとの相性」ではなく **F310 側**。

##### F310 の状態（直結で計測、すべて実施済み）
| 調べたこと | 結果 |
|---|---|
| 列挙・記述子の解析 | **正常**（`8 bytes buttons=12@36 hat=yes` 4軸、値も妥当） |
| epx から IN トークンを3000回 | **全部 NAK**（`nak=3000 timeout=0 other=0`）= **機器は生きている** |
| 張り直し（20ms、PID反転） | 毎秒50回動作、レジスタも期待どおり（`buf_ctrl 7420 -> 5420`）。**効果なし** |
| 張り直しを切る | 変わらず 2 件 |
| 他機器の割り込み EP を全部止める（`X`） | 変わらず 2 件 = バス混雑ではない |
| スティックを動かし続ける | 変わらず 2 件 = 無操作だからではない |
| `SET_PROTOCOL(report)` | **OK**（制御転送は健全） |
| `SET_IDLE(128ms)` | **OK**（同上） |
| 挿し直し | 復帰しない |

**制御転送はすべて通るのに、割り込み IN だけ永久に NAK する。**
**同じ F310 は同じ日の朝、同じ張り直しで 665 件流れていた。**
→ 残るのは機器の内部状態か故障。**PC につないで確かめるのが最速**（`docs/DEVELOPMENT.md` の切り分け手順2）。

#### 【重要】割り込みエンドポイントが8本を使い切る
【訂正・2026-09-26】**8本は誤り。枠は15本**（「ホストのエンドポイントの枠は 15本」の節）。8本に見えたのは診断コードの走査が8本で打ち切っていたため。
パッド3台 + ハブ2段で **ちょうど 8/8**。うち**2本は使われない OUT**（DS3 と F310）:
```
intep0 hub7  IN            intep4 addr=2 ep2 OUT  DS3  <- 未使用
intep1 hub8  IN            intep5 addr=2 ep1 IN   DS3
intep2 addr=1 ep1 IN  Switch    intep6 addr=3 ep1 IN   F310
intep3 addr=1 ep1 OUT Switch    intep7 addr=3 ep2 OUT  F310 <- 未使用
```
DS3 の出力は制御転送で送っているので割り込み OUT は要らず、F310 も OUT を使わない。
**使わない OUT を開かないようにすれば2本空く**（`hcd_edpt_open` の `--wrap` で可能）。
目標構成（キーボード + マウス + パッド2 + USBメモリ2）にはこの節約が要る。
割り込み OUT が本当に要るのは Switch Pro のハンドシェイクだけ。

#### 切り分けに使った道具（`X` キーを変更）
`X` は「レポート数がいちばん少ないパッドを残して、他の割り込み IN EP を止める」に変えた。
**繋ぎ替えずに「他の機器が流しているせいで動かないのか」を確かめられる。**
復旧は `R`（ホストの作り直し）。

### 【重要】TinyUSB のバグ: ハブ記述子の要求に種別を入れていない（回避済み・2026-09-25）
`hub.c` はハブ記述子を要求するとき **`wValue = 0`** を送る:
```c
.bRequest = HUB_REQUEST_GET_DESCRIPTOR,
.wValue   = 0,                  // <- 本来は 上位バイトに種別 0x29 が要る
```
USB 2.0 の仕様では wValue の上位バイトが**記述子の種別**で、ハブ記述子は **0x29**。
Linux は必ず `USB_DT_HUB << 8` を入れている。**寛容なハブは 0 でも答えるが、厳密なハブは STALL する。**
- 症状: 列挙が `config_set_port_power 286: ASSERT FAILED`（= ハブ記述子の取得が失敗）で止まり、
  **ハブ自身がマウントされない**。ぶら下がった機器も当然見えない。
  `TU_ASSERT` なので TinyUSB は再試行せず、抜き差しするまで直らない。
- **ハブによって動いたり動かなかったりする**ので、機器の相性に見えてしまう。
  実際「このドックは動かない」と一度諦めていた（2026-09-24）。

#### 回避（`src/input/usbfix.c`）— SDK は触らない
`tuh_control_xfer()` を `--wrap` で横取りし、
「クラス要求・宛先=デバイス・IN・GET_DESCRIPTOR・wValue=0・wIndex=0」のときだけ
**`wValue` を `0x2900` に差し替える**。制御転送は同時に1本しか走らないので、
差し替え後の setup は静的な1個で足りる。回数は `usbfix_hub_desc_fixes` で数えている。

#### 実測（2026-09-25）
セルフパワー（PD給電）の複合ドック `2109:2817`（VIA Labs VL817）で、
**修正前はハブすら列挙できなかったものが、修正後は配下も含めて全部見えるようになった**:
```
[usb]  addr=1 VID=258A PID=0016 speed=Full      <- キーボード
[usb]  addr=2 VID=0BDA PID=8153 speed=Full      <- Realtek USB LAN
[usb]  addr=3 VID=2109 PID=8817 speed=Full      <- カードリーダー等
[usb]  addr=7 VID=2109 PID=2817 speed=Full  [HUB]
[usb]  addr=8 VID=1A40 PID=0101 speed=Full  [HUB]
```
映像は `underrun=0` `fifo_stall=0` `recover=0`、`reinit=0` `wedged=0` `seq_err=0`。

**【教訓】「このハブは相性が悪い」で片付ける前に、`-DSGNANO_USB_DEBUG=1 -DSGNANO_USB_LOG_RAM=ON`
でログを出すこと。** 今回は1回の観測で `config_set_port_power 286: ASSERT FAILED` が出て、
そこから仕様を当たるだけで原因にたどり着いた。昨日は同じ機器を「複合デバイスは諦めます」で
終わらせていた。

### 【重要】TinyUSB のバグ: epx の最大パケットサイズの使い回し（回避済み）
`hcd_setup_send()` は epx（全機器で共用する制御用エンドポイント）を毎回初期化し直すが、
**最大パケットサイズに「前回の機器の値」を使い回す**:
```c
_hw_endpoint_init(ep, dev_addr, 0x00, ep->wMaxPacketSize, 0, 0);
```
**EP0 のサイズが異なる機器が混在すると、制御転送が壊れる。**
- 実測: キーボード（EP0=64）と DualShock 3 を同じハブに繋ぐと、DS3 への
  `GET_DESCRIPTOR` が **0 バイト**を返し、振動や LED の指示も届かない。
  どちらか1台だけなら正常。**ユーザーが「キーボードを繋いでいると失敗する」と
  気づいたのが決め手だった。**
- 列挙中は `usbh_edpt_control_open()` が機器ごとに呼ばれるので正しく動く。
  **列挙が終わったあとの制御転送だけが壊れる。**

#### 回避（`src/input/usbfix.c`）— SDK は触らない
リンカの `--wrap` で横取りする（`CMakeLists.txt` の `target_link_options`）:
- `hcd_edpt_open` … EP0 を開くときのサイズを機器ごとに覚える
- `hcd_setup_send` … 送る直前に、その機器のサイズで epx を開き直す

`hcd_edpt_open()` は `tu_edpt_validate()` を通らないので制御エンドポイントの記述子でも
受け付ける（`tuh_edpt_open()` は `default: return false;` で弾くので使えない）。
開き直しは epx が止まっている前提の場所（本来 `assert(!ep->active)` がある）で行うので安全。
- **実測: 回避後はキーボードと DS3 が同居しても両方 `OK (18 bytes)`。振動も届く。**
- TinyUSB 側で直ったら、`--wrap` を外すだけで元に戻せる。`U` の `ep0_reopens` で回数が見える。

### 診断の道具
- `U` キー … HID インタフェースごとに `xfer=busy`（転送中＝正常）/`FREE`（流れが途切れた）と
  最後のレポートからの経過、さらに `[hw]` 行でホストのインタラプト EP のレジスタ
  （`int_ep_addr_ctrl` / `ep_ctrl` / `buf_ctrl` の `avail`）を並べる。
- 毎秒の `[run] hid:` 行 … レポート数・座標・ホイール・ボタン・`rearm=N/M`・`ctrl/ok/fail`。
- `Q` キー … マウスに制御転送（GET_DESCRIPTOR）を1回投げる。**機器が生きているかの確認**。
- `G` キー … GET_REPORT(Input) を1回投げる。制御転送でレポートを読めるかの確認。
- `R` キー … USB ホストスタックを作り直す（止まった機器を立て直す最後の手段）。
- `-DSGNANO_HID_MOUSE_ONLY=ON` … マウス以外の HID を polling しない（切り分け用）。
- `-DSGNANO_MOUSE_CTRL_POLL=ON` … ハブ越しロースピードのマウスを GET_REPORT で読む
  （手持ちの機器は非対応だったので既定 OFF）。
- `Z` / `z` キー … 割り込み EP を手で張り直す（`Z` は PID 反転あり、`z` はそのまま）。
- `U` キーの `[mouse]` 行 … レポート記述子の解釈結果、現在のプロトコル、生レポート、
  **値が0以外になったことのあるバイト位置**、見たレポート長、ホイールが動いた回数。
  「どこまで届いているか」を機器のせいにする前に確認できる。
- **レポートの流れが途切れたら要求し直す**（`tuh_hid_receive_ready()` で判定）。
  【重要】「一定時間レポートが来ない」で判定してはいけない。動かしていないマウスは
  転送を出したまま NAK で待っているのが正常なので、時間で見ると毎回誤検出する。

### 実測（2026-09-25、マウス直結・キーボードはハブ経由）
毎秒約100レポート（bInterval=10ms）。映像は `underrun=0` `fifo_stall=0` `recover=0`
`min_ready=25` `pair_max=56/56µs` で変化なし。
- アプリ時間 40µs -> **77µs**（マウスの2行を毎フレーム書くぶん）。窓は約1.47ms なので余裕は十分。
- グリフ展開 `glyph refresh max=25µs`（1フレーム 4〜6 セル）。上限64セルに対して軽い。


### 【重要・2026-09-27】NKRO への切り替えを「空のレポート」で行ってはいけない
**キーが1つも入らなくなる不具合があった。** 症状は「キーボードは列挙され LED も点くのに、
打鍵がまったく届かない」。

- `nkro_active` を **レポートID 0x04 が来たら無条件で** 立てていた。
- NKRO 側を使うと決めた時点で**ブート側のキーを捨てる**（二重入力を避けるため）。
- ところが接続直後に**全ビット0のレポート**が1件来ることがあり、それで切り替わる。
  その後 NKRO 側が黙ると、ブート側も捨てているので**入力が完全に死ぬ**。
- 見分ける目印は `U` の **`NKRO: active ... max keys held at once=0`**。
  「active なのに一度もキーを見ていない」＝空のレポートで切り替わった証拠。
- **対処: 実際にキーが押されているレポート（ビットマップが非ゼロ）を見て初めて切り替える。**
  代償は、最初の1打鍵だけ二重に入る可能性があること（ブート側と NKRO 側の両方が報告するため）。
  **入力が死ぬより害が小さい。**
- 実機で確認（2026-09-27、ドック + ハブ3段の構成）: 修正後は `NKRO: not seen` のまま
  ブートプロトコル（6キーまで）で**打鍵が正しく届く**。この構成では NKRO 側（inst=1）が
  134秒間沈黙しており、**黙っている側に賭けない**作りになったことが効いた。
  （2026-09-26 に11キー同時押しを確認したときは NKRO 側が生きていた。構成で変わる。）

### 【未解決】ハブ経由だと起動時にキーボードが列挙されないことがある
今回の構成（セルフパワードック + ハブ3段 + 光学ドライブ + LAN + カードリーダー）では、
**起動時にキーボードが列挙されず、`R`（ホストの作り直し）で毎回つながる**。
- 自動復帰の仕掛けは「**同時マウント数が最大より減ったまま5秒**」で働くので、
  **最初から出てこない機器は拾えない**。
- 当面は `R` で回避する。直すなら「起動から N 秒たっても期待した機器が居ないなら作り直す」
  のような、**増える方向の検出**が要る。

### 【元からの問題・2026-10-03】光学ドライブの列挙中にアドレスが尽き、ウォッチドッグで再起動を繰り返す
光学ドライブ `1132:4511` は1本のプラグにハブ・LAN・カードリーダー・光学を持つ複合機。起動直後の流れ:
1. 列挙が遅く、`reinit_check()` の「3秒たっても何もマウントされない」が**列挙の途中で**ホストを作り直す
2. 作り直しのたびに「Device Attach」が重なり、アドレスが回収されないまま尽きる
3. TinyUSB の `enum_request_set_addr 1612: ASSERT FAILED`（新しいアドレスが 0）
4. アプリのループが TinyUSB のイベント処理（`tuh_task_ext` -> `tu_fifo_read`）から抜けなくなる（映像は動き続ける）
5. ウォッチドッグの時間切れで再起動。まれに、その再起動でブートROM が止まる（QSPI の件）
- 突き止め方: ウォッチドッグを切ったビルドで止め、core0 の PC を止めずに12回読んだ（`DWT_PCSR`）。
  TinyUSB のログ（RAM のリング）は `mdw` ではなく `dump_image` で読み出した（アプリが止まっていて `u` キーが効かないため）。
- プローブがつながって C_DEBUGEN が立っていると、3 の assert で core0 が BKPT で止まる（ウォッチドッグなしのビルドで見えた）。
- 変更前のビルドでも同じ手順で再起動する（アロケータとは無関係）。
- **訂正**: C7 の確認で「`\`（TOC）の直後の `:` は黙って捨てられる」と書いたが、実際は
  `*** PANIC *** Can't continue xfer on inactive ep 81` で TinyUSB が panic し、ウォッチドッグで再起動していた。

#### 対処（2026-10-03、`src/input/usbwatch.c`）
1. **作り直しの判定でハブも数える**（`anything_mounted()`）。TinyUSB はハブに `tuh_mount_cb` を呼ばないので、
   `usbhost_mounted_n` だけ見ると、ハブの先を列挙している最中を「何もマウントされていない」と誤判定して3秒で作り直していた。
   これが連鎖の引き金。
2. **ハブだけの状態は 10 秒待ってから作り直す**（`SGNANO_USB_REINIT_HUB_MS`）。ハブの先の列挙が
   `process_enumeration` の assert で黙って失敗すると TinyUSB は再試行しないので、1 だけでは「ハブしか居ないまま」で止まる
   （40秒の記録5回中1回で発生）。ハブの先の機器は実測3〜5秒で載るので、10秒なら列挙の途中には割り込まない。
3. **詰まりの見張り（`stuck_check`）をハブだけの状態にも広げる**。相手の機器が居なければハブに制御転送を投げる。
- 測り方: 書き込み -> リセット -> 30〜40秒記録を繰り返し、再起動・作り直し・assert・マウントの数を数える。
  | | 再起動 | 結果 |
  |---|---|---|
  | 直す前（3回） | 2 / 0 / 2 | 3回中2回で再起動の連鎖 |
  | 1 のみ（8回） | 0 | 再起動は消えたが、ハブしか居ないまま止まる回がある |
  | **1〜3（6回）** | **0** | **6回ともキーボードと光学ドライブが載り、作り直しも0回** |
- 映像は `underrun=0 fifo_stall=0 recover=0 pair_max=55/57us` のまま。

### 【2026-10-04、積み残し】作り直しのあと、使えていたキーボードが戻らない → 入力機器が戻るまで作り直す
**症状**: ホストを作り直したあと（制御転送の詰まりの見張りや `R`）、キーボードが戻らないことがある。FDD は戻るので、

**対処（`usbwatch.c` の `usbwatch_enum_stall_check()`）**: **HID がマウントされたことのある機器**（VID/PID で覚える）が、
いない・列挙が止まったまま 12秒たったら作り直す。

- 同じ機器のために3回作り直しても戻らなければあきらめる。全体の上限 6回（揃った状態が60秒続いたら戻す）。
- 間隔の下限（8秒）で断られたら、もう一度待ってから頼む（すぐ頼み直してログが溢れたことがある）。
- 【注意】`tuh_mounted()` は SET_CONFIGURATION が通った時点で真になり、その先のクラスドライバの設定が失敗しても真のまま。
  (a) の判定には使えない（最初これで見逃した）。マウントの通知（`usbhost_mount_seen`）で見る。
- `U` の `enum_stall=N` で、この見張りが作り直した回数が分かる。

**実測（キーボードが載ったあと、`R` を10回）**: 試行の経過
| 版 | キーボードが戻った回数 | 備考 |
|---|---|---|

### 【2026-10-04】TinyUSB の `tuh_task()` が抜けなくなる（ウォッチドッグの再起動が連鎖する）
**症状**: ウォッチドッグの再起動のあと、続けて何回か起動が止まる（`W` の再起動で10回中1回ほど）。止まった起動の USB の
ログは毎回「機器を4台見つけたあと `process_enumeration 1496: ASSERT FAILED`」（構成記述子の全長が `CFG_TUH_ENUMERATION_BUFSIZE`
= 256 より長いと読めた）。止まった場所の印（`src/app/crumb.h`）は「描画待ちの中の `tuh_task()` の中」。
**原因（TinyUSB の作り）**: `tuh_task_ext()` は、列挙中（`_dev0.enumerating`）に来たほかのポートの「つながった」を列の後ろへ
回す。後回しが1つなら抜けるが、**2つ以上あると互いに回し合い、列挙が終わるまで抜けない**。列挙が TU_ASSERT で打ち切られると
`_dev0.enumerating` が立ったままになり、永久に抜けない。起動時はハブの先の機器がいっせいにつながるので後回しが2つ以上になりやすい。
`process_set_config 566`（積み残しの (a)）も同じく列挙を打ち切る。
**対処（`usbfix.c`、SDK は無改変）**: TinyUSB の assert のメッセージは `CFG_TUSB_DEBUG_PRINTF`（`usblog.c`）に届くので、
列挙の関数（`process_enumeration`・`enum_*`・`process_set_config`）の assert を合図に、列挙中の機器のハブとポート
（`hcd_devtree_get_info(0)`）について `DEVICE_REMOVE` を `hcd_event_handler()` へ渡す。これはその場で `_dev0.enumerating` を
下ろす（hub.c が切断を見つけたときと同じ経路）。ルートポート直結のときは何もしない（全機器が外れる）。`U` の `enum_released=N`。
- 実測: `W` の再起動20回で連鎖0回（assert は6回の起動で出たが、どれも先へ進んだ）。対策前は10回中1回
- 【注意】`SGNANO_USB_LOG_RAM=OFF` だと assert のメッセージが届かないので、この対処は働かない
- 【残る穴】assert なしで列挙中の制御転送が返らない（RP2040/RP2350 の HCD には制御転送の時間切れが無い）と、やはり抜けない。
  ポートの電源の入れ直しの直後に起きた。時間で見張る案（タイマー割り込み）は、回し合いの間はタイマー割り込みも届かず
  （列の操作が `critical_section` で割り込みを止める）、働かなかった。この pico-sdk の TinyUSB は OSAL が pico 用なので、
  列のロックは `hcd_int_disable` を通らない（数えても 0 だった）

## 【2026-10-09】ATA パススルー（SAT）で IDENTIFY DEVICE を読む（ファイラーの Shift+F12、`src/input/usbata.c`）

## 2026-10-09 裏読み（epx）の割り込みの嵐

- 症状: exFAT の PNG を表示している間にときどき、core0 の描画が数フレーム止まった（`late_render`。期限のとき core0 が 92〜128 ライン遅れ、core1 は先にいる）
- 調べ方: ライン割り込み（最優先）の中で、core0 が表示に追いつかれそうになった瞬間の NVIC の実行中・保留中の割り込みを写した -> **USB の割り込み（IRQ 14）が実行中で、
  描画の割り込み（IRQ 51）が保留**。USB の割り込みが続けて実行中だったライン数を数えた -> 最長 161 ライン（約 5ms）。裏読みの受け口の 1 回は最長 4µs だが、
  **出てから 5µs 以内に入り直した回数が 1 秒に約 49 万回**（嵐）
- 原因: 空振りの割り込みの要因は `BUFF_STATUS` | `TRANS_COMPLETE`。裏読みを始める直前に、**ほかのエンドポイント（割り込み枠）の完了**が残っていると、
  その `buf_status` のビットは TinyUSB のもので、差し替えた受け口（epx の bit0 しか下ろさない）では下りず、割り込みが入り直し続けた
- 直し（`usbhw.c`）:
  1. 始めるとき、ポーリングを止めて 200µs 待ったあとで `buf_status` が 0 でなければ借りない（`usbhw_bg_refused_pending`。TinyUSB が先に片付ける）。
     8 回の PNG で 5 回これで断り、空振りの割り込みは 0
  2. 念のため、裏読みの間に epx 以外の完了が来たら `BUFF_STATUS` の割り込みを止め（epx の完了は `TRANS_COMPLETE` で来る）、戻すときに元に戻す（`usbhw_bg_masked`）
- この嵐が、映像の「1 フレーム遅れに固定」（`docs/notes/video.md`）の引き金だった

## 2026-10-10 ファイラーの F8: 割り込みエンドポイント 15 本と機器

- RP2350 の USB ホストは、EP0 とバルクに共用の epx のほかに、ハードがポーリングする割り込み用のエンドポイントを 15 本持つ

## 2026-10-10 NTP（SNTP）・USB の窓への写しで HardFault

  newlib の memcpy は端数を「1 バイト -> 2 バイト」で写すので、長さを 4 で割った余りが 3 のとき 2 バイトの書き込みが奇数の番地に当たる。

- 起動時のバナーの終わり（モード 1 -> 2）で表示が乱れる件（積み残し）: 列挙が遅れて重なるとき。機器がつながってから 3 秒たつまで切り替えを待つようにした

## 2026-10-10: 「マウスとキーボードを両方つなぐとキーボードがトラブる」を追った
構成: ドック（VL817 `2109:2817`、その 1 番ポートの先に `1A40:0101`。ドックの中にハブのチップが 2 つある）、
キーボード `258A:0016`（Full）、マウス `045E:00A4`（Low）、USB メモリ、LAN（RTL8153）、VL817 の中の機器 `2109:8817`。
- **マウス・キーボードとも、使っている間は止まっていなかった**（マウスを 2 段目、キーボードを 1 段目に入れ替えて）。キーボードが効かなくなったのは
  **USB ホストの作り直しで全部の機器が数秒〜20 秒外れていた間**だった。作り直しのきっかけは 2 つ:
  1. **「機器が減った」の誤判定**: `2109:8817` が列挙の途中（マウントの前）で外れ、TinyUSB がそれにも `tuh_umount_cb` を呼ぶ
     （`process_removing_device` は列挙の途中の機器を区別しない）。こちらが数から引いていたので「減ったまま 5 秒」で作り直していた。
     → **マウントを知らせた機器だけ引く**（`usbhost_mount_seen` で見分ける。ログは `device removed before it was mounted`）。
     直す前は 10 分で作り直し 3 回、直したあとは 11 分で 0 回（`underrun 0`）。
  2. **制御転送の詰まり**: 生存確認（キーボードへの GET_DESCRIPTOR(device)）が返らず、10 秒後に作り直した。
     → アドレス 0 だけだった打ち切り（`dev0_abort`）を**全アドレスに広げた**（`ctrl_abort`。2 秒で失敗の完了を入れる。
     アドレスのある機器へ続けて 3 回打ち切っても戻らなければ作り直す。生存確認の失敗は「返ってきた」に数えない）。
     実機では、作り直しのあとの列挙の途中で 4 回働いた（`a control transfer to addr 1 did not return in 2 s -- failing it`）。
- **【教訓】観測のしかたで「止まった」を作った**: レポートの数を SWD の `mdw` で読み続けている間は C_DEBUGEN が立っているので、マウスを挿し直したときの
  TinyUSB の assert（`TU_BREAKPOINT`）で CPU が止まり、SWD を離したあとウォッチドッグで再起動した。HID の数を長く見るときは UART のログ（`[run] hid` 行）で。
- **【教訓】HID は操作しないとレポートを出さない**。「レポートが 0 のまま」は、操作してもらっているときだけ意味がある（2 回読み違えかけた）。
- F8 の一覧で HID の種類がずれていたのは、HID のインスタンスの番号を機器ごとの番号と取り違えていたため（全体の通し番号）。

## 2026-10-11: 制御転送の打ち切りで、割り込みを止めたまま 100µs 待つと表示の DMA が止まる
- 2 秒返らない制御転送の打ち切り（`usbwatch.c` の `ctrl_abort_now`）で、SIE に STOP_TRANS を出して 100µs 待つ間、割り込みを止めていた。
  打ち切るたびに `fifo_stall` が約 3000（underrun は 0 = 描画ではなく、リングから PIO へ送る DMA が止まった）、表示経路の自動の作り直しが走った。
  **モード1（FB なし）でも起きた**。ライン割り込みが 3 ライン遅れると、ライン表の巻き戻しなどに間に合わず表示の DMA が止まるらしい。
- 切り分け: USB の割り込みは 0.1 秒に 1〜7 回で 1 回 2µs（入り直し続けてはいない）。アプリのループを 0.45 秒止めても起きない。
  STOP_TRANS と待ちを外すと起きない（ただし古い転送があとで返り、TinyUSB が `ep 80 was already available` で panic してウォッチドッグで再起動した）。
  STOP_TRANS を決まった値で書いても起きる。**STOP_TRANS は出し、待つ間だけ割り込みを止めない**と、90 秒で打ち切り 14 回、作り直し 0・panic 0。
- **【訂正】** 10/10 に「印を下ろすと直った（印が残ると USB の割り込みが入り直し続ける）」と書いたが、約 2900 の本当の原因はこの待ちだった。
- 教訓: **割り込みを止めたまま待たない**。表示の経路は、ライン割り込みが 100µs 遅れるだけで壊れる（自動の作り直しまで戻らない）。

## 2026-10-23: USB をタスクにしてから見つけたこと（tuh_task が抜けない・ハブに機器用の番地・LAN・SD カード・ペンタブレット）

### USB のタスクと usb_lock
- TinyUSB とその上の層を、core1 の M33BEATOS の USB のタスク（優先度 7）で回すようにした（`usbhost.c` の `usb_task`、`SPEC_m33beatos.md`）。USB の割り込みと 1ms ごとに起きる。
  アプリ・LAN・Ruby とは `usb_lock` で交互に動く。スタックは 4KB -> 2KB（実測の最高 792 B。4KB だと LAN をつないだとき PNG の解読の 64KB がアリーナから取れなかった）
- TinyUSB の待ち（`tusb_time_delay_ms_api`、列挙の 450ms など）は、USB のタスクの中なら眠る（`usb_lock` は持ったまま。その間アプリは待つ）

### tuh_task が抜けない回り方（ウォッチドッグの再起動の連鎖）
- CD ドライブのハブ（`214B:7250`）の先に 4 台を一度につないだとき、起動のたびにウォッチドッグで再起動した。止まった場所は `tuh_task` の中（USB の段 0x10）、待ちの外
- プロファイル（`scripts/mbprof.py`）で USB のタスクが 99.5〜100%・自分のループを 1 周も終えず、アプリは 0%。core1 の PC は `tu_fifo_read` / `queue_event` の往復と、
  core0 が取得の間待たせる割り込み（`core1_bell_isr`、アプリがはみ出したまま開始を出せないので待たせっぱなし）
- 原因: `tuh_task_ext` は知らせの列が空になるまで回る。列挙中に来た別の機器の `DEVICE_ATTACH` は列の後ろへ積み直され、ほかに知らせがあると取り出しては積み直すを繰り返す
  （usbh.c にも "otherwise we may loop forever"）。列挙中の機器（キーボード）が制御転送に答えないと列挙が終わらず、答えない転送を打ち切る見張り（`ctrl_abort`）は
  `tuh_task` から戻ったあとなので来なかった
- 直し: `--wrap=tu_fifo_read` で知らせの列の取り出しを包み、`tuh_task` に入って 50ms を越えたら空と返す（1 件の大きさが `hcd_event_t` のものだけ）。
  知らせは列に残り、次の `tuh_task` が続きを処理する（`usbfix.c`）。直したあと同じつなぎ方の 4 回の起動でウォッチドッグ 0 回（抜けさせたのは 1 回の起動で 9〜10 回）

### ハブに機器用の番地が配られて hub_data の外へ書いた

### 2026-11-05 ハブ交換（1A40:0101 + ASIX 0B95:1790）

セルフパワーの新しいハブに交換したところ、ファイラの画面が「読んでいます」のまま固まり、
キーボードのハイライトが動かなくなった。Num Lock の LED は切り替わるので、USB のレポート自体は
届いている。旧ハブ `2109:2817` では再現しない。

- RAM の TinyUSB ログ（SWD で `usblog_keep` を読む）に `USBH Device Attach` の繰り返しと
  `Failed` の連続があった。`[run]` は 60 Hz でフレームを出し続けるが `glyph refresh 0 cells`、
  `tuh_task max=500512us`。
- 新しいハブ内蔵の ASIX AX88179（`0B95:1790`）で、RX と通知（割り込み）の再要求が失敗し、
  毎フレーム `Failed` を出して表示を圧迫していた。`ecm.c` で失敗時は **1 秒バックオフ**し、
  最初の数回だけ `[ecm] rx/int re-arm failed (...)` を出すようにした。これで `Failed` の
  連発は止まった。
- ただし、キーボードの制御端点（`GET_DESCRIPTOR(device)`）が詰まって 10 秒後にホストを
  作り直す問題と、表示の再描画（`glyph refresh`）が 0 のままという問題は残った。
- 遠隔の `USBKICK` コマンドでキーボードの HID 端点を 20 ms ごとに張り直す試しを追加した。
  キーボード本体（addr1 inst0）を対象にしたが、このハブでは制御端点の詰まりは解消しなかった。
- **表示の固まりの原因と対処**: ファイラは全体描画に `video_app_us_left() >= FULL_DRAW_US`
  （1ms）を要求する。新しいハブでは LAN/USB がアプリ時間を食い、毎フレーム 1ms を切ったため
  `dirty` のまま全体描画が永久に先送りされていた（`glyph refresh 0 cells`）。1 秒以上描けない
  ときはアプリ時間が足りなくても強制的に描くようにして、ハイライトが動くことを実機で確認した。
- **キーボードの制御端点**: 生存確認（`GET_DESCRIPTOR(device)`）が返らない HID は、ホスト全体
  ではなく**その機器のハブ・ポートだけ**をリセットする（`usbwatch_stuck_check` の `reset_force`）。
  これで 10 秒 busy からのホスト作り直しを避けられる。
- **ASIX LAN**: このハブ内蔵の `0B95:1790` は、RP2350 の Full Speed ホストでは時々しか
  列挙しない（一度は DHCP まで通ったが、リセット後に消えることがある）。キーボード・USB メモリ・
  表示は安定したので、LAN は Full Speed の相性問題として残る。必要なら別の LAN アダプタを使う。
- **最終構成（実機で3台同時に動作）**: キーボード `258A:0016` = hub9 port2、
  ASIX LAN `0B95:1790` = hub9 port3、USB メモリ `13FE:3600` = hub9 port4。
  LAN を port4 に挿すと見えなくなることがある（このハブのポートごとの電力/相性）。
  LAN は port3、メモリは port4 で安定。表示は強制描画で復帰し、ハイライトが動くことを確認。
- 結論: 旧ハブ `2109:2817` は安定。新ハブ `1A40:0101` は、表示の強制描画・HID のポート限定
  リセット・ASIX の再要求バックオフを入れたことで、キーボード・USB メモリ・LAN・表示が
  使える。LAN のポート相性（port4 で見えない）だけが残るハード側の注意点。
  LAN ドライバの再要求バックオフは、ほかの ASIX 環境でも `Failed` の連発を防ぐ。

### 2026-11-05 USB-ATAPI ブリッジ `05AB:0200`（ベンダー独自）

USB ドライブケースの USB-ATAPI ブリッジ `05AB:0200` を、`05E3:0606` ハブの先に接続して調べた。
原因は DVD-RAM ドライブ本体ではなく、**このブリッジがベンダー独自プロトコル**であること。

- `USBDEV`（`&` キー相当の遠隔コマンド）で構成記述子を読むと、interface 0 は class `ff`
  （ベンダー独自）、subclass 00、protocol ff。alt 0 は bulk OUT `01` だけ、alt 1/2 は
  bulk OUT `01` + bulk IN `82`（64 バイト）。
- `usbufi` の quirk に `05AB:0200` を ATAPI + BOT として足し、`find_bulk_alt()` で alt 1 を
  選んで端点を開き、`SET_INTERFACE(1)` を送るところまで進んだ。`[ufi] alt 1 selected` のあと
  INQUIRY（12h）を送ったが、**CSW の署名が `00 00 00 00`** で、REQUEST SENSE（03h）・
  TEST UNIT READY（00h）も同じ。標準 BOT/SCSI を話していない。
- さらに UFI のデータ段が 20 秒返らず、リセットを繰り返して**同じハブの USB メモリと LAN まで
  落ちた**。そのため `05AB:0200` の quirk は外し、未対応のままにした（alt 設定を選ぶ汎用処理
  `find_bulk_alt()` と `SET_INTERFACE` の手順は残した）。
- 対応するには、このブリッジのベンダー独自プロトコル（CBW/CSW の形式）の資料か、PC で
  正常に動くときの USB キャプチャ（usbmon / Wireshark）が要る。別の USB-IDE/SATA ブリッジで
  標準 UFI/MSC を出すものに変えるのが早い。

### 2026-11-05 高負荷構成（15 端点・EP0 の飽和）

Elecom ハブに USB メモリ・LAN・キーボード・セカンドハブ（`05E3:0606`）を付け、
セカンドハブに USB メモリと USB HDD（`152D:0578`）を付けた構成で、空きポートに
マウス（`045E:0083`）を挿したところ、セカンドハブ側の HDD と USB メモリが見えなくなり、
マウスを抜いても戻らなかった。

- RP2350 ホストの非制御エンドポイントは **15 本**（ハブの状態・HID・バルクを全部含む）。
  この構成はマウスを足すとほぼ満杯になる。
- 満杯のときに `hcd_edpt_open` が新しい端点を開こうとすると HCD が NULL を踏み、
  既存の機器まで落ちる。`__wrap_hcd_edpt_open` で空きを数え、**満杯なら新しい端点を
  開かず false を返す**ようにして、既存の機器を守る（`[usbfix] no free interrupt
  endpoints ...` を最初の数回だけ出す）。
- さらに、制御用の EP0 は全機器で 1 本を共有する。キーボードの生存確認
  （`GET_DESCRIPTOR(device)`）がハブの負荷で返らず、10 秒後にホスト全体の作り直しが
  走って LAN と HDD まで落ちた。`stuck_target()` から **HID を外し**、ストレージの
  制御端点だけを生存確認するようにした。HID の停止は `hid_rearm_check` / kick が見る。
- 15 本という上限と EP0 の帯域はハードの制約なので、フル構成（ハブ2 + キーボード +
  LAN + メモリ2 + HDD + マウス）を安定させるには、機器を減らすか High Speed ホストが要る。
  安定する組み合わせの例: キーボード + メモリ1 + LAN / キーボード + セカンドハブ + HDD + メモリ1（LAN なし）。

## 2026-11-08 MSC の同時転送とキーボードの復帰（USBRESTART）

- **原因**: `msc512` の「512 バイト機器 + SRAM バッファ」の近道が `m5.busy` を立てず、
  G: の読み出しと A: の書き込みが同時に走ることがあった。RP2350 の HCD はバルクを 1 本ずつしか
  扱えないため、完了が返らず 30 秒の時間切れになり、同じハブのキーボードの HID 端点も `xfer=busy` で
  残ることがあった。全転送を `m5` で直列化し、busy の確認と設定を `save_and_disable_interrupts` で排他した。
- **`USBRESTART`**: 遠隔コマンドで `usbkbd_restart()` を呼び、USB ホストスタックを作り直す。
  キーボードが `USBINFO ALL` で `xfer=busy`・`last report` が古いままのとき、UART から
  `USBRESTART` を送ると再列挙されて戻った（実機）。`USBSYNC` / `USBRESET` / `USBREAD` は
  ストレージの切り分け用（書き込み確定・BOT 立て直し・生セクタ読み）。
- **注意**: 2 台の USB-HDD を同時に使う長時間の FAT コピーは、まだ JMS578 側で詰まることがある。
  G:→B:（同じ HDD の exFAT）は 303 ファイルで成功し、B:→A: で補完して A: も 303/303・大きさ一致になった。

## 2026-11-16 ハブ越しのロースピードのキーボードと「もっさり」

- 109 キーボード（Elan `04F3:0103`、ロースピード）をハブ `1A40:0101` の先につなぐと、キーの反応と修飾キーの表示が遅い、という報告（ユーザー）。
- **キーボードも GET_REPORT で読む**（`usbkbd.c` の `kbd_poll_*`、既定 `SGNANO_KBD_CTRL_POLL 1`）: ハブ越しのロースピードの割り込み転送が数レポートで止まるのはマウスで分かっていたので（`SGNANO_MOUSE_CTRL_POLL`）、キーボードも 8ms ごとに GET_REPORT(Input) で読む。キーボードのレポートは「いま押している状態」なので、同じ中身は `was_pressed` で二重に数えない。読めている間は割り込みのレポートを捨てる。20 回続けて失敗したら割り込みの道に戻す。成功のたびに `usbhost_hid_last_ms` を進め、リピートの見張り（5 秒来なければ止める）が切らないようにした。
- **切り分けの道具**: 遠隔コマンド `KBDTRACE`（割り込みの道と GET_REPORT の道のレポートを、中身が変わったときだけ時刻つきで残す。ほかに「監督がキーを取った」「ファイラーがキーを処理した」「修飾キーの表示を描いた」「ファイラーが usb_lock を 2ms 以上待った」の印。読むと空になる）と `KBDPOLL ON|OFF`（GET_REPORT で読むかを動いたまま切り替える）。
- **測った結果**: このキーボードはハブ越しでも割り込み転送が止まっておらず、押した・離した瞬間は割り込みの道でも GET_REPORT の道でも数 ms 以内に見えていた（GET_REPORT は 1 秒に約 125 回、失敗 0）。遅れていたのは画面の側で、Shift のレポートから修飾キーの表示まで 200〜920ms かかることがあり、1 回は描かれなかった。描いた直後のアプリ時間の残りがほぼ 0 だった。
- **原因はドライブ文字の固定（同じ日に入れた `fdrvfix.c`）の退行**: ファイラーは毎フレームドライブの一覧を作り直し、そのたびに表（64 行、キャッシュを通らない PSRAM）を「予約した文字か」で 26 x 64 行、照合でドライブごとに 64 行、書き足しの検索でドライブごとに 64 行（シリアルの文字列比較つき）引いていた。これでアプリ時間を使い切り、修飾キーの表示（残り 400us 以上で描く）と全体の描き直し（1ms 以上で描く、最長 1 秒待つ）が後回しになった。
- **直し**: 有効な行（8 つまで）の番号と固定した文字のビットを SRAM に持ち、表を書き替えたときだけ作り直す（`reindex`）。照合と予約の確かめはそれだけを見る。書き足しの確かめは 1 秒に 1 回。直したあとは、描いた直後のアプリ時間の残りが約 0.2〜0.3ms あり、ユーザーの確認で「キーの反応が軽く、修飾キーの表示もきびきび動く」。
- **教訓**: 毎フレーム回る処理（ファイラーの `scan_drives` など）に足すものは、キャッシュを通らない PSRAM を何度も引かないこと。足したらアプリ時間の残りを測る（`KBDTRACE` の draw-mods の 2 つ目の値が残り / 10us）。
- **【追記 2026-11-17】GET_REPORT で読む作りは既定で切った**（`SGNANO_KBD_CTRL_POLL 0`）。exFAT の A:（320GB）から 96kHz/24bit の WAV（1 秒に約 576KB）を鳴らすと、8ms ごとの読み取りで負荷が上がって途切れた（ユーザーの実機では負荷 500%）。0.5 秒に 1 回の「割り込み転送が止まったときだけ速く読む」見張りにしても、12〜15 秒で途切れが 7〜10 回増え、切ると増えなかった（同じ曲・同じ時間で並べて測った）。ハブ越しのロースピードの制御転送は USB の口を 1 回ごとに長く占め、USB メモリの裏読みが中断される。FAT32 の B: で目立たないのは、FAT32 が大きな塊を一度に読み、割り込まれる回数が少ないためと見ている。この 109 キーボードは割り込み転送で届いていたので困らない。止まるキーボードに出会ったら、遠隔コマンド `KBDPOLL ON`（見張りの形で入る）で試す。マウスの GET_REPORT（`SGNANO_MOUSE_CTRL_POLL`、8ms ごと）も同じ取り合いを起こしうる（ハブ越しのロースピードのマウスをつないで大きい WAV を鳴らすときは注意）
